## 0. 为什么这一页差点建错东西

`impact/index.ts` 今天按「同名即引用」连边（`addSites(refs, t.name, …)`），页面里已经把自己的病写进文案：
「一个 `private readFile` 吸进 107 个文件的同名 ref」。第 300 页接精确边时**刻意没动它**。
我第一版探针只量了一种切法（「按 import 收紧」），跑完准备动手时才发现——

> `fixtures/impact/accuracy-repo/ground-truth.json` 的 note（2026-10-01 人工核对）写着：
> 「def/ref **按名字连边、不采 import**——同名定义的调用点按合同连到全部两份定义，**不算假阳性**」

那个夹具是**全局脚本形状**的仓库：`api.js` 直接 call `slugify(...)`，整份文件没有一个 import 语句。
⇒ 「按 import 收紧」会把冻结判卷的 16 条真值边删到剩 1 条。这条不是我改得动的（AGENTS.md：不许把冻结判卷面
当 workaround 改），所以这一页改成**四种切法各数一遍，并同时对着那个夹具数「会掉几条真值边」**——
安全的那一种才是能买的。这个反序（先想删、后发现自己一直踩着合同的另一头）就是量在前面的价值。

## 1. 四种切法（真仓 8769 对 vs 冻结夹具 16 条真值边）

| 切法 | 判据 | 真仓摘掉 | 夹具 16 条存活 | 买不买 |
| --- | --- | --- | --- | --- |
| B 文件级 | ref 文件 import 过 def 文件 | 6096（**69.5%**） | **1/16** | ✗ 毁合同 |
| C 名字级 | 且名字真出现在那条 import 子句里 | 6170（70.4%） | **1/16** | ✗ 毁合同 |
| D 负面证据·本地自有 | 引用方自己也 def 了这个名字 ⇒ 摘 | 4276（48.8%） | **16/16** | ？摘得多但**没摘到病**（下表两个大户的「自带同名」都是 0） |
| E 负面证据·另有归属 | 引用方把这个名字**绑在别处**（从第三方文件或外部包 import）⇒ 摘 | 576（**6.6%**） | **16/16** | ✓ 摘得准：正好命中那两个大户 |

E 的"另有归属"里 **`node:fs` 这种外部包也算证据**——这正是 `writeFile`/`readFile` 那两行的成因。
B/C 摘掉的绝对数最大，但它们与 D/E 不是一回事：B/C 要求"有正证才连边"，D/E 只在"有反证时才摘边"，
没有证据（全局脚本仓库）就照旧连边 ⇒ 只有后者与夹具登记的合同相容。

## 3. 读数的边界（不许被读成别的）

- 两个数之间的 10 对差（8759→8769）是**工作树在飞**：隔壁会话正在改 `orchestrator.ts` 等文件，
  两次跑之间被扫进来了。这一页所有数都是**工作树读数**，不是 HEAD 读数。
- `591 个文件解析成功／读不到＝0／解析失败＝0`——这两格单列，不并进任何比例的分母。
- 探针是现读，不产帽不产判据 ⇒ 不进 `package.json` 门表；自检要求「真仓 A>0、数到同名大户、
  夹具真值面跑到了、且 A≥B≥C 单调」，缺一格就退 1。
- **这一页的自检是事后补的，而且是它最该早一点在的时候**：第一版只数真仓（B/C 两种切法、没有任何反面对照），
  按那份读数我就会去建「按 import 收紧」——正好撞在冻结夹具登记的合同上。
  是去读 `ground-truth.json` 那句 note 才把「同一套判据对着夹具再跑一遍」这一格补进探针里的。
  教训与「报数前先重测」「命中率候选形状要穷尽」同一族：**候选切法要穷尽，且每种都要跑一遍
  "它会不会伤到已登记的真值面"**——只量收益不量代价，就会建出一个把冻结合同踩掉的"改进"。
