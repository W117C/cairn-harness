## 一、闸放在哪一格，为什么不是更"自然"的那格

`remember` 有**两个生产者**，且它们走不同的门：

1. 主会话：`createGatedRemember`（`agent-runner.ts:767-778`）→ 方案门 / 档位 / 审批卡 → `remember.run`
2. **会话结束沉淀轮：`rememberTool: remember`（`agent-runner.ts:1470`）——交出去的是未加门的工具本体**
   （合并审批本身就是那一轮的权限门）

⇒ 把闸放在 main 层的包装上，**恰好绕开最容易含密钥的那条路**：沉淀轮的输入是整段会话回放，
`read_file` 读到的 `.env` 内容正在里面，而那一轮没有逐次审批卡。
放在 `remember.run` 一处即同时覆盖两者——这也是为什么这里不需要第二份实现。

⚠️ 那条 0 单独看没有意义——死尺也报 0。所以自检同印在输出里，且 `files===0 || 自检失败 ⇒ exit 1`。
反控用的是本仓自己的判卷散文（sha256 冻结、`gate-manifest.ts` 事实源），里面**有**十六进制字样与
`file:line` 锚点，正是最容易触发高熵支的形状 ⇒ 这一支绿了才说明「0 误伤」是性质不是巧合。

⇒ 结论：**不需要按 ruleId 分档**（原拟的「模式名才改、纯高熵只报」这一层复杂度当场没有必要），
一律复用 `redactSecrets` 的产物：命中即掩码落盘、回执点名处数；`blocked` 沿用 `scan.ts` 既有契约
（「true = 命中 critical（如私钥块）：调用方应拒绝而非仅脱敏」）——**拒绝档不是我新造的政策，是老 API 早就要求调用方做的事，只是此前没有调用方照做**。
