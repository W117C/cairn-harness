本仓的插件发现只有三个入口（`src/agent/plugins/discover.ts:271-298`，调用点 `src/main/agent-runner.ts:2525-2527`）：

⇒ 本机当前：**0 个插件、0 个 MCP server、0 个受信 skill**。§1 的 22 件就是本机现状的全部。

## §3 断点算术：什么条件下才碰得到帽

余量 12,502 字符。合成载荷（`desc` 长度 × 每个参数属性的 `desc` 长度；MCP 侧 `parameters`
是 server `inputSchema` **原文直传**，见 `glm-session.ts:452-453`，故单件体积实际不封顶）：

| 载荷档 | 单件 chars | 断点件数 | 现实性 |
|---|---:|---:|---|
| 精简（desc 200 / 2 属性） | 641 | 19 | 常见 |
| 中等（desc 600 / 4 属性） | 2,441 | **5** | 常见 |
| 话痨（desc 2048 / 6 属性） | 10,611 | **1** | 上界侧，实际存在 |
| 极端（desc 2048 / 12 属性） | 19,463 | 0 | 罕见 |

单条 MCP 描述的装载期硬帽是 2,048（`MCP_DESCRIPTION_CHAR_LIMIT`，`src/agent/plugins/mcp.ts:32`），
只管 `description`，**不管 `parameters`**。

**结论 2：碰帽不是「装了很久才会」，而是「装 1 个话痨 server 或 5 个中等 server 就会」。**
而且 MCP 是本仓的一等公民功能（有分级、信任门、白名单），不是野路子。⇒ 这是一个
**「等第一个人装 MCP 时就会踩」的潜伏缺陷，不是当前成本**。

## §4 碰帽那一刻：降配梯的动作与代价

以「中等」载荷（单件 2,441 字符）逐级加 MCP 工具，走真实的 `planSurfaceBudget`：

| MCP 件数 | 超帽 chars | 压描述 | 丢工具 | unresolvable | 仍然可缓存的前缀 |
|---:|---:|---:|---:|---|---|
| 4 | 2,082 | 4 | 1 | false | 11,471 / 25,385（45.2%） |
| 6 | 9,374 | 6 | 3 | false | 11,471 / 32,677（35.1%） |
| 8 | 16,666 | 8 | 5 | false | 11,471 / 39,969（28.7%） |
| 10 | 23,958 | 10 | 7 | false | 11,471 / 47,261（24.3%） |
| 12 | 31,250 | 12 | 9 | false | 11,471 / 54,553（21.0%） |

梯级 A 先把非 core 的描述压到 600，梯级 B 从尾向前整条丢 `optional`。两点值得记：

1. **定时五件排在 MCP 之前**（`gateToolSpecs` 先 push 它们，注入项后 append）⇒ 超帽时先丢 MCP，
   定时五件只有等 MCP 全丢光才会被丢。这是好的顺序。
2. **梯级 A 本身就吃掉大部分前缀**：压描述改的是中段，缓存按前缀命中 ⇒ 稳态前缀只剩 ~11,471 字符，
   占面宽度的 21%–45%。所以「已经压过一次的描述」和「没压过的」之间，还有第二次跳变的隐患
   （体积回落时不会自动展开回逐字原文——`planSurfaceBudget` 的快路径只在**从未超帽**时保证逐字不变）。

**结论 3：降配梯一旦触发，prompt cache 的复用率会掉到两成到四成。这不是理论推断，是上表的实跑数字。**

## §5 唯一一条真硬伤：两把预算的口径不对齐

### 5.1 降配梯的账漏了易变侧

`MODEL_SURFACE_TOTAL_CHAR_LIMIT` 的注释（`src/agent/model-surface.ts:5-8`）说这顶帽管的是
「固定面 + 易变 system 块的字符和」，`SurfaceBudgetInput` 也有 `volatileChars` 字段。但**生产调用点
`src/agent/glm-session.ts:882-888` 不传它** ⇒ `accountModelSurface` 落到 `volatileChars = 0`
（`model-surface.ts:83`）。

易变侧四块各自的硬帽（`measure-volatile.mts` 实跑，字符/token 分列不混算）：

| 块 | 硬帽常量 | 登记口径 | 中文折字符 |
|---|---|---|---:|
| 记忆注入 | `MEMORY_TOKEN_BUDGET_DEFAULT = 6_000` | token | 6,000 |
| skill 重挂·合计 | `SKILL_REMOUNT_TOKENS_TOTAL = 25_000` | token | 25,000 |
| skill 路由清单 | `SKILL_ROUTING_CHAR_LIMIT = 1_536` | char | 1,536 |
| 符号地图·上限 | `MAP_TOKENS_MAX = 4_096` | token | 4,096 |
| hook 上下文 | `HOOK_CONTEXT_TOTAL_CHAR_LIMIT = 24_000` | char | 24,000 |
| 附件引用 | `formatAttachmentContext` 每附件一行路径 | 无需帽 | 可忽略 |

**易变侧最坏合计 ≈ 60,632 字符（中文）／165,920（英文），是降配梯视野（11,498）的 5.3 倍／14.4 倍。**

同值巧合值得单独点名：`HOOK_CONTEXT_TOTAL_CHAR_LIMIT` 与 `MODEL_SURFACE_TOTAL_CHAR_LIMIT`
**都是 24,000**，但互不承认对方——hook 上下文进 skills 块，而 skills 块不在后者的口径里。

### 5.2 但不是「默默超支」：另两把账是全的

这条必须说清楚，否则会把缺陷读成钱在偷偷烧：

- **压缩预算全量计了**：`glm-session.ts:937-941` 的 `AssemblyOverhead` 里
  `systemChars` 含 `skillsBlock` 与 `attachmentContext`，另计 `memoryChars` / `mapChars`。
- **最终 fail-closed 硬闸**：`glm-session.ts:1002-1010` 的
  `finalChars = JSON.stringify({messages, tools}).length` 超限直接 throw，请求不发。

⇒ 准确的说法是：**降配梯在真正该出刀的那一轮永远不出刀**。
它只看得见固定面，而压力来自易变侧；于是压力全部落到「压缩（削历史）」或「硬闸（整轮失败）」，
**「削工具面」这条最便宜的路被结构性地排除了**。

### 5.3 本机现状：易变侧不是 0

实跑（本仓工作区）：

| 块 | 实测 | 怎么量的 |
|---|---|---|
| 记忆 | **0 字符** | `buildMemoryInjection({workspace})` → `{project:null, global:null, charsCurrent:0}`；`.agent/` 下无记忆文件 |
| skills 块 | **0 字符** | 无插件 ⇒ `pluginContext` 返回 undefined |
| 符号地图 | **3,978 字符 / 1,047 tok** | `createMapBuilder().build(...)` + `mapInjectText(...)` 实跑 |
| 附件引用 | 0 | 无附件 |

⇒ **首轮真实固定成本 = 11,498 + 3,978 = 15,476 字符 = 帽的 64.5%**，
而降配梯报的是「47.9%，在帽内」。两者都不算错，但**只有前者是这一轮真发出去的字节**。
地图只在 `history.length ≤ 2` 时注入（即首轮）。

**装上第一个带 hook 的插件就能把这一格推到 100% 以上**——hook 上下文一项就 24,000 字符 = 整顶帽。

### 5.4 「修账本」实际等于三件事，代价不一样

| # | 事 | 代价 | 判 |

| 1 | **改注释**：说清这顶帽管的是固定面（system+工具），易变侧另有各块硬帽 | 只改一段注释 | **✅ 已做**。`model-surface.ts` 文件头与常量文档已按实参改写，并把「为什么不解开循环接进去」的三条理由钉在原地 |
| 2 | **给尺子补字段**：`surface_account` 增记四块字符数 | 4 个字段 + 测试 | **✅ 已做**（见 [施工回执](../tool-face-volatile-account-receipt-2026-10-03.md)）。⚠️ 口径比先前想的更微妙：不是「上界」而是**压缩前快照**——压缩会重建 skills 块，且可能因**新增重挂资格而变大**（`plugins/index.ts:466-470`）。已写进字段注释与新判据 |
