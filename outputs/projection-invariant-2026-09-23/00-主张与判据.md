## 一、缺口（本仓自己的指针，含一处已发生的破口）

| # | 面 | 现状 | 缺什么 |
|---|---|---|---|
| G1 | 生产者纪律 | `compaction.ts` 做得对：`atomicUnits()` 按 `callId` 把 `tool_call↔tool_result` 并成单元，`selectCut` 纪律 1「切点不得落在原子单元内部→回退到单元起点」，`selectTruncation` 按单元整丢 | —— 这一侧**没有缺口**（能力 19 §六留的"压缩会不会产孤儿"待核项，本轮结案：**不会**） |
| G2 | **出口校验** | `projectContext` 里只处理两个方向：缺结果的由 `closeDanglingToolCalls` 补一条合约束的 tool 消息；自动验证拍的裸结果降级成 user。**没有任何一处**校验"结果的 id 有没有前驱" | 出口对破纪输入**照吐**（`01` §二 实测：手工只摘 `tool_call` ⇒ 投影吐 1 条孤儿） |
| G3 | **已经在破的两处** | `orchestrator.ts` 的 `stageCallId = callId + "-sup" + n`（supervise 多阶段）与 `stageCallId = chain.callId + "-s" + n`（pipeline 链）——都从未作为 `tool_call` 声明过；**同文件**的兄弟函数 `emitSyntheticResult` 却注释明写「合成 tool_result 挂回原 spawn 的 tool_call id（§4.4.4）」 | 一处是疏忽，**两处是缺不变量**。且 `agent-plan` §4.4.4 早已把这条写成方案要求（"协议自洽无孤儿结果"） |
| G4 | 下游 | `openai.ts` 直传 `tool_call_id`；`anthropic.ts` 拼 `tool_use_id` 进 `pendingToolResults`；`gemini.ts` 查不到名字就 `?? ""` | 三家各一种后果（两种 400 形状 + 一种**静默改名**——最坏的那个反而不报错） |
| G5 | 观测者 | 「投影出来的消息序列合不合法」**没有任何门在跑**（本轮第一次跑，就跑出 3 条） | 与能力 18/19 同一病根：**建了规矩没建观测者** |

**为什么 G2 才是主论**：能改变"哪些事件进上下文"的路径实测有 **8 个文件**在引用排除集/归因判定
（`compaction`、`context`、`orchestrator`、`plugins/index`、`prune`、`sidechat`、`tool-choice`、`events`），
而 `atomicUnits` 的**真实调用点 2 处、全在 `compaction.ts` 内部**（探针报的 3 处里含函数定义自身一行）。
⇒ 其余 7 个都不受该纪律约束。**给每个生产者立一份规矩 = N 份迟早漂移**（本仓为这件事专门立过
「同族出口策略副本」这条名字），而出口只有一份。

**最说明问题的一条**：`context.ts` 里已经有这么一句注释——
「压缩面不产这种形状——`atomicUnits` 把 `tool_call↔tool_result` 并成一个原子单元、切点不拆对（纪律 1）」。
**这句话本身是对的，但它是一句注释，不是一条断言**：它管得住读代码的人，管不住
`orchestrator.ts` 里那两行新写的派生 id。本仓自己立过那条规矩
（`fdbc1ba`：「能静态判定的规矩不该只写在文档里」），这条就是它的一个未收口的实例。

而紧接其后的那句话更值钱，作者写明补悬空调用**不是**在补压缩的漏，而是
「给**任何一条投影出口**都不留未答调用兜底：将来若有面单独摘掉结果，这条守卫仍然成立」。
⇒ **"出口兜底"这个思路在码内已被明确认可并落地过一次**，只是它只兜了「缺结果」这一个方向。
本页因此不是一个新主张，而是**把同一条已获认可的设计补上另一个方向（缺前驱）**——
这也是它比 16/17/18 更该先落地的理由之一（见 §六-1）。

## 二、外部对照（这一类是"常见到有人写修复博文"的级别）

- Anthropic 侧的这条约束是硬状态机：`tool_result` 块必须能找到前驱 `tool_use` 块，否则请求被拒；
  社区里有专门的「tool_result 找不到对应 tool use id 解决方案」排障文，
  以及多篇讲 **Anthropic↔OpenAI 兼容体系之间 Tool Use 状态机适配**的文章（跨模型换协议时这条最容易破）。
- 与本页相关的关键点：**这类错误在多家适配器上表现不一致**——一家 400、一家静默改名、一家可能容忍。
  这正是"必须在投影出口统一收束、而不是在每家适配器各修一遍"的理由（G4 实测三家行为各异）。
- 本仓自己的先例比外部更有分量：`context.ts` 的自动验证拍注释已经把整条推理走过一遍
  （裸 `tool_result` 会 400 ⇒ 合成 `tool_call` 又违反 action-fusion 的「no extra tool calls」
  ⇒ 正解是**降级成 user 消息**）。**通道已经建好、已落地一次，supervise 只是没用它。**

## 三、设计：三层，按依赖排（各答「长在哪 · 谁持有 · 为何不是别层」）

### L0 出口不变量收束器（**主论**，且是纯投影面改动）

`projectContext` 返回前做一次线性扫描：`seen: Set<callId>` 累 assistant 的 `tool_calls`；
遇到 `role:"tool"` 而 id 不在 `seen` ⇒ **不删、不藏**，改投为 `role:"user"` 消息
（正文加一行归属：`[harness] 以下回执无配对调用…`），并计数。

> **⚠️ 判据后来被补宽了一维（能力 22 实测反喂）**：本页初版只写「id 必须在 `seen` 里」，
> 而真投影证明**id 配对对一类破口完全无感**——把一条 `user_message` 插进
> `assistant[calls]` 与它的 `tool` 结果之间，孤儿 0、悬空 0，两项检查全过，
> 但 `context.ts` 注释自己要求的「必须**紧跟**」已经破了。
> ⇒ 收束器判据 = **id 配对 ∪ 邻接**（"非 tool 消息不得插在任何 calls 与其结果之间"），两侧各一根针脚。
> 证据与复跑：`outputs/midrun-steering-2026-09-23/01-实测与回执.md` §二。
> 同一条实测还记下一个**与插话无关的既有形状**：本仓正常投影会在 calls 与结果之间夹一条 assistant 文本行——
> 各家 provider 受不受**未证**，复核时别把既有形状当破口、也别把破口当既有形状。

- **长在哪**：投影**唯一出口**，与 `closeDanglingToolCalls` 并排（同一处、同一族判定，**不新开创面**）。
- **降级成 user 而不是丢**：本仓立过的规矩——**假象比空白更坏**，且丢了判卷/回放就看不见这件事发生过。
- ⚠️ **只改投影面，事件流一字不动**（与 `closeDanglingToolCalls`、能力 19 L0 同一条纪律）：
  写回事件流 = 篡改历史 + 打断前缀缓存（RD/`prefix-churn` 两道已发货门会当场抓）。
- **降级文案不许含 `Date.now()`、不许含派生 id 以外的易变量**（同上两条门）。

### L1 派生 id 纪律（防同族复发）

harness 合成回执**只准挂"已作为 `tool_call` 落过流"的 id**。要发第 2、第 3 阶段，
必须**先声明**（走既有 `tool_call` 落流），或者**由 L0 降级成 user**。
静态棘轮：`src/` 内凡以字符串拼出 callId 的落点（现测得 2 处：`-sup`、`-s`）
必须出现在一份**显式白名单**里，且每条要么配一个真实声明点，要么显式标 `demote-to-user`。

- **长在哪**：与 `TOOL_NAMES` 同类的"静态契约清单"层——`base.ts` 或 `events` 契约面，**不是** orchestrator 内部，
  否则下一个拼 id 的人还是看不见它。

### L2 观测者：把本轮这条扫描变成门

跑真语料（现 45 个含 `tool_call` 的文件）过 `projectContext`，**孤儿数必须为 0**。

- ⚠️ 开门之日它是**红的（3 条）**——属本仓明文的"预期红"，处置顺序必须是
  **先修 G3 那两处 / 或先落 L0 收束**，再把水位收进 `LEGACY_WAIVERS`（**只降不升**口径）。
  **绝不许**为了让门绿而先改判卷语料。

## 五、明确不采纳（理由 / 证据 / 反转条件）

| 不采纳 | 理由 | 反转条件 |
|---|---|---|
| 在 provider 适配器各修一遍 | 三家行为已实测各异（两种 400 + 一种静默改名），补三遍 = 造三份出口副本，正是本仓点名的缺陷类 | 永不——出口收束后三家自动同构 |
| 直接丢弃孤儿消息 | 假象比空白更坏；且丢了就没有"这事发生过几次"的读数（G5） | 永不 |
| 合成一条 `tool_call` 补前驱 | **本仓已自己否决过**：`context.ts` 自动验证拍注释写明它违反 action-fusion 的「no extra tool calls」不变量 | 除非该不变量被正式修订（走裁决，不偷偷改） |
| 只修 `-sup`/`-s` 那两行的 id | 治标：出口仍无闸，下一个生产者再犯一次；而且 G3 的成因正是"某处没想到要挂回" | 作为**热修**可以先走，但必须与 L0 同轮，不许以它收口 |
| 把 supervise 多阶段整体改成 user 消息通道 | 丢掉 §4.4.4 "挂回原 tool_use id" 的语义（模型要能把回执当自己调用的返回来续写） | 反转：若第 2 阶段起的语义本就不是"应答"而是"新事件"，那 user 才是对的——**这一条本轮未证**（`01` §三），要按语义裁 |
| 现在就引入协议级 schema 校验库 | 多一个依赖、多一层分发面；本页这条是 O(n) 线性扫描就够的东西 | 反转：需要校验的不变量多于 3 条时 |
