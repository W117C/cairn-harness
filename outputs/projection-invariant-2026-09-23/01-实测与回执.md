## 一、缺陷：supervise 多阶段的合成回执用**派生 id**，投影吐出孤儿 tool 消息

### 症状（真语料 + 真 `projectContext`）

```
含 tool_call 的语料文件 45 个 → 投影后孤儿 tool 消息 3 条 / 悬空调用 0 条
   outputs/ga-strategy-2026-09-20/supervise.events.jsonl      1
   outputs/ga-strategy-2026-09-20-rep2/supervise.events.jsonl 1
   outputs/ga-strategy-2026-09-20-rep3/supervise.events.jsonl 1
```

三次独立复跑各出 **1 条**，同一条 id ⇒ **确定性**，不是时序抖动（对照 `panels-check` 那种 flake 的判读法）。
逐条点名（真投影输出，非人工推断）：

```
投影消息共 35 条；其中 role:tool 14 条
投影里真孤儿 tool 消息的 id: call_33546c96177b4c95b69c4275-sup1
文件里的 spawn/supervise 类调用: [{"id":"call_33546c96177b4c95b69c4275","name":"spawn_agent"}]
```

### 成因（两兄弟路径，一条守规矩一条不守）

| 路径 | 写法 | 是否合法 |
|---|---|---|
| 单次 spawn 的收队回执 | `orchestrator.ts` 的 `emitSyntheticResult`：`callId: w.spawnCallId`，函数头注释明写「合成 tool_result 挂回原 spawn 的 tool_call id（§4.4.4 注入形态）」 | **合法**（挂回原 id，协议自洽） |
| supervise 多阶段 | 同一个 `orchestrator.ts` 里 `const stageCallId = callId + "-sup" + String(stageCount)`，再把 `{callId: stageCallId}` 传给 `spawnStage` ⇒ 最终落流的 `tool_result` 用的就是这个**派生 id** | **不合法**：主流里从来没有一个叫 `…-sup1` 的 `tool_call` |

⇒ 一条消息同时犯两个错：**原 `spawn_agent` 调用没被回答**（该调用本该由这条回执回答），
而**这条回执自己又无主**。今天看到"悬空调用 0"，是因为
`closeDanglingToolCalls` 在投影时给原调用补了一条合约束的 tool 消息——
**它在掩盖这个派生 id**，而不是这个 id 合法。

而 `agent-plan.md` §4.4.4（本文档集所依据的方案）对此**已有明文**：
「注入形态：作为原 spawn_agent 调用的合成 tool_result 写回主流
（Roo reopenParentFromDelegation 实证：挂回原 tool_use id，**协议自洽无孤儿结果**）」
——`emitSyntheticResult` 是照做的，`stageCallId` 是没照做的。

### 本仓已经有的正确通道，它没用

`context.ts` 的自动验证拍注释里把同一类问题已经推演过一遍，原话：

> 「harness 补拍没有配对的 tool_call，**裸 tool_result 会让 provider 侧 tool 消息失去前置 tool_calls 而 400**，
> 合成 tool_call 又违反 action-fusion 的「no extra tool calls」不变量 ⇒ loop 当时只能「落证据不外注」。
> 这里补上那条合法通道：投影阶段把它作为**一条 user 消息**回流。」

⇒ **正解在同一个仓里已经落地过一次**（降级成 user 消息）。supervise 那两行只是没走它。

### 下游不设防（三家适配器各一种后果）

```
openai.ts    ：...(m.tool_call_id !== undefined ? { tool_call_id } : {})      → 原样出网
anthropic.ts ：pendingToolResults.push({ type:"tool_result", tool_use_id: … }) → tool_use_id 无前驱 tool_use
gemini.ts    ：name: toolNames.get(m.tool_call_id ?? "") ?? ""                → 查不到就静默改名成 ""
```

### ⚠️ 一条我**没有**证的东西（不许当成已证）

那三次 ga-strategy 运行**是完成了的**，所以"这条已经在线上炸过 400"**未被证实**。
两种可能都还没排除：① 那次运行的 provider 端容忍（GLM/兼容端点未必严格校验）；
② 注入之后父环再没发过请求。⇒ 落地第一步是**复现到出网面**（真起一次 supervise、看请求体），
别把"投影吐孤儿"直接写成"线上 400"。Gemini 那条的**静默改名**则是另一回事：它不会炸，会更坏。

## 二、缺口不在那个 `-sup1`，在"出口没有第二道闸"（这才是本能力）

故意造三种违反纪律的 compaction，看**真出口**的反应：

```
[吐孤儿]   只摘 tool_call(k1)、留它的 tool_result —— 违反纪律 1 → 孤儿 tool 消息 1 条
[出口安全] 成对摘（k1 的 call+result）—— 纪律要求的形状          → 孤儿 0 条
[出口安全] 只摘 tool_result(k1)                                  → 孤儿 0 条（被 closeDanglingToolCalls 合上）
```

而纪律本身是对的（交叉核对，调真函数）：

```
真 atomicUnits 对样例流划出 2 个单元，其中「call+result」二元单元 2 个
```

三个事实合起来就是本页的主张：

1. **`compaction` 侧守得很好**：`selectCut` 纪律 1「tailStart 不得落在原子单元内部 → 回退到单元起点」、
   `selectTruncation`「按原子单元从最旧起丢」、keep-first 按单元闭包扩护。
   所以**压缩不会产生孤儿**（我在能力 19 §六留的那条待核，此轮结案：裁剪/压缩两侧都不产孤儿）。
2. **但出口对"任何生产者破了纪律"毫无反应**：上面第一行是我手工造的破纪事件流，投影照吐。
   能改变投影集合的路径实测有 **8 个文件**在引用
   （`compaction.ts`、`context.ts`、`orchestrator.ts`、`plugins/index.ts`、`prune.ts`、`sidechat.ts`、
   `tool-choice.ts`、`events/index.ts`），
   而 `atomicUnits` 的**真实调用点 2 处、全在 `compaction.ts` 内部**（探针报的 3 处含定义行自身）。
3. 于是 §一 那个缺陷**必然可能**：`orchestrator` 是投影集合的改变者之一，却不受原子单元纪律约束。

> **一句话**：一个只有生产者自觉、出口不校验的不变量，等于没有不变量。
> 本仓已经有两处在**手工**维持它（`closeDanglingToolCalls` 补结果、auto-verify 降级成 user），
> 第三处（`stageCallId`）漏了——**漏的不是疏忽，是这条规矩没有出口观测者**。

## 三、已证 / 未证

**已证（复跑命令在上）**
- 真语料 45 文件投影出 3 条孤儿，全为同一种派生 id，三次复跑一致；悬空调用 0。
- 派生点在 `orchestrator.ts` 的 `stageCallId = callId + "-sup" + n`，与守规矩的 `emitSyntheticResult` 同文件。
- 出口对"只摘 tool_call"这种破纪输入**不校验、照吐**（合成流实测）。
- 原子单元纪律本身有效（真 `atomicUnits` 输出确认），且只被 `compaction` 引用。
- 三家 provider 适配器各自不设防（两种 400 形状 + 一种静默改名）。

**未证 / 待核**
- 线上是否真发生过 400（§一 末那条，落地第一步就是复现到出网面）。
- supervise 环**第 2 阶段及以后**的 id（`-sup2`…）为何在语料里没出现：
  是那三次运行只跑到一阶段，还是多阶段另有收束路径——**未查**，会影响修复面的大小。
- `promote`/`sidechat` 等其它投影改变者有没有同类派生 id 写法（只查了 `-sup` 一处）。
- 修完之后 supervise 的语义等价性（把阶段回执降级成 user 消息，模型是否还把它当"我调用的返回"来续写）。
