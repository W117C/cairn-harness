# 对照表：Claude Desktop 5.1231.2 × Cairn（现读代码）

> 取证日：2026-11-12。两侧都是**现读**：左列是本轮从 Claude.app 产物实测（证据见 `01-取证摘要.md`），
> 右列是本仓现读源码/规范。**每行都标了「观察」还是「推断」**；推断的行不作为改代码的依据。
> 本页只列**可落成动作**的差异；纯风格偏好不进表。

## 一、架构层

| 面 | Claude Desktop 5.1231.2（实测） | Cairn（现读） | 差异性质 | 判断 |
|---|---|---|---|---|
| 渲染层主体 | claude.ai Web 应用（`ion-dist.asar`：5190 资产 / 4717 JS chunk / `index.html` 52 KB）跑在 Electron 壳里 | 自绘 React 渲染层（`apps/desktop/src/renderer/`） | 路线不同 | **不是差距**：Claude 用 Web 应用复用 claude.ai 的迭代速度；Cairn 是本地优先的自有实现 |
| agent 运行时 | 随包下发 CLI（`claude.exe.zst` 字面量 5 处），宿主拉起子进程 | 自有 core（`src/agent/`、electron-free） | 路线不同 | **不是差距**；但两边的「宿主 ↔ agent」边界值得比（见第五节） |
| 窗口族 | 7 个渲染层（main / quick / about / buddy / find_in_page / file_viewer / local_exec_consent） | 主窗口 + 弹出窗（`PopoutApp`）+ 快速入口 | Claude 窗口面更宽 | **观察**：Claude 把「页内查找」「本地执行授权」「文件预览」都做成独立窗口/独立同意面；Cairn 的本地执行授权走会话内 `ApprovalCard` |
| 能力声明 | frame 契约 **129 个版本**；每版声明 `capabilities`(27) / `changes`(97) / `inertChanges`(69) / `core:["permissions"]` | `src/providers/capabilities.ts` 的 `CapabilityReadout`（单一能力面） | Claude 另有**能力演进账** | **可落动作**：Claude 把「已上线 / 在改 / 已失效」三态写成契约文件并随版本递增；Cairn 只有能力清单，没有「变更/失效」账 |
| 能力装载 | 运行时 manifest 把能力**代码切分**（每能力一个 chunk，懒加载） | 渲染层 `state/` 33 个模块，静态打包 | 体积策略不同 | **观察**，非差距 |

## 二、契约与安全

| 面 | Claude（实测） | Cairn（现读） | 差异性质 | 判断 |
|---|---|---|---|---|
| 桥面形状 | **21 个** `exposeInMainWorld` 全局名 + 约 24 个命名空间对象（`claude.web` / `claude.settings` / `claude.internal.ui` / `claude.internal.computerUse` …） | **1 个** `exposeInMainWorld("agent", api)`（`apps/desktop/src/preload/index.ts`），通道表程序化生成 | 结构差异 | **可落动作**：Cairn 的桥是单一扁平面——好处是窄，代价是**渲染层拿不到「这块能力属于哪个域」**。Claude 的 `claude.<域>` 命名空间让能力归属可枚举（可做一版能力清单判卷） |
| 通道命名 | 结构化拼装 `$<uuid>_$_<namespace>_$_<method>`；**35 个具名状态切片**共用同一序列化格式 | `apps/desktop/src/main/channels.ts` 的 `INVOKE_CHANNELS` / `PUSH_CHANNELS` 映射表 | 结构差异 | **观察**：Claude 35 个状态切片 vs Cairn 渲染层 `state/` 33 个文件——**粒度相当**；Cairn 缺的是「切片清单」这一份可枚举的对照物 |
| 帧身份 | 桥函数先比 `webFrame.top.frameToken` / `routingId`，再核对来源白名单（claude.ai / claude.com / preview / localhost / `*.ant.dev` / `app://localhost` / `file:`） | preload 无帧身份校验（`contextIsolation` 由 Electron 默认兜住） | 安全面 | **观察＋推断**：Claude 的帧模型更复杂（多 frame + webview），帧身份校验是它的必要条件；Cairn 当前是单 frame，**不抄**。但「桥面归属域」这件事可抄 |
| artifact 帧传输 | `cowork-artifact://shell` 自定义协议 + MessagePort；宿主把 `claude_activity`(working) 回传 | 无对等面 | 功能差异 | **观察**：Claude 的 artifact/frame 是**独立进程边界 + 独立协议**；Cairn 没有 artifact 概念（渲染的是消息内的 markdown / 代码 / 交付卡） |
| 协议版本 | 未观察到显式版本号（通道名内嵌随机 uuid） | `IPC_PROTOCOL_VERSION = 53`（`src/main/ipc-protocol.ts`） | **Cairn 更强** | **不抄**：Cairn 显式版本号优于上游的隐式 uuid 通道 |
| 本地执行授权 | 独立窗口 `local_exec_consent` + 独立桥命名空间 `claude.internal.localExecConsent` | 会话内 `ApprovalCard` + `use-permission-confirm.ts` | 形态差异 | **观察**：Cairn 的会话内授权卡与 §4.9「浮层式输入卡」形制一致；上游独立窗口是 Web 应用架构的产物。**不抄** |

## 三、设计系统与动效

| 面 | Claude（实测） | Cairn（现读） | 差异性质 | 判断 |
|---|---|---|---|---|
| 令牌来源 | `@ant/cds` vanilla 薄（**674** 名 / 957 声明 / 38,918 B @5.1231.2） | vendored 副本（**704** 名 / 1021 声明 / 41,505 B @**3.6556.2**） | **漂移** | **差距（可落动作）**：见 `02-CDS-上游漂移差分.md`。上游删了 30 个 git-diff 状态色、改了 `--opacity-icon-secondary`（0.4→0.3）；本仓 vendored 薄带的是**旧一代** |
| 漂移是否被现有判卷发现 | — | 否（`cds-parity.test.ts` 钉的是 vendored 自身与 `UPSTREAM.json` 一致） | **判卷缺口** | **差距（可落动作）**：需要一条「vendored vs 本机上游」的漂移判据，否则每次上游更新都是静默的 |
| 动效词汇 | 56 个 `@keyframes`；计时令牌化（`--cds-dur-fast/slow/snap`）+ `--cds-btn-spring`；状态钩子 `[data-mode]` 212 / `[data-reduce-motion]` 88 | 5 档时长（`--t-instant` 60ms … `--t-slowest` 450ms）+ 4 族缓动（`--ease-out/snap/overshoot/out-quint`）；§4.10.2 | 层级相近 | **不抄**：Cairn 的时长刻度已在本仓规范里成型；上游那套是 CDS 内部令牌，本仓不引 CDS 私有令牌 |
| 减弱动效 | `[data-reduce-motion]` 88 处（**属性**开关，不止媒体查询） | `prefers-reduced-motion` 媒体查询归零（§4.10.2 硬条款） | 机制差异 | **可落动作（轻）**：Cairn 已有媒体查询；上游用**根节点属性**承载，作用面可覆盖 JS 侧行为。本仓可考虑加同形属性开关——**属下一批候选，不是本轮** |
| 工作态指示 | `cds-working-dot-halo` / `-lands` / `-veil` 三件（halo→lands→veil 的编排） | 自有品牌色方块光标（业主第 19 遍裁过的元素） | 形态差异 | **不抄**：业主已定形态；本轮只登记「上游把 working 指示做成三段编排」这一事实 |
| 弹跳值变化 | `cds-pill-pop-up` + `cds-pill-pop-down` **两条分开**的关键帧 | 照抄 3.6556.2 的「一条动画内上冲 40% + 回落 60%」（ADR 0009） | **形状已变** | **差距（可落动作，轻）**：本仓照抄的是上游**旧一代**形状；重抽 CDS 时应顺带核对这条 |

## 四、内容与插件

## 五、宿主 ↔ agent 边界（唯一一条我认为真正值得看的架构差异）

- **Claude**：渲染层（claude.ai Web 应用）通过 35 个状态切片 + 结构化通道与 Electron 壳对话；
  agent 运行时是**另一个进程**（随包 CLI），宿主负责拉起与授权（`permissions` 被 frame 契约标为 `core` 能力）。
  ⇒ 「能力」与「进程」是两层：`capabilities` 管**能做什么**，`core: ["permissions"]` 管**哪一层说了算**。
- **Cairn**：`src/agent/` 是**同进程**（electron-free 的纯内核），渲染层经 `src/main/ipc-protocol.ts` 与之对话。
  ⇒ 能力面是单一的 `CapabilityReadout`。

**推断（非观察）**：Claude 把「能力清单」与「能力归属层」分开写进一份**可版本化的契约文件**，
本仓只有前者。**这不是「本仓缺个文件」，而是「本仓没有一处能回答『这个能力属于核心还是扩展』的地方」**。
是否值得补，取决于业主对扩展面的规划——**本轮不动**。

## 七、明确不抄（并附理由）

- **不抄**上游的 artifact/frame 进程边界与 `cowork-artifact://` 协议：Cairn 无 artifact 概念，且该机制是 Web 应用架构的产物。
- **不抄**上游 129 版 frame 契约的规模：那是跨年演进的历史，本仓没有这份历史，补进来是负担不是资产。
- **不抄**上游的动态通道 uuid 拼装：Cairn 的显式 `IPC_PROTOCOL_VERSION` 更强。
- **不抄**上游 21 个桥全局名的**数量**：照抄数量不产生能力；只有「域可枚举」这一点有判卷价值。
- **不抄**上游内置 6 个技能替代本仓插件体系：本仓在插件生命周期上更深（见第四节）。
