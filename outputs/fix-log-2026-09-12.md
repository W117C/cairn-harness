### 关键设计决策（P0-1）：`shell_ro` 不进威胁表

`shell_ro` 属于 shell 家族（规则匹配互通），但**不**进静态威胁表。原因：它自带 fail-closed 的只读静态白名单硬闸，对危险命令强于威胁表；若让它的命令先过 `staticRisk`，`curl … | sh` 会被判 `critical` → 走 L4「送审」而不是**静态拒绝**，等于把 **deny 降级成 ask**（`tests/agents.test.ts` 断言「只读 bash 静态过滤拒绝」）。

## 2. 根因 4 详解（本次最易踩的坑）

**为什么不用 `AbortSignal.timeout()`**：它是**总时长**上限。LLM 流式生成合法地可持续数分钟（长回答 / 大工具参数 / 慢思考），总时长超时会把**正常请求杀掉**。真正要防的是**停滞**——建连后长时间零分片（对端挂起 / 中间设备黑洞）。

故 `stallGuard(windowMs)` 用**每次收到分片就续期**的看门狗：静默超过窗口才 abort。
`withTimeout()` 只用于一次性请求（MCP connect / listTools）——那里总时长语义本就正确。

其他要点：

- **abort reason 传 `new Error(...)`**：fetch 与 body reader 直接用它作拒绝值，上层**无需翻译**即可拿到「停滞超时：…ms 内无任何数据」；否则会退化成通用的 `The operation was aborted`。
- **看门狗定时器 `unref()`**：否则单测里会挂住 worker 不让进程退出。
- **`finally` 里 `void reader.cancel().catch(() => {})`**：消费者提前 break / 出错退出时主动关 body，否则连接与对端资源一直挂着。
- **MCP 超时后底层连接仍挂着**：catch 里先 `client?.close()` / `transport?.close()`，**再**记失败态（fail-visible，不留僵尸连接）。
- **测试桩安全性**：`providers-check` 与 `tests/*` 的 fetch 桩全是 `async () => new Response(...)`，**完全忽略 init 参数** → 新增 `signal` 字段不会误伤（已逐个核对）。
