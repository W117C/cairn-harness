## 一、方法（以及我自己的表尺两次骗我）

对账 = 「提示词里点名的工具」÷「那一档真拿得到的工具集」。两次假信号都出在**尺**上，不在产品上：

1. **取料面空读数**：第一版按 `import { BASE_SYSTEM } from "…/permissions/autonomy"` 取，
   结果 `长度 0B` 而报告写成"提到 0 个工具"——那是**没尺**，不是干净。真身在 `src/main/agent-runner.ts:138`
   （autonomy 里只是注释提到过它）。⇒ 任何"0 命中"必须先回答"我这条读取真的够到被测物了吗"。
2. **词面命中 ≠ 承诺方向**：worker 两支提示词都提到 `spawn_agent`，我第一版按"提到了该面没有的工具"报了红。
   逐字读才发现两处是否定式：「不能再 spawn_agent（工具表已摘除）」/「不要运行 spawn_agent（深度恒 1）」。
   ⇒ 存在性匹配只能当**候选生成器**，判定必须回到那句话本身；否则我把"正确地告知边界"报成缺陷。
3. **构造的面 ≠ 产品那次构造**：第一版用 `orchestrator-config.WORKER_TOOL_TABLE`（read 面常量）当 worker 面，
   而生产面是 `buildWorkerToolTable()`（含 `impactAnalysis` 那一支与 write 档的 `delete shell_ro`）。
   ⇒ 判"某档有没有这把工具"要吃**建表函数**的产物，不吃手抄常量（规则 123 的另一面）。

## 二、结论

**worker 两支：逐字对齐，无缺陷。**

| 提示词 | 点名的可用工具 | 真面（建表函数产物） | 判定 |
| --- | --- | --- | --- |
| `WORKER_SYSTEM`（只读档） | `read_file / grep / glob / lsp / shell_ro` | 同集 | ✅ 逐字一致 |
| `WORKER_WRITE_SYSTEM`（写档） | `read_file / grep / glob / lsp / write_file / edit_file / shell_rw / remember` | `WRITE_WORKER_TOOL_TABLE` 同集（builder 行 40/89–92：`delete shell_ro` + 这四把） | ✅ 逐字一致 |

且它多做对了一件事：**明确写出"你不能做什么"**（不能 spawn、不能合并/提交、哪些 git 子命令被静态拦），
这正是第 51 页那条探针暴露的反面——不是给模型一条走不通的路，而是提前说清墙在哪。

唯一的小缺口（不属缺陷，记一笔）：`impactAnalysis` 开着时 worker 也会拿到 `impact_query`（builder :37），
两支 worker 提示词的"可用工具"行都不提它 ⇒ 模型只能从工具 schema 里认识它。工具面本来就每轮重送，
不提不算说谎；只是当"什么时候该用它而不是 grep"这类指导值得占字节时，那一行才是归宿。

**`BASE_SYSTEM`：一句话对四档 ⇒ 两处偏差（已立案 #35，未偷做）。**
`agent-runner.ts:1397` 把同一份文本发给所有权限档，而 `checkPermission(mode, "write_file")` 实测是
`read-only→deny / default→ask / guided→allow / auto→allow`；纪律 2 却写「先 propose_plan 并等批准
（未批准的写操作**会被权限层拒绝**）」：

- `default` 档：机制是**弹卡问人**，不是"拒绝" ⇒ 模型对后果的预期错（它会以为写直接失败）；
- `guided`/`auto` 档：写**根本不需要**方案，这句话仍命令它先提交 ⇒ 白多一跳。
- ⚠️ 严重度按代码校准：auto 下 `propose_plan` 走 `approvePlan()` 自批（:67→:77），**不会卡住等人**
  ⇒ 是"多一跳"不是"自主跑不动"。我第一版判断偏重了，写下来免得下次照抄那个版本。

修法与验收写在 #35（含"针脚 `base-system-discipline` 要同时改指"与"没传模式时逐字不变"的零回归那条）。
动不了的原因还是同一句：`src/main/agent-runner.ts` 与 `scripts/mutate-verify.mjs` 现在都在并发会话手里（均 `M`）。
