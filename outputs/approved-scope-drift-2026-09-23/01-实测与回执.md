plan = { paths: new Set(proposal.files.map(f => f.path)), covered: new Set(), approvedAt: i }   // 批准集 / 已做集

if (e.ok && pair.at > plan.approvedAt) plan.covered.add(path);   // ← 任何路径都收，不问批没批准

## 二、真函数的四种输入（只数 `verified` 边界）

| 输入 | verified 前进边界 |
|---|---|
| 批准 1 个、只写批准的那 1 个（**合规**） | **1** |
| 批准 1 个、实际写 3 个（**越界 2 个**） | **1**（与合规**一模一样**） |
| 批准 1 个、**一个都没照做**（只写批准外的 z） | **0** |
| 批准 1 个、什么都没写（对照） | **0** |

⇒ 结论比我第一版的猜测更窄、也更值得修：

1. 机器**只抓得住「批准的那项完全没做」**；
2. **「照做 + 顺手多改 N 个文件」与纯合规给出的读数完全相同** ⇒ 越界结构上不可见；
3. 而越界的写动作**照样进 `completed`/边界的分子** ⇒ 能力 15 的「成本 ÷ 前进」里，
   "前进"被越界动作抬高 = **越改得多越显得便宜**（假便宜方向与直觉相反）；
4. **判据的严格方向正好反了**：完全不照批准做会被拒（0 条），部分照做+越界反而满分（1 条）。

（第 3 条我原先写成"越界零代价"，那是**没验就下笔**：见 §五 的自误记录。）

## 五、本页我自己的一次假读数（必须留字）

探针第一版给 `propose_plan` 发了 `tool_call` 却**漏发它的 `tool_result`**
⇒ `pending` 永不清空 ⇒ 四种输入都只产出 `kind:"user"` 边界，而我把它当成"1 条前进边界"，
于是下了一句"越界零代价、四种输入读数完全相同"的**假结论**——连"完全不照批准做"那格也是 1。

补上 `tool_result` 后才是 §二 那张表：**其中一格确实是 0**，判据并非全盲，而是**单向**。
⇒ 教训照本仓老规矩办：**读数为 0 或四格全同，先怀疑流形没喂对，再怀疑机器有毛病**；
且任何"某函数怎么反应"的断言，必须**同时给出正例与反例**（这里反例就是那格 0）。
