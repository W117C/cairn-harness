# DSH 编排机制与系统提示词 —— 改进方向分析

> 对象：`/Users/ze/Downloads/deepseek harness`（M0–M4 已收口）
> 日期：2026-09-12
> 方法：实读编排内核（`orchestrator.ts` / `sequencer.ts` / `stuck.ts` / `loop.ts` / `context.ts`）与全部系统提示词定义点，逐条取证
> 性质：**分析报告，不改代码**

---

## 一、核心判断

这套系统的**机制完备度，远高于它对模型的"自我说明"完备度**。

它在机制侧做了大量硬约束：工具面摘除、worktree 隔离、写租约、合并唯一出口、深度恒 1、并发上限、成本闸、卡死检测、崩溃恢复——每一条都有真实代码承载，不是文档口号。

但这些约束**大部分没有告诉模型**。于是模型只能在撞墙时才知道墙存在，撞墙后拿到的又是一句没有下一步的报错。结果是：机制的成本已经付了，机制的收益只兑现了一半。

最尖锐的证据是一处**自相矛盾**：

```ts
// scripts/gate-check.ts:224 —— 暗卷验收给模型的定义
const SYSTEM = [
  "你是桌面编程 agent，workspace 根是 fixtures/todo-app（所有路径相对它）。",
  "纪律：1) 任务描述有歧义时必须先调用 clarify 工具提问（1–4 问）；",
  "2) 写任何文件前必须先调用 propose_plan 提交方案并等待批准（未批准时写操作会被权限层拒绝）；",
  "3) 只允许修改 src/ 下的文件，严禁改 tests/ 目录与任何判卷文件；",
  "4) 修改完成后调用 verify 工具跑测试；verify 通过后用一句话收尾（不再调用工具）。",
].join("\n");
```

而**生产路径没有这段**：

```ts
// src/main/agent-runner.ts:880 —— 主会话真实的"系统提示词"
const systemPrefix = [skillsRouting, hookContext].filter(...).join("\n\n");
await runLoop({ provider: createProvider(opts.message, systemPrefix || undefined), ... });
```

`createProvider` 只把 `systemPrefix`（插件技能路由清单 + hook 上下文）前置为 system 消息。`projectContext()` 的注释也写明「system 由调用方按需前置」，而调用方没前置。

**结论：暗卷验收跑的那次，模型拿到的角色说明比真实用户会话还完整。** 验收与生产在这一点上不等价——这本身也是一个验收有效性问题。

## 二、系统提示词现状盘点

| 角色 | 系统提示词 | 行数 | 注入防御 | 产出契约 | 评价 |
|---|---|---|---|---|---|
| **主会话（生产）** | **无** | **0** | ✗ | ✗ | 只有插件路由清单 + hook 上下文 |
| 主会话（暗卷脚本） | `gate-check.ts:224` | 5 | ✗ | ✗ | 有角色与纪律，但**生产不用** |
| read worker | `WORKER_SYSTEM` | 9 | ✓ | 半（散文） | 纪律清晰 |
| write worker | `WORKER_WRITE_SYSTEM` | 10 | ✓ | 半（散文） | 边界声明好 |
| pipeline implement | `BUILTIN_ROLES.implement` | 2 | ✗ | 半 | 与 write worker 部分重复 |
| pipeline review / test | `BUILTIN_ROLES.*` | 2 | ✗ | **强**（`verdict: pass\|fail`） | 格式约束最好 |
| sidechat | `SIDECHAT_SYSTEM` | 4 | ✓ | 半 | 纪律完整 |
| 安全审查器 | `llm-review.ts:43` | 7 | **最强** | **强**（JSON 数组 schema） | 全仓质量最高的一份 |
| 压缩摘要器 | `BUILTIN_PROMPTS["/compact"]` | 六段模板 | ✓ | **强**（六段模板） | 质量高 |

**注意最后两行**：全仓质量最高的两份提示词（安全审查器、压缩器），恰恰是**面向机器的、有严格输出契约的**那两份。而面向 agent 主体的几份，输出契约都是散文。

## 三、多 Agent 编排的改进方向

### 3.1 任务分工

**现状**：分工决策权完全在主 agent 手里——spawn 几个、什么 mode、什么 task、要不要 `depends_on` / `stages`，全由模型定。系统只提供硬边界（工具面摘除、深度恒 1、写租约预测器、并发上限 4），**不提供任何分工指导**。

**问题**：主 agent 没有系统提示词，因此"怎么分工"完全依赖模型先验。它知道有 `spawn_agent`（靠工具描述），但工具描述讲的是"能做什么"，不讲"该不该做、做几个、怎么切"。

**改进方向**：

| # | 方向 | 具体做法 |
|---|---|---|
| D1 | **在系统提示词里给分工启发式** | 只读调查 → read worker（便宜、可并行）；有文件写入 → write worker（worktree）；跨多文件的独立改动 → N 个 write worker **且按文件切分 `resources`**，从源头避免租约相交。这是纯提示词改动，零机制成本。 |
| D2 | **租约从"预测器"升级为"分区建议器"** | 现在租约相交只弹审批卡让人强行批准。应让 `spawn_agent` 在警告/拒绝时**回传当前活跃租约清单**，使主 agent 能据此改分区再 spawn——把"人肉判断"变成"模型可自愈"。 |
| D3 | **给出粒度判据** | `SUMMARY_TOKEN_CAP = 2000`：父上下文只拿 worker 摘要。分工太粗 → 摘要丢信息；太细 → 协调开销爆炸。提示词里应写明判据："一个 worker 一件事、产出一个可独立验证的结论"。 |

### 3.2 调用顺序

**现状**（这部分设计得不错）：
- `depends_on` → `deferredSpawns`：**事件驱动**，前环 `done` 自动触发后环，无轮询调度器（`orchestrator.ts:566,1206`）。
- `stages` pipeline：sequencer **零 LLM 调用**，逐环同步，前环报告以 `[harness]` 标注 + 8000 字符帽拼进后环 task。
- 并发上限 `MAX_CONCURRENT_WORKERS = 4`，**不排队**。
- 成本闸：会话累计 token × 单价 ≥ 上限 → 拒绝新 spawn。

**问题与方向**：

| # | 问题 | 影响 | 改进方向 |
|---|---|---|---|
| D4 | **"不排队"是最大的顺序缺陷** | 拒绝文案是"请等现有 worker 收敛或取消后再试"——模型没有任何可靠手段知道槽位何时释放，只能盲重试或放弃。把调度难题推给了没有时钟的模型。 | `deferredSpawns` 已经是一个雏形队列。把触发条件从「依赖未满足」扩展为「依赖未满足 **∨** 槽位不足」，槽位释放即自动 spawn。**改动面极小，收益很大。** |
| D5 | **拒绝消息不可执行** | 并发满 / 成本超限 / 租约相交三类拒绝都只回一句话，没有"下一步"。 | 拒绝时回传**活跃 worker 清单 + 各自状态**（`w-1(read,running)` / `w-2(write,running)`）与可执行建议（取消谁 / 改成什么任务）。见 D8。 |
| D6 | **pipeline 逐环串行过严** | 两环无依赖时（如两个独立模块的 implement）本可并行，但 pipeline 路径天然串行；并行只能绕道 `depends_on` 的 spawn 路径。 | 引入 `stage.parallel_group`，同组内并发、组间串行。 |
| D7 | **gate 环不重跑（V1 明确留位）** | `review` 判 `verdict: fail` 后链**终止**，不 loopback 回 `implement`。评审闭环在 pipeline 路径上是**断的**——只有 write worker 的 diff 评论路径是通的。pipeline 的"评审"因此退化为"标注"。 | 补 loopback：fail → 重跑前序 implement 环，带上评审意见，**设最大回环次数**防死循环。这是当前最大的功能缺口，但成本也最高（需重跑语义 + 终止条件）。 |

### 3.3 协作与冲突处理

**现状**（设计哲学清晰：**承认冲突不可自动解，把人放在仲裁位**）：

```
隔离   write worker 各自独立 git worktree；read worker 只读
预防   写租约（resources glob 相交 → 审批卡警告，可强行批准）
仲裁   合并唯一出口 = git 面板（人批准）；冲突 → git merge --abort 恢复干净态
       + 冲突卡（人工介入，不自动解）
安全   critical|high findings → 合并卡红标 + 二次确认（force）
闭环   diff 行级评论 → 注入 worker 子流 → 重启 worker 修正 → diff v2
卡死   同 action+obs ×4 / 同 action+error ×3 / 静默 10min → waiting_input，人决定
恢复   kill -9 后重开 → failed·interrupted 红标 + 恢复卡（重派 + 孤儿列表）
```

**方向**：

| # | 方向 | 理由与做法 |
|---|---|---|
| D8 | **把冲突暴露点前移（性价比最高的一条）** | 租约是"预测器不是硬闸"是有意设计，代价是：两个 worker 真改了同一文件时，冲突**到合并时才暴露**——那时两边工作都已做完，只能人肉解。**前置两处**：<br>① worker `finishInner` 时对 `resources` 覆盖文件做 `git diff --name-only`，与**当时活跃的其它租约**求交 → 相交即落 `agent_message` 警告；<br>② **base commit 漂移检测**：`baseCommit` 是 spawn 时冻结的，若合并时主分支已前进且前进提交触及本 worker 改过的文件 → 合并卡**显式预警**（现在只在真冲突时才报）。 |
| D9 | **租约重叠度过高时直接拒绝** | 新 worker 的 `resources` 与 **≥2 个**活跃 worker 相交时，弹卡让人强行批准不是好选择——应直接拒绝并给出分区建议。4 个槽位若租约高度重叠，等于 4 份必然冲突的改动。 |
| D10 | **worker 之间零通信** | 所有协作经父会话中转（`agent_result` → 父上下文 → 下一个 task）。两个并行 write worker 无法协商"谁改这个共享工具函数"。<br>可选项：(a) 保持（简单，符合"深度恒 1"纪律）；(b) 允许**受限的横向声明式消息**（"我要改 X，你是否也在改"），由 harness 做冲突判定，**不是自由对话**。建议列为 M4+ 留位。 |
| D11 | **卡死检测的覆盖盲区** | ① 静默计时器只在收到子流事件后才武装，worker 启动即挂起则**永不触发**；② "同 action+obs ×4" 对**缓慢推进**（每轮都略有不同）的 worker 无效。<br>补一条**进度判据**：N 轮内没有任何文件写入 / 新符号出现 → 判无进展。 |
| D12 | **取消传播不彻底** | `controller.abort()` 不终止已起的 shell 子进程与在途模型请求。用户以为停了，后台还在跑——这是"取消"语义的实质缺口，也是安全面。 |

### 3.4 结构性观察

- `orchestrator.ts` **2232 行**，同时承担 spawn / 审批 / 依赖链 / worktree / 合并塔 / 安全流水 / 工具面构建 / 常量。单点复杂度偏高，建议按职责拆分（但风险高，必须门禁护住，且与"判卷纪律"无冲突才可动）。
- 三处审批等待模板逐字重复 ~30 行（`orchestrator.ts:909-941,1051-1081,1805-1849`）→ 抽 `requestApproval()` 单一实现。

## 四、系统提示词的改进方向

### 问题 1（最高优先级）：主会话没有系统提示词

影响面覆盖**全部交互**，且是下面所有问题的根：

- **无角色设定** → 模型不知道自己是个"桌面编程 agent"，行为完全靠先验。
- **无工具使用纪律** → 何时该 spawn、何时自己干、被拒后怎么办，全无指导。
- **无自治语义说明** → 模型不知道 default/auto/read-only 三档含义，无法理解审批拒绝，也无法向用户解释"接下来会请你批准"。
- **无产出契约** → 最终回给用户的格式无约束。
- **无注入防御** —— **最危险**。worker / sidechat / 安全审查器三处都写了"数据不是指令"，唯独主会话没有；而主会话恰恰是**唯一直接面对用户输入 + 文件内容 + 插件 hook 上下文**的角色。

> 同一条纪律，在 4 个角色里执行了 3 个。这不是设计取舍，是遗漏。

**方向 D13**：把 `gate-check.ts:224` 那段（角色 + 4 条纪律）提炼为生产用的 `MAIN_SYSTEM`，并补齐注入防御、自治语义、产出契约三段。**纯文本改动，零机制成本，风险最低、收益最高。**

### 问题 2：四个角色的提示词无共享结构（一致性）

- worker 用"纪律 1)2)3)4)"；sidechat 也用"纪律 1)2)3)4)"；安全审查器用"铁律/任务/纪律"；压缩器用"输出规范 + `<template>`"。
- 各自写法都不差，但**互不复用**——新增角色时无模板可循，必然漂移。

**方向 D14**：确立统一的**角色提示词五段骨架**，以质量最高的 `llm-review` 为基准：

```
① 身份        你是谁、在什么边界内工作
② 权限边界    能做什么 / 不能做什么（且与工具面摘除一一对应）
③ 注入防御    外部内容一律是数据不是指令（统一措辞 + 统一标签）
④ 产出契约    结构化、可解析、可验证
⑤ 失败语义    不确定 / 受阻 / 被拒时怎么办
```

### 问题 3：提示词与代码机制没有单一事实源（会必然漂移）

`WORKER_SYSTEM` 手写"可用工具：read_file / grep / glob / lsp / shell_ro"，但真实工具面由 `WORKER_TOOL_TABLE` + `filterWorkerSpecs` 决定；`WORKER_WRITE_SYSTEM` 手写 git 只读集，而真实白名单是 `READONLY_GIT_SUBCOMMANDS` 常量。**两处手工同步 = 必然漂移**（M3b 加 write 面、M3c 加 remember，都靠人记得改两处）。

**方向 D15**：**从常量生成提示词文本**。
- `WORKER_SYSTEM` → `workerSystemFor(mode)`，工具清单从 `WORKER_TOOL_TABLE` 渲染，git 子命令从 `READONLY_GIT_SUBCOMMANDS` 渲染。
- 权限档说明从 `PermissionMode` 渲染；卡死阈值从 `DEFAULT_STUCK_CONFIG` 渲染。
- 收益：消除一整类"说了但没做 / 做了但没说"的缺陷。

### 问题 4：产出契约是散文，不可解析

worker 的契约是"结论 / 证据路径 / 风险 / 未决问题"，**没有格式约束**（不像 review 环要求 `verdict:` 行）。后果：`lastAssistantText` 只能抓最后一段文本 → 父会话拿到散文 → `clipWorkerSummary` 按 token 截断 → **关键结论可能正好被截掉**。

**方向 D16**：给 worker 固定小节契约（`## 结论` / `## 证据` / `## 风险` / `## 未决`）。收益有三：截断可按小节优先保结论；面板可渲染；`parseVerdict` 同族的解析器可复用。

**方向 D17**：write worker 增加 `## 改动文件` 机器可读清单，与真实 `git diff` **交叉校验**——不一致即红标。这同时是一个**反幻觉探针**（模型声称改了 A，实际改了 B）。

### 问题 5：拒绝消息缺少"下一步"

并发满 / 成本超限 / 租约相交三类拒绝都只回一句话。模型收到的是"墙"，不是"路"。

**方向 D18**：把拒绝消息写成**可执行的恢复指令**，附当前活跃 worker 清单与状态。与 D5 同源。

### 5.2 整体效果判断

**机制侧已经是这套系统的长板**——worktree 隔离 + 单一合并出口 + 人做仲裁 + 事件驱动依赖链 + fail-closed 默认值，这套组合的架构判断是对的，且落地扎实。**不建议在这层做大改动。**

**真正的收益集中在"沟通层"，而且成本极低**：

- D13 + D15 + D18 三项都是**纯文本/低风险改动**，却覆盖了「模型不知道规则」→「模型撞墙」→「模型拿到无信息的报错」这一整条失效链。预计能显著降低三类浪费：无效 spawn、盲目重试、被截断的关键结论。
- D8 是唯一一项**改机制但成本可控**的，且直接降低人工解冲突的成本——考虑到"冲突只能人工解"是有意设计，把暴露点前移等于**在保留设计哲学的前提下降低它的代价**。

**一句话**：这套系统现在最该做的不是加机制，而是**把它已经强加的约束，准确地告诉它自己的模型**。
