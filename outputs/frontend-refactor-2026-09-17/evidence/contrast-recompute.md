# 证据 · 令牌对比度独立复算（主理人自算，2026-09-17）

> 目的：核对 `src/renderer/index.html:15-94` 令牌块注释里的对比度宣称值是否可信。
> 方法：**不引用任何既有结论**，用 Python 独立实现 `oklch → oklab → 线性 sRGB → WCAG 相对亮度 → 对比度`，
> 数据取自源码字面量。复算脚本见本目录 `contrast-recompute.py`（可直接重跑）。

## 1. 复算方法（可复现）

```
oklch(L,C,H) → oklab:  a = C·cos(H), b = C·sin(H)
oklab → LMS':  l_ = L + 0.3963377774a + 0.2158037573b
               m_ = L − 0.1055613458a − 0.0638541728b
               s_ = L − 0.0894841775a − 1.2914855480b
l = l_³, m = m_³, s = s_³
线性 sRGB:     r =  4.0767416621l − 3.3077115913m + 0.2309699292s
               g = −1.2684380046l + 2.6097574011m − 0.3413193965s
               b = −0.0041960863l − 0.7034186147m + 1.7076147010s
WCAG 相对亮度: Y = 0.2126R + 0.7152G + 0.0722B   （R/G/B 为线性值，钳位 [0,1]）
对比度:        (Y_hi + 0.05) / (Y_lo + 0.05)
```

## 6. 收尾定案：`--border-strong` dark 的「三处不一致」其实是「基准面未标注」

Phase 4 审查官报出 `--border-strong` dark 有三处互不吻合的值（文档 3.83 / 审查 4.13 vs bg / 审查 3.50 vs surface-2）。主理人收尾复算，先把 oklch 转成**真实 sRGB hex** 再比对：

| 深色面 | oklch | 真实 hex |
|---|---|---|
| `--bg` | `oklch(16.8% 0.012 250)` | `#0b0f14` |
| `--surface` | `oklch(20.8% 0.014 250)` | `#13181e` |
| `--surface-2` | `oklch(24.4% 0.015 250)` | `#1b2127` |
| `--border-strong` | `oklch(56% 0.012 250)` | `#6f757b` |

| `--border-strong` dark 对… | 对比度 | 对应谁 |
|---|---|---|
| `--bg` | **4.12:1** | 审查官的 4.13 |
| `--surface` | **3.83:1** | 文档的 3.83 |
| `--surface-2` | **3.48:1** | 审查官的 3.50 |

**结论：三个数全部正确，没有一处算错。** 差异 100% 来自**基准面不同**，而原表列标只写「vs bg」，未区分 `--bg` / `--surface` / `--surface-2`。

**最低值 3.48:1 仍 ≥ 3:1** → `--border-strong` 满足 WCAG 1.4.11 非文字对比要求，**无需改色**。

同一根因也解释了审查官对 `--border` 的判断：文档列标写「vs bg」而实算基准是 `--surface`（1.34:1），对 `--bg` 实为 1.44:1 —— **审查官那条「基准错标」是对的**。

### 方法学结论（第三条，建议写成硬约束）

> **对比度数值必须连"基准面"一起标注**（例：`3.83:1 @ --surface`）。
>
> 本轮**三份互不复用的独立复算全部算对**，却因为基准面未标注，看起来互相矛盾，白白产生一轮「残留待核」。这不是算术问题，是**标注问题**——而未标注基准的数字**不可用于决策**。
>
> 与 §4 的结论互补：§4 说「数值必须可复算」，本条说「**可复算还不够，基准也必须显式**」。两条合起来才是完整纪律。
