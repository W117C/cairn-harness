0. 一句话结论

你的前端不是"烂代码"，是"好手艺 + 零工程护栏"。

对话底子扎实——oklch 双主题令牌体系完整、无障碍资产齐全（298 个 aria-*、30 个 role、13 处动效降级、Enter/Space 键盘可达性实测正确）、色板对比度全部达标。真正的问题是三件事：

  1. 结构：4147 行发货代码挤在两个文件里（index.html 1866 + app.js 2281），且是「跑 mock 的原型」与「追加式真实桥接」的拼接体，两半靠共享模块级变量隐式耦合。
  2. 护栏：发货的 4147 行零静态检查——tsconfig 的 allowJs 未开启（app.js 不被 typecheck 覆盖），且全仓无 eslint/prettier/stylelint、无 CI。唯一有类型保障的，是已经死掉的 React 树。
  3. 口径：panels-check 的 7 个 CDP 探针指向 dead React DOM，在发货层命中全 0 → 门禁不可能全绿，性能口径无人守。

→ 所以优化重点应放在护栏 + 结构 + 口径，不是重写视觉。

3. 重构与设计方案

3.1 目标架构：7 层单向依赖

详见 03-refactor-design.md §1。核心是把"拼接体"变成"分层体"：

工具层(utils) → 状态层(单一 store) → 投影层(复用 projections.ts)
                                        ↓
                     组件层(卡片/面板注册表) → 视图层(render/*.js)
                                        ↓
                            桥接层(bridge/ipc.js) → 启动层(main.js)

三条硬规则：

  1. 桥接层是唯一能碰 window.agent 的地方（现状：app.js:1660-2281 的 IIFE 覆写原型函数，与原型层共享 sessions/selectedId/archived）。

§B 状态编码规格（VIS-01 / 03 / 04 / 05）

B.1 七态三重编码（色 + 形 + 字）

完整状态集 = 成功 + 运行四态 + 被拒 + 已中断（共 7 项）。硬约束：全部转灰后，仅凭图形 + 文字仍能区分 7 态。

两处刻意的「同色不同形」（优先不新增色相）：

  • 被拒 vs 失败：同用 --st-fail，但形可辨（⊘ vs ×）+ 文字不同。
  • 已中断 vs 等待：同用 --st-wait，但形可辨（空心环+‖ vs 纯空心环）+ 文字不同。

1.3 隐式耦合的根治（MAINT-02 的核心）

现状实测：app.js 前半（1-1659）声明并持有模块级可变状态：

两半隐式耦合：任一侧改动可静默破坏另一侧；且 send/selectSession 在原型层是 function 声明（app.js:1047 / 235），桥接层用 = 覆写 → 同名字段语义漂移，无静态校验（allowJs 未开，见简报 F-2）。

  1. 单一 store 拥有全部状态。sessions/selectedId/archived/real/ui 收敛进 store.state；app.js:28-52 的 let 全部删除。
  2. 视图层不再持有可写状态。render()（app.js:165）、sessionItemHTML（122）、renderArchive（483）改为 renderX(state) 纯函数。
  3. 桥接层不覆写函数，改为：
   // bridge/ipc.js（目标）
   export function createBridge(api, store) {
     const off = api.onEvent(e => store.dispatch({ type: 'event', e }));

每个方法内部只做 api.*(...) → store.dispatch(...)。

  1. mock 降级为 seed 源（不是平行实现）：
  • mock/seed.js 导出 seedStore(store)：把 FOLDERS/sessions/archived（app.js:30-48）作为初始数据 dispatch 进 store。
  • 原型的打字机 send（app.js:1047-1136）改造为 mock/mockRun.js 的 dev 适配器：它产出的事件经 同一 store.dispatch({type:'event'}) 入口进入状态层——与真实桥接走同一条数据流，视图层无法区分二者。
  • main.js 装配：window.agent?.listSessions ? createBridge(...) : seedStore(store)。
  1. 验证对齐 MAINT-02 验收口径：
  • grep -n 'window\.agent' src/renderer/**/*.js 仅命中 bridge/ipc.js；
  • grep -cE '= (async )?function' src/renderer/**/*.js（覆写式赋值）= 0；
  • grep -nE 'let (sessions|selectedId|archived)' src/renderer/*.js 命中数 = 1（仅 store.js）。

为什么不选「保留两半、只加类型」：覆写式契约无法用类型表达（send 从 () => void 变成 async () => void 且语义完全不同）。根治只能靠收敛状态 + 单向数据流，这也是 MAINT-01/02 的目标态原文（需求 §2.1）。

2.3 4147 行拆解顺序与风险（先抽什么、后抽什么）

抽取顺序 = 按「状态耦合度」从低到高：

  1. 先抽工具层（M1）——零状态纯函数，零风险，先建立 import 机制与模块纪律。
  2. 再抽视图层（M3）——纯渲染，但要小心 renderEvent（1854）内的隐式状态读（real.cards、real.toolGroup）；此步必须先把这些隐式状态显式化为参数。
  3. 再抽状态层（M2，最高风险）——两半的共享根。一次移动 sessions/selectedId/archived/real，任一处遗漏即静默断链（如 loadSessions（1680）写 sessions、selectSession（2213）写 selectedId）。缓解：特征测试 + 双跑 diff + 只读访问器过渡（写点先集中到 store action）。
  4. 再抽桥接层（M5，次高）——把 4 个覆写函数改成 adapter 方法；语义等价最难（权限映射 1669 / running 守卫 2184/2210 / ask 卡 2130 / 两级折叠 1630-1656）。
  5. 最后 mock 降级（M6）——依赖前三步已建立「事件 → dispatch → 渲染」单一数据流。

风险最高步 = M2（理由：状态是两半唯一交汇面；无类型保障（F-2）；app.js 2281 行里对这几个变量的读写点分散）。

降低「不停机」风险的三条具体手法：

  • 同名 shim 转发：M1-M5 每步都在 app.js 内保留旧名符号（转发到新模块），删 shim 是最后一步，因此任意时刻旧调用点仍有效。
  • 双跑 diff：M2/M5 用 ?arch=next 挂载新路径，用 §M0 的 golden 快照对新旧 DOM 逐字 diff。
  • 开关即回滚：开关默认旧路径；新路径出错时删开关即回到旧实现，无需回滚提交。

F-1 🔴 持久化布局 schema 完全绑死在已死的 React 层

这 8 个键正是 React 树 panels/registry.tsx 的面板 id（approvals/token/git/memory/plugins/sidechat/agents/schedule）。
