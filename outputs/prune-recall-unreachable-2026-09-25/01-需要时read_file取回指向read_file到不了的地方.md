# 第 51 页 · 「需要时 read_file 取回」指向一个 read_file 到不了的地方

日期 2026-09-25。基线 HEAD `25179c6`。
这是第 49/50 页那一类（模型可见文案点名的动作做不通）的**第三次命中**，也是三条里最贵的一条：
前两条一个躲在默认关的开关后面（`impact_query`），一个只在零命中时出现（`glob` 的说明）；
**这一条长在长任务的主路径上，而且 prune 是默认开着的。**

## 一、结论

`computePrune` 把旧的大 `tool_result` 换成占位串，并附一行
`[原文已存附件 <绝对路径>，需要时 read_file 取回]`。
而那个附件目录算自 `join(dirname(logPath), "prune-attachments")` —— 会话日志在应用数据目录里，
**在工作区之外**。`read_file` 走 `resolveInWorkspace`，**第一句就拒绝对路径**。
⇒ §7.4「被裁原文写会话附件目录可回取」这条能力，在模型那一侧**一次也执行不了**。
剪枝因此对 agent 是**不可逆的信息销毁**——而这条接线（09-20 那次）当初的目的恰恰就是"别不可逆"。

## 二、实测（探针逐字读数，`scripts/probe-prune-recall.ts`，exit 1）

工作区与会话目录分家（照生产表达式算附件目录），事件面逐字照抄 `prune-check` 的稳定触发形状：

```
✅ prune 真触发了（否则整支没有尺） — why=saved
✅ c-old 的打桩把路径交给了模型（承诺可见） — "[Old tool result content cleared]\n[原文已存附件 /var/…/prune-attachments/…"
✅ 该路径就是实际写出的那个文件（同源） — /var/…/probe-415d0647-c-old.txt
✅ 文件真存在、内容逐字一致（prune-check ④ 已覆盖的那半）
❌ 模型照那句做得到（read_file 真能取回原文） — 工具抛错：read_file: 只允许 workspace 相对路径，收到绝对路径: /var/…/c-old.txt
```

四个 ✅ 说明**上游全对**：写盘对、路径对、同源对、内容与原文逐字一致。
只有第五格——**把承诺的动作真的做一遍**——是红的，而那一格恰好没有任何判卷覆盖。

## 三、为什么满树的门没抓到（这是判据的形状问题，不是漏写一条断言）

`scripts/prune-check.ts` 在这条上已有三条断言（③d 路径可见 / ④ 读回逐字一致 / ④b 路径同源），
2026-09-20 那笔还专门把"打桩文本逐字等于占位串"换成了更强的两条——方向完全对。
但 ④ 的回取用的是 **node:fs 的 `readFile`**，不是 **`read_file` 这个工具**：

> 证的是"文件正确"，不是"产品可用"；中间差的正是那道信任边界。

这正是本仓点名的两处：
- 第五族第三形状（验收脚本直接 import 实现，把真出口那两级从判卷面里删掉）；
- 规则 152 的第 ③ 条（阴性/能力类结论必须配一条**「工具本身做得到」**的对照，否则分不清"没有"与"够不着"）。

**可迁移的找法**：凡是 harness 对模型说「你可以 X」的地方，判卷里必须有一次**真的用 X 的那把工具**去做，
而不是用比它更宽的宿主能力（fs、直接 import、`child_process`）代做。代做＝把边界本身测掉了。

## 四、后果分两支（第二支更坏）

| 会话支 | 有没有别的通道 | 后果 |
| --- | --- | --- |
| 主会话（有 `run_shell`） | 理论上 `cat <绝对路径>` 能读，但：① 那句让模型用的不是它；② shell 要过权限门/沙箱 profile，读应用数据目录不在"工作区只读"的直觉范围内 | 多花一轮 + 一次审批，模型大概率改道重做原工作（重读、重 grep、重算）＝**返工与 token 双花** |
| worker 只读档（工具集只有 `read_file`/`grep`/`glob`/`lsp`，见 `src/agent/worker-shell-tools.ts`） | **零通道** | 剪掉的原文对那个 worker 永久消失；它只知道自己"看不到"，不知道东西在哪 |

## 五、修法三族与各自前置（我没有偷做，理由在末尾）

- **A（我倾向）**：给 `read_file` 一个**窄的第二允许根**——只接受显式由 `ToolContext` 传进来的 `recallRoot`，
  且仅当解析后的路径落在其内才放行（绝对路径也允许，但仍限该根内 + 仍过 `assertRealContainment` 的 symlink 面）。
  要动的点：`src/tools/base.ts`（类型）、`src/tools/read_file.ts`（判定）、`src/agent/loop.ts`（把 opts 里的根塞进 ctx）、
  **`src/agent/glm-session.ts:620` 那一跳（现在是热文件 `M`）**。
  ⇒ 能力保住，边界不放宽到任意绝对路径。
- **B**：把那句改成"真做得到的动作"（例如明说"工作区之外，本会话工具读不到；如需全文请在 goal/会话面板由用户取"）。
  代价：**收回 §7.4 的回取能力**——属产品裁决，不由我单方面翻。且这两处文案各有一根变异针脚钉着
  （`prune-stub-loses-attachment-path` 一类），动文案要连着动针脚。
- **C**：附件改写到工作区内的 `.agent/` 区域 ⇒ 路径自然可达，但**往用户仓库里写会话垃圾**、
  还要处理 git 噪声与并发会话互踩 ⇒ 我判断比 A 差。

**没偷做的理由（两条都是硬的）**：① A 的最后一跳落在并发会话的热文件上（`glm-session.ts`、`agent-runner.ts` 现在都是 `M`），
按本仓"只追加不改写在飞文件"的规矩不能动；② 探针**故意不进 `gate-manifest`**——未修缺陷的门会恒红，
下次没人分得清"新坏"与"已知未修"。探针自己给非零退出码（打印红 N 而 exit 0 的探针不是绿），
修好那天它会自己变绿。
