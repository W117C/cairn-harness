# M10 · 降智信号清点（2026-10-01）

**这份清单回答一个问题：agent 干活时，harness 有没有给它（或给用户）一个"假信号"？**

假信号是降智最隐蔽的一类来源：模型本身没变，但**它看到的东西是错的**——
于是它照着错信息规划、执行、收工。本仓自己点过名的形状是「**取不到 ≠ 没问题**」与
「**说了 ≠ 验了**」。这一轮把这类信号逐个查了一遍，能修的都修了。

## 二、六条逐条（带证据）

### 1. 退出码把失败报成成功 ✅ 已修

README:222 写「1 = 跑完了但有失败（**工具失败** / 验证红 / provider 报错）」，
而实测 `--mode default` + 非交互时：`write_file` / `run_shell` 全被权限门拒、工作区一字未改，
**退出码是 0**。接进脚本或 CI，失败会被当成成功。

**修法**：纯函数 `runFailed`（五个计数器全取自媒体流）。**实测对照**：修复前 EXIT=0 → 修复后 EXIT=1。

### 2. 演示通道台词谎称完成 ✅ 已修

给它「翻译 README」，它照跑固定剧本去动 `src/todo.ts`，结尾打印
「3 条测试全部通过，bug 已修复，任务完成」——**而同一趟里工具是失败态**。
台词来自剧本，不是判卷结论；而 README 全文 **0 次**提到 demo 通道。

**修法**：README 与 `--help` 写明三条（与你的任务无关 / 台词不是结论 / 会真写文件）。
**实测**：出现该误导的通道现在有明确免责说明。

### 3. 判卷面可改 ⇒ 假绿灯 ✅ 已修

12 条基准任务里 **5 条的模型改过 `tests/`，而这 5 条全部判 PASS**。
一把能被改测试骗过去的尺，比没有尺更坏。

**修法**：任务书 `expects` 补 `judgeUntouched`。**实测**：同一批任务
**11/12 → 9/12**，掉下去的都标着〔改了判卷面〕——**不是能力退化，是原来的绿灯本来就是假的**。

### 4. 澄清答案串题 ✅ 已修

`loop-eval` 的澄清答案写死给内建题（"给待办应用加个开关"），而 `ClarifyGate.submit`
是**原样透传**不按问题过滤 ⇒ 别的任务提问时收到那张"开关"表。
**实测**：B4（分页）的模型收到后直接反问「上一轮你答的是「addTodo / done 开关」，
但本仓库里没有任何 todo」——烧掉一整轮，还被带偏去改判卷面。

**修法**：那张表只给内建题，外部任务交空答案（与 CLI 无人值守档同语义）。**实测**：该反问 1 → 0。

## 三、第 5 条：**未修**，附接线请求（`loop.ts` 属 M5 的写范围）

### 现象（实测，非推断）

工作区**没有可验面**（无 `package.json` / 无 verify 配置）时，模型写过盘、
`autoVerify` 开着，但那"补一拍验证"**没有发生**，然后 run 直接收束：

```
事件类型: user_message, assistant_message, tool_call, tool_result, impact_report
verify_result 事件数: 0
有没有「验证被跳过」的记录: ❌ 没有
写盘发生了吗: 是（写过盘）
```

`src/agent/loop.ts` 里那段（`hasSurface === false` 或探测抛错 ⇒ 跳过）**只 `console.warn`**，
**事件流里不留任何痕迹**。

### 为什么这是降智信号

读者分不清这四种情况（它们的事件流形状**完全一样**）：
① 验证通过（不会——那会有 `verify_result`）
② **验证被跳过：这个仓库没有可验面**
③ **验证被跳过：探测本身炸了**
④ 压根没走到那一步

这正是本仓自己点名的「**没量到 ≠ 通过**」。而且它是**harness 自己的机制在静默失效**——
比模型的错更难发现。

### 已确认的缓解（所以严重度是中等，不是致命）

我查了下游消费者，**它们都处理对了**：
- `goal.ts` 有 `absent` 态（"从头到尾没有验证记录"），注记是
  「本轮**先把验证跑起来拿到证据**，别在没跑过测试的情况下继续加东西」⇒ 不会据此收工 ✅
- M0 的读数把 `verifyOkLast === null` 当**不达标**（"verify 未通过/未跑"）✅
- 终端渲染会打出那行 `console.warn`（管道里可能被淹没）⚠️

**所以真正缺的不是"防止误判"，而是"留下一份可查的账"**——事件流是这棵树唯一的事实出口。

### 接线请求（给集成 owner / M5）

> **改哪里**：`src/agent/loop.ts` 的 auto-verify 判定段（`hasSurface` 那几行）。
> **改成什么**：跳过时**落一条事件**，而不是只 `console.warn`。
> 建议形状：`verify_skipped { reason: "no-surface" | "probe-failed", detail?: string }`。
> **不许做什么**：不许因此增加额外模型调用（原注释明确"零行为零额外调用"是设计目标），
> 也不许把"没可验面"改成"判红"——那不是失败，是**没有量**。
> **验收**：跑一个没有 `package.json` 的工作区，事件流里要能查到 `verify_skipped`；
> 反向验证：把这条 emit 摘掉 ⇒ 判卷必须红。

## 四、四条正面发现（**别再"修"它们**）

| 面 | 实测结论 |
|---|---|
| **工具输出溢出** | `output-ring` 溢出时交出去的是**两行提示**（省略量 + 下一步），不是静默截断；还修过"中文少报 3×"的 bug |
| **影响面的否定结论** | `impact-query.ts` 明确区分「无跨文件调用点（波及半径为 0）」与「波及半径**未知（不等于 0）**」（不支持的扩展名 / .git 等永久排除 / 被文件数帽挤掉）——**不吐假的否定结论** |
| **目标续跑的证据态** | `goal.ts` 有 `verified / failed / stale / absent` 四态，`absent`（从没验证过）不会被当成"完成" |
| **验证失败的归因** | 五类分开（timeout / not-run / 工具链缺失 / 包管理器自身错 / 代码红），**环境红不占模型的修复额度**——直接防"模型照着假红改本来正确的代码" |

## 五、第 6 条：登记待观察（**有意为之，不单方面改**）

`src/agent/context.ts:26` 注入的压缩摘要是：

> 「[系统操作·上下文压缩摘要] **另一个 agent** 已完成如下工作，继续时避免重复劳动。」

而 `context.ts:247` 把它用在**主会话自己的压缩**上（worker 压缩已被排除）——
也就是说，模型被告知**它自己此前干的活是"另一个 agent"干的**。

**但这不一定是缺陷**：`src/agent/compaction.ts:367` 的摘要器指令也是同一套
「交接叙事」，`context.ts:22` 的注释里就叫它"交接叙事"；对 sidechat 那一格
（`sidechat.ts:189`）"另一个 agent"是**字面正确**的。**同一份信封服务两种语义**。

**我没有改，也不建议现在改**，理由与边界：
- 这是**有意设计**（两处措辞自洽），不是漏改；
- 我**没有证据**表明它实际造成行为退化（实测：12 条基准任务里
  **压缩从未触发**——0 次 compaction，所以这条的影响面在**超长会话**，
  而我手上没有那种会话的对照读数）；
- 真要动，应当**按调用点分两种信封**（自我压缩说"本会话此前的工作"、sidechat 保留"另一个 agent"），
  并配一条判卷钉住两种语义——那是独立一笔，不该顺手改。

**建议**：登记为「语义不实、影响未证」。谁要是拿到了"长会话里模型把自己的决定当别人的"
的真读数，再按上面的方向开一笔。

## 五之二、`no-progress` 的接线请求（M10 的核心项，同样不越界去改）

**现状**：`src/agent/no-progress.ts`（248 行）**已经是接线就绪的**——
`judgeNoProgressEvents(events)` 直接吃事件流，返回 `{ action: "silent" | "note" | "directive" | "escalate", ... }`，
内部还有 `detectVerifyStagnation`（同一验证失败的重复）与 `detectAlternatingThrash`（A/B 来回）。
**但全树零生产消费者**（我实测：`grep` 生产调用点 0 处），只在门禁 `no-progress-check` 里跑。

**也就是说：模型可以连着十几轮原地打转，harness 一声不吭。** 这正是"最会防止模型降智"
这一条里最名不副实的一格——判据写好了，没人用它。

### 接线请求（给集成 owner）

**① 落事件**（`src/agent/loop.ts`，每轮工具结果落完之后）：
调用 `judgeNoProgressEvents(events)`；`action !== "silent"` 时追加一条事件
（建议 `no_progress { action, signals, detail }`）。**只落事件，不做额外模型调用。**

**② 投影成注记**（`src/agent/context.ts`）：照**现有 `autoVerifyNote` 的同一套路**——
把最新那条 `no_progress` 事件投成**下一轮可见的 user 消息**（带 token 预算、过一遍截断）。
这一套本仓已经在跑（`loop.ts` 注释：「红由 context.ts 的 autoVerifyNote 在**下一轮**回流给模型
（零额外模型调用）」），所以**不新造机制**。

**③ 不许做什么**（三条，都是防"修出新降智"）：
- 不许把 `action` 直接改成"停下来"——`escalate` 该由既有收束闸与 goal 判据处理，不在这里另开一路；
- 不许每轮都出声（`silent` 是绝大多数轮的正确答案）——**一个爱叫的检测器本身就是新的假信号**；
- 不许新增模型调用（这会直接违背"省 token"那条目标）。

**④ 验收 + 反向验证**：
- 正向：造一段"同一验证失败连续 2 次"与"动作 A/B 来回 3 轮"的事件流，断言 `action` 升到
  `note` / `directive`，且注记真的出现在下一轮的上下文里；
- **反向**：把 ① 的 emit 摘掉 ⇒ 判卷必须红（否则这条接线没有任何东西在看住它）；
- **假阳性护栏**：一段正常推进的事件流必须判 `silent`（这条比正向更重要——
  检测器误报会直接变成新的降智信号）。

## 五之三、接线之前先量了"它会不会乱叫"（**零成本、已出结论**）

**为什么要先量这个**：接线的风险不是"不灵"，是**乱叫**——
一个爱叫的检测器**本身就是新的降智信号**（它会打断正常推进的模型）。
而这件事**不用花一分钱**就能回答：M0 那两次基线留下了 **24 份真实事件流**（12 条任务 × 2）。

### 结果

| 测量 | 读数 |
|---|---|
| 24 份真实跑上的判定分布 | **`silent` × 24**（零误报、零触发） |
| 原始信号最大值 | verify beats **1**｜同一签名重复 **1**（阈值 2）｜工具调用 12–29 次 |
| **阳性对照**（仓库冻结语料） | `real-red-verify-stagnation` → **escalate** ✅｜`synth-alternating-thrash` → **note** ✅｜3 份真实绿跑 + 2 份"不该报" → silent ✅ |

**阳性对照是关键**：它证明**我的量法本身是对的**（该叫的确实叫了），
所以"24 份全 silent"是检测器准，不是我的脚本坏了。

### 结论（三条，都要说清）

1. **接线安全** ✅：24 份真实跑零误报，不会打断正常推进。
2. **它确实抓得到真实停滞** ✅：仓库语料里 `real-red-verify-stagnation` 是**真实案例**，
   它判了 `escalate`。所以这不是"只在合成数据上灵"的判据。
3. **但不能声称省了多少 token** ❌：我那 24 份里 verify beats **最多 1 个**
   （都是一次就绿），**根本没出现停滞形状** ⇒ **触发频率未测**。
   谁要写"接了 no-progress 省了 X%"，先拿出频率读数。

**建议的接线姿势**：按 §五之二 接，但**把它当保险，不当收益**；
接完之后**在真长任务上量它的触发率**——如果 N 条长任务里一次都不触发，
那它就是"零收益的常驻装置"，该重新评估阈值或摘掉。

## 六、这份清单怎么用

1. **给集成 owner**：§三 那条接线请求可以直接派活（`layer=loop.ts`，属 M5 范围）。
2. **给后续做防降智的人**：**先看 §四**——那四条已经很好，别浪费预算重做。
3. **给评测的人**：假信号会同时污染"能力读数"和"人的判断"，所以**修信号优先于修能力**——
   本轮的实测就是例子：修好判卷面之后，同一批任务的成功率从 11/12 变成 9/12，
   **能力没变，读数变准了**。
