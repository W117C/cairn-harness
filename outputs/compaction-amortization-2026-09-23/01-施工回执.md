## 3. 这一格我自己弄错的四处（都留档）

1. **驱动器每轮新建 provider ⇒ 跨请求状态永远是空的。**
   表现是「A/B 两支逐字同值」，读起来像**策略失效**；实际是策略读的东西在这个驱动方式下不存在
   （`headSurvival` 恒 null）。生产是「一个 run 一个 provider」，驱动器必须照做。
   ⇒ 一般教训：**判据测不到 ≠ 被测物不存在**；先证观测路径与生产同形，再谈结论。
   这也是本仓「同族出口」缺陷的反面版本——我造的测试脚手架与生产不同形。
2. **合成样本的 tail 配置不像生产**：第一版把 `tailMinTokens/tailMaxTokens` 压到 300/900，
   tail 预算 900 落在工作集下限 1,500 之下 ⇒ 策略**按设计**拒绝动作，A/B 又同值。
   改法是让样本用生产缺省，而不是放宽下限——后者会为了测试把真实保护拆掉。
3. **窗口开太小，触发全落在 `overflow` 那一支**：`overflow` 按设计不摊销（见 `00` §3 边界三），
   所以「不动」是对的；我一度把它当成 bug。修法是放大窗口让阈值路径可达，
   并**把触发种类记进读数**（第一版读种类是在临时目录被 `rmSync` 之后才读文件，永远读不到，
   表现是「触发种类=[无]」——正是那条 EPIPE 式自伤）。
4. **一条断言靠手数字符位置**：`stableChars` 我按「第一条之后」估成 8，实际断点在 15。
   改成 `prev.indexOf("2")` —— 让断言自己说明「断点 = 被改的那个值的位置」，不靠我数。

另：一处测试脚手架里我留了一条 `expect(x).toBe(cond ? x : x)` 的**恒真式**，被自己的眼睛逮住了；
本仓有专门扫恒真式/析取式的体检，这种断言留着就是给下一轮埋雷。

5. **一条变异针脚存活，暴露出我依赖了 `clamp` 的求值顺序**：
   第一版策略返回 `{ tailRatio: next/available, tailMaxTokens: next }`，配一句「两个旋钮一起收」的注释——
   看着很稳，但 `cc-only-one-tail-knob-tightened`（保留 tailMax 不改）实测**存活**：
   在今天的 `clamp = min(hi, max(lo, v))` 下，`tailRatio` 其实是多余的那个，真正承载的是 `hi`。
   ⇒ 改成把上下限同时钉到 `next`（`ratio` 不动），两种求值顺序都得同一个值；针脚改盯「只钉一个边界」，
   并且测例直接断言 `orderA === orderB`。同时承认：这条策略的第一版**通过**了测试也只是因为
   断言写的是「比基线小」而不是「等于 next」——弱断言放过了强缺陷。

6. **测例改名后忘了改指锚点 ⇒ 表现为「变异存活」**：把那条测例从「tail 两个旋钮必须一起收」改成
   「上下限被钉到同一个值」之后，针脚的 `expectFail` 还写着旧标题。runner 判的是「红在**期望那条用例**上」
   （子串比对），找不到就叫存活。⇒ 规矩：**改测例标题必须同笔 grep 一遍 `expectFail`**。
   这一族本仓已记过一次（见 git log 里「锚点的 expectFail 要写用例标题不是散文」），我又踩第二遍。
