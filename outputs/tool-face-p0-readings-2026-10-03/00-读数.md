## 1. 结论先行

### 1.1 上游的内核读数是对的；**不完整的是它的结论**——越线完全由插件驱动

上游结论 §一.3 写：首方固定面实测 default 17 件 = **2,501 token/轮**，低于官方「工具定义 >10K token」触发线约 4 倍，因此「token 驱动不命中」。

**本日复核：内核那一格上游量得准。** 仓库内核自己产出的缺省面：

| 档 | 工具 | 工具字符 | 首条 system | 合计 / 帽 | 折 token | 是否超帽 |
|---|---|---|---|---|---|---|
| `default` / `auto` | 22 把 | 10,801 | 697 | **11,498 / 24,000** | ≈3,194 | ✅ 在帽内 |
| `read-only` | 9 把 | 3,881 | 697 | 4,578 / 24,000 | ≈1,272 | ✅ 在帽内 |

⇒ **光看内核，24k 帽与 10K token 触发线都不会被碰到**，上游那格读数成立。

**不完整的是被它推出的结论**：真实桌面请求（135 次）里，面是内核的 3–5 倍——

| 指标 | min | p50 | p90 | max |
|---|---|---|---|---|
| 工具件数 | 10 | **60** | 83 | **115** |
| 工具表字符数 | 5,792 | **52,716** | 67,598 | **86,776** |
| 折 token（/3.6） | ~1.6k | **~14,643** | ~18,777 | **~24,104** |
| 折 token（/4，memory/inject 口径） | ~1.4k | ~13,179 | ~16,900 | ~21,694 |

**135 次请求里有 117 次（86.7%）工具表单项就超过 10K token 触发线。**

准确的说法是：**上游说的「数量那一维已越线（含插件 77 把）」是对的**；本文补的是——**同样的差额把 token 那一维也一起顶过了线**（p50 约为内核的 4.9 倍字符数）。所以「token 驱动不命中」这句只对**内核**成立，对**装了插件的真实部署**不成立。差额全在插件/MCP 侧（历史可见宇宙 124 把里，内核之外的族占绝大多数：`ego_*` 33、`mnemon_*` 17、`univer_*` 14……）。

### 1.2 但**别把这句读成「每次请求都在降配」**——这些会话跑在没有 24k 帽的构建上

送出面出现 52,716 / 86,776 字符，而 `MODEL_SURFACE_TOTAL_CHAR_LIMIT = 24_000`。**若该帽在跑，送出面不可能超 24k**——除非 `unresolvable`，而 core 约 13 件 ≈ 6.5k 字符，装得下 ⇒ 不是它。

所以：**这批历史数据是「未降配」的真实面**。它证明的是「面真的会这么大」，**不能**用来证明当前仓库里的 `planSurfaceBudget` 会不会开火、会丢谁——那仍然要等 `surface_account` 在新构建上落账。

## 3. 两条必须先看的边界（否则会把读数读反）

1. **这是「送出面」，不是「声明面」。** `request/header` 记的是发出去的 `SurfacePlan.specs`。降配梯吃掉的量在日志里**看不见**——那正是要新事件的理由。反过来有用且成立：**送出面 > 24k 字符 ⇒ 该轮降配梯必然开过火**（core 装得下，不可能是 `unresolvable`）。本批数据全部超线 ⇒ **它们都没走降配梯**（见 §1.2）。
2. **24k 帽只算「首条 system + 工具 JSON」之和**，这里只量了工具那一项。缺的那一项只会让真实面**更大**，所以越线判定是**保守**的（宁可漏报，不误报）。

## 6.5 读数 4：把**仓库真实的 `planSurfaceBudget`** 套到历史真实工具表上——它会丢掉谁

这是 V6 剩下那一半。做法：从 `request/header` 的 `{name, description, parameters}` 还原成
`GlmToolSpec`，直接调**仓库里的真函数**（不是重写一份），`systemChars` 一律取 **0**（最有利假设：
首条 system 不占字符；真实值只会丢得更多 ⇒ 下面的丢弃量是**下界**）。

```
请求 135 次｜形状对不上的条目 0
降配梯开火的请求        117 / 135
unresolvable            0 / 135        （app 名匹配不上内核 core，全部可丢 ⇒ 总能凑够）
每次丢掉几把            min 6 / p50 40 / p90 50 / max 84
丢过的不同工具          86 把，其中 36–39 把**是真实会话用过的**（承载 22–23% 的真实调用量）
```

**关于丢弃顺序的一条重要更正（2026-10-03 当晚复核）**：把 135 份历史工具表的数组顺序逐一比对，
**135/135 全部是按字母严格升序**——在那批日志所属的构建里，「从数组尾部丢」**等价于「按字母表倒序丢」**，
结果 `write`（真实调用 109 次）在 117 次开火里每次都被丢，而 `bash`、`edit` 因首字母靠前活下来。

**但这不一定是当前仓库的行为。** 实测仓库自己产出的工具表（`sessionToolSpecs`，22 把）：

```
read_file, grep, glob, lsp, edit_file, apply_patch, write_file, run_shell, clarify, propose_plan, …
… automation_create, automation_update, automation_delete, automation_run_now, automation_list
是否按字母升序：否
```

它是**能力序**：core 在前、插件按注册顺序追加在后（与 `model-surface.ts` 注释里那条「core 在前、
plugin 在后」的不变量一致）。所以当前仓库的尾丢顺序是「**最后注册的插件的工具先被丢**，然后 pinned」。

⇒ 两条结论要分开记：
1. **稳健的那条**：降配梯在 117/135 上开火、每次要丢约三分之二的面，丢掉的集合里包含真实在用的工具。
   无论数组按什么排，**「按位置」都不等于「按效用」**——现在的序是注册序，与任务相关性无关。
2. **不能外推的那条**：「按字母丢」是那批日志所属构建的排序产物，**不要**当成当前仓库的必然行为。
   同理，模拟里 `write` 被丢也是 app 名匹配不上内核 core 的产物——仓库的 core 受保护，`write_file` 不会被砍。

上游 §7 预言的「位置尾丢在静默丢错人」因此**仍然成立**，只是要按注册序说：**最后装的插件最容易被丢**，
而「最后装的插件」往往正是用户为当前任务刚装的那一个。

**必须一起读的三条边界**（否则会把这条读成「上线后必然丢 `write`」）：

1. **app 层名 ≠ 内核名**。`write`/`read`/`edit` 与 `write_file`/`read_file`/`edit_file` 不是同一层；
   仓库的 `CORE_SURFACE_TOOL_NAMES` 认不出这些 app 名，所以本次模拟**高估**了丢弃量。真实上线时
   core 受保护，`write_file` 这类不会被砍。
2. **仓库的工具表顺序有另一条不变量**（`model-surface.ts` 注释：「core 在前、plugin 在后」，由
   `model-surface-check` 守）。历史数组的**字母序**不是那条顺序 ⇒ 具体名字只作**指认**，不作预言。
3. 因此能站住的是**形状**，不是名单：**降配梯会在绝大多数请求上开火、并且按位置（=与效用无关的
   某个序）丢掉真实在用的工具**。「按效用丢」要改的正是这一格。

```bash
# 真实工具面（每次请求的工具表：件数 / 字符数 / 是否越线）
node --import tsx outputs/tool-face-p0-readings-2026-10-03/measure-declared-face.mts [--json]

node --import tsx outputs/tool-face-p0-readings-2026-10-03/measure-used-tools.mts [--json]

# 降配梯会丢掉谁（跑仓库真实的 planSurfaceBudget）

```

产出：`declared-face.json`、`used-tools.json`、`cap-impact.json`（同目录）。
`measure-cap-impact.mts` 依赖 `used-tools.json`（读不到会显式告警并跳过「丢掉的有没有被用过」那一问）。

**两个格式坑**（都踩过一次，写进两个脚本头注）：
1. `session.v4.jsonl.zstd` 是**一帧一次 append 的拼接流**，Node 的 `zstdDecompressSync` / 流式解码**都只解第一帧就停**——实测 36,774 B 的文件只吐出 291 B 且**不报错**。必须按帧魔数 `28 B5 2F FD` 切帧。
2. **v4 词表 ≠ 内核词表**。v4 是 `tool/call` / `assistant/attempt` / `turn/start`；`src/events/index.ts` 的 `AgentEvent` 是 `tool_call` / `assistant_message`。按内核词表去 grep v4 日志会**零命中且零报错**。

## 8. 未做 / 不可得

- **已补出**：`surface_account` 想回答的两件事里，「真实面多大」由 §4 直接量出，「降配会丢谁」由 §6.5 把**真函数**套在历史面上算出来。两者都不需要新构建。
- **仍不可得（这才是新事件不可替代的那一格）**：**真实降配轮里的 declared（入参）那一份**。这些会话跑在没有 24k 帽的构建上（`request/header` 只是发出去的那份），所以「本来有多少、被吃了多少」在日志里无从对照——§6.5 给的是**反事实推演**（把帽套到历史面上），不是**实测的 before/after**。
- **未做**：`surface_account` 在真实桌面会话上的落账读数——需要改动进到跑着的 app 里（当前 app 的产物里**没有** `MODEL_SURFACE_TOTAL_CHAR_LIMIT`，也无 `planSurfaceBudget`）。
- **未核**：跑出这些会话的内核到底是哪一版（app.asar 里找不到该常量，desktop profile 的 `node_modules/@deepseek-ai/` 下也没有 bundle）。但 §1.2 的推断**不依赖**版本考古：数据本身（送出面 52k–87k）就排除了「24k 帽在生效」。
- **未核**：`135` 次请求是否覆盖全部 73 份会话的高频路径（有 1 份会话无 header）。
- **已核（本节新增）**：历史数组**为什么**是字母序——**不是当前仓库的行为**。实测仓库产出的表是能力序
  （core 在前、插件按注册顺序在后，见 §6.5），因此字母序是那批日志所属构建的产物。
  **仍未核**：那个构建在哪一层排的序（app 侧还是更早的内核），以及它是否同时绕过了 core 保护——
  这决定「那批历史 face 到底代不代表仓库上线后的形状」。**不影响 §6.5 的稳健结论**（按位置 ≠ 按效用），
  但影响能不能拿那 117 次当上线后的预测。
