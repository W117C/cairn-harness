1. **「pipeline 加环/改道」裁否**——真轨迹里 `mode=pipeline` **一次都没有**（sequencer 消息 0 条）。
   在被绕开的那条路上加改道机制＝为假想需求设计。口径与 W1b / D8 同一条：**先量触发面，再谈建**。
2. **读数当场指出真正的缺口在哪**：模型不写 pipeline，它把结构化计划**塞进 supervise 的顶层参数里**——
   `rep3` 那次申报的是一份三阶段门控计划（实现 → 验证 → 修复循环，带 gate 标记），


## 四、边界（写明，别读成"参数面做完了"）

1. **表"过报"比漏报危险**。漏报＝误拒合法调用，测试与真实调用会当场撞出来；
   过报（表说某档读、代码其实已不读）＝该拒的放过去，静默。过报侧今天有一条机器哨兵：
   锚点 `spawn-arg-table-loses-a-reader`（删掉表里一个读键 ⇒ 「每个键至少被一档读」立刻红）。
   它守的是"整格丢失"那一形；**"键还在表里、代码却不读了"那一形今天没有判卷**——
   那要在每档真调用处加断言（`resources`/`context`/`model` 各一条），本笔未做。
2. **`resources` 在 pipeline 那一档只是"读了为了警示"**：`spawnPipeline` 拿它算链内租约相交警告，
   但逐环 `stageArgs` 不带它 ⇒ **链的写租约并没有真的持有**（`spawnSupervise` 同形）。
   本笔不修它（修法是让逐环真登记租约，会改审批与冲突语义，且 pipeline 真轨迹为 0），
   另立任务。**"申报的租约只进审批卡、不进约束"是比"静默丢键"更重的一格**。
3. **值形状不判**：`stages: []`、`depends_on: "abc"` 这类"键对但形状错"仍由各档自己管
   （`parseStages` / `parseStringList` 已严）。本表只管"这个键这一档读不读"。
4. **规格文案没跟着改**（`role` 的说明仍未点名"只有 read/write 读"）：`src/agent/glm-session.ts`
   此刻在别的会话的写入窗口里（transport/attachment 两簇在飞），本轮不动别人的在飞文件。
   拒绝语已经把同一件事说给模型听了，所以这不是缺口而是**待收的重复**——下一次动该文件时顺手补。
5. 拒绝发生在 `depends_on` 延迟登记之前 ⇒ 一个既带依赖又带错键的调用会先收到参数面那句。
   这是刻意的（先纠正申报，再排队），但它意味着**依赖等待中的调用不会先落 `deferred` 回执**。
6. **顺手量到一条判卷假红，别把它读成"已修"**：`verify-claims.mts` 的 32:C1
   （「没有任何门对账 schema 声明的参数 ↔ 实现真读的 args.X」）今天读作"已失效"。
   实测 HEAD 与工作树两侧：`scripts/mutate-verify.mjs` 单文件里 `properties` 与 `args.X`
   **各自都存在、但同一行双命中 0 条**——它的判定是**文件级**的，于是变异表里那些**引用代码片段的针脚文本**
   把这条判据顶成了假红（第 32 页那句话本身仍然成立：这样的门今天没有）。
   根因是第 33 页 §79 的老形状（静态判据把示例文本当代码），修法要 AST 级或至少同行级 + 反向对照，
   已并入任务 #2（那条本来就是"参数面对账的分母缺口"）。
7. **主树那句 `typecheck exit 0` 今天是"读了别人的在飞态"读出来的**：`src/main/index.ts` 与
   `src/preload/index.ts` 此刻被并发会话**整体删除**（未提交），所以 tsc 看不见它们；
   同一道门在 HEAD-only worktree 里报 34 条（`Cannot find module 'electron'` 及其级联 implicit any）。
   两个口径的对照做过：本单元之前的 `aa30513` 在同一 worktree 配方下也是 34 条同一批 ⇒
   **与本笔无关**，但这条读法本身是缺陷族的第 N 次现身（门读盘 ⇒ 对"HEAD 里有、盘上没有"的文件零信号，
   第 35 页 §97 同形）。**任何"typecheck 绿"的声明都要注明算的是哪棵树**。
