# 队列保存、派发与恢复：阶段验证

持续优化目标保持 active。范围是共享工作树增量，未提交或发布；HEAD `be9c0be5`、分支 `fix/spec-summary-double-count`。完整套件数字覆盖运行时的共享工作树，包括保留的其他任务改动。

## 改变的行为

- 从 run-queue 提取队列持久化模块，写入与出队共享按 workspace/session 串行的链。出队保存确认前不调用 run；保存失败恢复队首，并合并等待期间新增的消息，不用旧数组覆盖它们。
- 已知保存失败会停止自动续发；显式恢复或“重试保存”才重试。“重试保存”本身不执行任务。保存中显示状态、禁用队列改写，失败显示未保存状态；本窗口未保存消息会保留。
- 整条 drain 在等待持久化前即防重入；恢复期间的新消息归入原队列。行级动作按渲染 id 重新定位，旧回调不会因索引变化操作别的消息。
- 重新开会话时，保存失败/写入中的本地队列不被旧盘面覆盖；队列版本保护读期间发生的本地变更，避免迟到快照把已经派发的消息重新放回队列。
- host 给会话响应增加 accepted 回执，按真实主面 user_message 挂点判断。明确未接收的失败可恢复入队；已接收后的执行失败保留既有停表语义，不自动重发。接收前取消也停表，避免重试循环。协议升至 v51，沿用版本失配闸。
- 新重试入口及保存状态使用现有正文颜色令牌；未新增依赖、JSONL 事件或队列磁盘格式。

## 尚未证明的边界

这里验证已知应答下的保存与接收顺序，不提供 exactly-once 崩溃保证：出队落盘后、run 接收前仍有进程崩溃窗口；IPC 断连时也可能不知道 run 是否已接收。要关闭这些窗口，需要持久化请求身份、接收确认与去重，不能靠 renderer 盲目重发。未保存的数据只保留在当前窗口，不声称能跨重启恢复。

多窗口同时修改同一个 sidecar 的冲突控制、真实 Provider、跨机器/网络分区、Windows/NFS、正式签名打包和发布没有验证。原有部分错误/运行统计通道仍按裸 sessionId 记账，不把队列数据的工作区归属等同于所有提示状态均已隔离。

后续继续核查异步创建会话的视图归属、错误提示与其他同名会话状态，以及持久化请求确认的剩余窗口。整体持续优化目标未完成。
