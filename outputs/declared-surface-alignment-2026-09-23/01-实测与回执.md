## 一、字面量清单的同名多份：两组，**两组都不一致**

全仓扫 `export const X = [...]` / `new Set([...])`（按引号取成员，不比字符串整串）：
**83 处声明、45 个标识符**，同名多份的只有两组，而两组成员都不同：

```
PROVIDER_IDS：2 份 ⇒ 成员不一致
   src/main/provider-keys.ts     [glm]
   src/providers/registry.ts     [glm, openai, anthropic, gemini]

HISTORY_STATES：2 份 ⇒ 成员不一致
   src/main/scheduler.ts         [queued, running, succeeded, failed, skipped, cancelled]
   src/renderer/projections.ts   [all, queued, running, succeeded, failed, skipped, cancelled]
```

⇒ 这两组**恰好是判据必须能区分的两种情况**：
`PROVIDER_IDS` 是**真分歧**（同一个名字，一份说 1 家、一份说 4 家）；
`HISTORY_STATES` 是**良性差异**（渲染层那份多了一个 `all`，那是筛选项不是状态）。
⇒ 任何"重名就报红"的门会在第二组上立刻变成噪声门，然后被人关掉
（与 23 的 `telemetry` 教训、25 的 `unknown` 塌缩教训同一条）。

## 二、provider 链的双向差集（发货 vs 够得着）

```
registry.ts PROVIDER_IDS    = [glm, openai, anthropic, gemini]
settings.ts PROVIDER_KINDS  = [demo, glm]
provider-keys PROVIDER_IDS  = [glm]

注册表有、设置里选不到（发货了但用户够不着）：[openai, anthropic, gemini]
设置里出现、key 面存不下（选了也白选）        ：[]
```

⇒ 三个方向里坏了一个：**3 家 provider 在注册表里活着，在设置与 key 面上不存在**。
`gap-fix-proposal` 的 P2-6 已把这条记为"能力已发货、入口没通"，但那是**散文**；
本页要的是让这类差集**每次编译都被算出来**（要么补入口，要么显式登记为 V1 边界）。

## 三、校验顺序：注册表检查排在权限门**之后**

`src/agent/loop.ts` 的真实次序（本轮读码）：先走权限判定与 `[permission denied]` 回执，
**之后**才 `const tool = (opts.tools ?? TOOLS)[name]`、才判 `unknown tool`。

⇒ 外部论文《Closed-World Resolution Against ToolHallucination》给的次序正好相反：
**「hallucination defense must precede the causal gate」**（§V），
且他们的基线结论是**「gating-only stack executes entirely」**——只设权限门的栈会把幻觉调用整条执行下去。
⇒ 本仓今天就是那个被点名的形状。（注：`loop.ts` 对未知工具**会**回一条 `ok:false`，不是崩溃；
问题不在"没兜住"，在"一个根本没注册的名字先过了权限门、被分级评估了一轮"。）

## 四、我探针自己的假阳性 = 这一缺口的现场演示

语料扫描把 `shell_rw`（3 次）、`shell_ro`（1 次）报成"未登记的工具名"。核对后它们是**合法名**：
住在 `src/agent/orchestrator-config.ts` 的 `WORKER_TOOL_TABLE`（worker read/write mode 工具表），
不在 `TOOL_NAMES`（10 个静态名）里。

⇒ 为了让探针能判"合法/幻觉"，我**手抄了一份运行期注入名单**（9 个别名）——
而这份手抄名单本身就是错的成因。⇒ **本仓没有任何一处能回答"这个作用域下哪些工具名合法"**：
静态表、worker 表、`installAppTools()` 的运行期注入、sidechat 表，四份各自持有，**无联合源**。
⇒ 同一文件的注释里已经记过一次同类事故（P0-1 同源补漏）：
「漏了 `shell_rw`，J7c 就退化成『**碰巧为真**』而非名单驱动」——
"断言恰好成立"和"断言由名单驱动"的差别，正是本页要的东西。

## 五、已证 / 未证

**已证**
- 同名多份清单两组、成员都不一致，且两组性质相反（真分歧 vs 良性差异）——这是判据设计的硬约束（§一）。
- provider 三向差集：3 格够不着、0 格白选（§二）。
- 校验顺序与外部结论相反：注册表检查在权限门之后（§三，读码）。
- 没有"作用域 → 合法工具名"的联合表，导致连**测量者**都要手抄名单且抄错（§四）。
- 该缺陷类本仓已自记一次（`orchestrator-config.ts` 的 P0-1 注释：断言"碰巧为真"）。

**未证 / 待核**
- DSH 的 provider 面里，worker 侧 `toWorkerModel` 是否真能把请求发到那 3 家（若能，则"够不着"仅指主会话；
  若不能，则是死代码）。本轮未跑通网络面 ⇒ 标未证，且这正是 P2-6 的联网未证项。
- 权限门在前是否**已经**造成过任何可观察后果（未见证据；这是次序问题，不是事故报告）。
- 参数级 schema 校验（外部论文的 (2)(3) 两类）在本仓的误拒率：本仓已有 `gateToolSpecs` 等静态规格表，
  但没做过"必填缺失/类型错"的拒绝计数 ⇒ 上 L1 时必须先只**记账不拒**。
- `HISTORY_STATES` 之外还有多少"良性同名差异"未被扫到（我只比了同名者；**异名同集**没查，
  那是另一半，落地时补，别假设 83 处里只有这两组重复）。
