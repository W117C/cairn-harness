# 长会话的投影规模有判据 · 2026-11-01

检查起点与交付面都是共享工作树，HEAD `be9c0be5`；本批改动未提交。

## 这一批做了什么

先量后判：流投影（`derived/stream.ts#projectStream`）是每条事件都要过的纯函数，长会话一旦退化成平方，
界面会先卡在投影这一步。本轮先量出现读，再把「规模斜率」钉成判据。

## 读数（本机，工作树，未提交）

| 规模 | 事件数 | 行数 | 耗时（最佳） | 每事件 |
|---|---|---|---|---|
| 300 轮 | 3 000 | 1 800 | 1.4 ms | 0.47 µs |
| 900 轮 | 9 000 | 5 400 | 4.8 ms | 0.53 µs |
| 2 700 轮 | 27 000 | 16 200 | 11.4 ms | 0.42 µs |

线性。判据不看绝对毫秒（机器快慢不同），只看斜率：事件 ×9 时耗时不得超过 ×25（平方会是 ×81）。

| 判卷面 | 读数 |
|---|---|
| 造红 | 在 `projectStream` 里插一段 `events.indexOf(e)` 平方扫描 ⇒ **1 红**：规模比 **40.6**（小 1.43ms / 大 58.00ms） |
| 复原 | 连跑两次 **2/2 绿**，sha256 相同 |
| 桌面套件 | **2073 条全绿**，exit 0（含 boundary 绿） |
| 两端 typecheck | 0 / 0 |

## 文件

- `red-green.log`：平方路径被抓住的原文与复原后的连跑绿。
- `desktop.log` / `typecheck.log`：桌面套件与两端 tsc。
- `scoped.patch`：本批两个文件的差量（判据文件相对 /dev/null）。
- `docs-check.log`：台账门在补页之后的读数。

## 边界

- 这是「规模斜率」判据，不是帧率判据：它只保证投影本身不退化，不管 DOM 布局与绘制（那部分靠折叠 + 行级 memo）。
- 小规模一侧有 0.2ms 下限，防止太快的机器上噪声做分母。
- 现读数字是本机一次读数，不是承诺；判据只用比例。
