## 一、结论

### 一句话

用户四个直觉中，**「不全量注入」方向正确但理由需要换**（真正被证据支持的是「按需/disclose-on-demand」而非「让模型或 laya 替模型挑」）；
**「事后约束 + 反向验证」有明确反证**，只能以「外部可验证反馈」形式成立，不能以「模型自评」形式成立；
**「laya 决定工具集」在能力形态上被官方数据否掉**，唯一未被否掉的 laya 用法是**「先重排、不裁剪」**——而它恰好与本仓 2026-09-21 旧结题 §5.1 第 ⑥ 条的判定**逐字一致**，且旧结题已经把它判为「严格不劣于现状」。

### Q1｜是否应当「不全量注入工具」

**结论：应当减少每轮必付的工具面，但不应当让「谁来决定用哪把工具」成为一个前置概率判断。**

分三层，证据强度不同：

1. **「工具面过大确实损害效果」——证据方向一致，但强度被高估了。**
   - 一手厂商实测：Opus 4 从 49%→74%、Opus 4.5 从 79.5%→88.1%（A3）。
   - 一文学术：MCP 工具选择 13.62%→43.13%（A1）。
   - 两者**同向**，但都是**在「数百把工具、每把描述数百 token」的极端候选集上**取得的大幅增益。
   - **不可外推到本仓**：本仓缺省固定面工具仅 13 把 / 6,397 字符（C6），远在官方触发线（>10k token 或 10+ 把，A2）之下半档。当前不是「损失准确率」的区间，而是「装三个 MCP server 就会进入该区间」的临界区间（C7）。
   - ⇒ 结论：**这是一个「防劣化 + 省 90.5% 固定面字符」的问题，不是「提升智能」的问题。** 用户「更能展现大模型能力」的预期，在本仓当前工具规模下**没有证据支持**。

2. **「该由大模型自主决定」——可以，但必须是模型自己发起检索，而不是让它面对一个被削过的工具表。**
   - 官方推荐形态是「模型保留高频 3–5 把 + 一个搜索工具，其余 `defer_loading`」（A2/A6）。关键在于**完整工具库始终对模型可达**。
   - **反模式**是「宿主/前置模型算一个子集，模型只看见子集」。二者的差距不是风格，是**错误模式**：该用而不可见的工具＝静默失败且难诊断（与 stage 白名单、斜杠命令等确定性契约冲突）。这条判定在旧结题 §5.2 已经拍过一次（C15）。

3. **本仓的最大障碍不是策略，是缓存。**
   - 可缓存前缀**字面包含工具面**（C1）。工具面一变 ⇒ 该层重写 ⇒ 本轮及之后按全价重发。
   - 本仓实测：命中时吃 86.6%，未命中时**整段归零，没有中间态**（C8）。⇒ 每轮重新计算工具子集，等于每轮主动制造一次整段归零。
   - 官方之所以敢说「不破坏 prompt caching」（A4），是因为它的机制是**单调追加**（deferred 工具先不进 prompt，`defer_loading:false` 的核心工具与 system 保持稳定），而**不是**「每轮重新选一批」。
   - ⇒ **任何「每轮计算工具子集」的方案，在本仓都要额外付「前缀重写」的代价，且需要满足 PC4 的逐字确定性（C3）。这条代价在用户原问里没有被计入。**

### Q2｜「先无干扰思考，事后用提示词/skill 约束与反向验证」

**结论：这个模式作为「机制」不成立；作为「外部可验证反馈的时机安排」部分成立。必须区分两件事。**

- **「事后用提示词约束」＝措辞级干预，证据显示边际收益极小。**
  BFCL V4 在 26 种提示配置 × 39 个模型上测「换措辞/换 markdown」：**无一致趋势，模型对此稳健**（A9/A10）。
  同时，**「怎么呈现工具」影响远大于「怎么措辞」**：函数文档 JSON > Python > XML，返回格式 Python/JSON > XML（A9）。
  ⇒ 用户「等思考完再上约束」如果落实为「同一模型在轮末读一段提醒」，是把预算花在证据最弱的那一格上。

- **「让被约束方反向验证自己」＝自评自判，有直接反证。**
  - 内在自我纠错（无外部反馈）**不能**提升推理，**有时反而下降**（A7，ICLR 2024，同行评审）。
  - LLM 评估者能**识别自己的输出**并系统性给高分，且自我识别能力与偏好强度**线性相关**（A8，NeurIPS 2024）。
  ⇒ 「大模型独立思考 → 再让大模型自己反向验证」在本仓会同时命中这两个反证。**成立形式只有一种：验证者的判据来自模型之外**（测试、lint、类型检查、git diff、deterministic gate、别人的产出）。

- **「skill 做事后约束」在本仓形态上做不到。**
  skill 是**按需加载的说明文本**，不是规则引擎（C14）；它不改变「模型有没有被约束」，只改变「模型脑子里现在有没有这段说明」。用它承担「约束」是把提示词换了个文件名。
  ⇒ 真正的事后约束在本仓已经存在且更硬：`sessionToolFace` 的 note 机制（省了谁必须说出去，C11）、PC3「工具面变了必须点名」（C2）、降配梯的 `unresolvable` 交人裁（C4）。**这些是确定性契约，不是提示词。**

### Q3｜知识沉淀

**结论：闭环已经存在，用户描述的「这一系列过程」不会自动产出沉淀；缺的不是流程，是「可判定的沉淀信号」。**

- **已有**：`distill.ts` 沉淀轮（白名单只允许 `remember`）+ `lessons.ts` 失败教训（**没有 callId 证据指针就不出条目**）+ `inject.ts` 注入（C13）。
- **已有**：事件流即事实来源（旧结题的「事件流外私有状态＝设计错误」纪律，C15）。
- **缺口**：沉淀的**触发**目前是「会话结束跑一轮 LLM 判有无值得沉淀」，旧试点实测该判断的 noul 分数 0.2985 偏保守（C15 §四），即**漏沉淀高价值项**的风险是实测到的。
- ⇒ **如果新增「工具选择」这一层而不落事件流，等于新增一处私有状态**，直接违反本仓纪律，且会让沉淀层看不见「为什么这轮只有这些工具」。
- ⇒ 正确落点：**工具面的每一次变化都必须落事件并点名**（PC3 已经是这条纪律的判据）。这样「工具面收敛过程」才可被事后蒸馏成知识，而不是变成不可审计的魔法。

### Q4｜laya 接入（用户最在意）

**结论：不应以「决定工具集」为接入点接入。** 这是本报告最硬的一条否定结论，依据是**官方一手数据**，不是推测。

**（1）形态不匹配 —— 这是硬约束，不是「需要实验」。**

| laya 的原生形态 | 工具选择需要什么 | 是否匹配 |
|---|---|---|
| `choice`＝**单选**，返回单一标签（A12） | 在动态增长集合上做**多标签排序** | ✗ 不支持多标签 |
| 选项数 ≳20 精度崩塌（77 标签 0.425，A13） | 候选集是几十把工具起 | ✗ 恰好落在崩塌区 |
| 官方对 >20 选项的护栏就是「先短名单」 | 短名单 + 排序正是所需 | △ 有原生对应物，见下 |
| 零样本低于多数类基线；0.766 来自在基准自身训练集上微调（A16） | 工具集合每装一个插件就变 | ✗ 候选集变动 ⇒ 微调成果随时作废 |

**（2）唯一形态上可行的用法：`predict_shortlist`（A14）——但它已被旧结题判过，且判的是「只能重排、不能裁剪」。**

- 机制：用 laya **自身编码器的嵌入**做相似度 top-k 短名单，再单次前向定答案（A14）。
- 关键限制：**短名单收益未经官方复测**——仓库原话是 issue #102 报告 BANKING77 从 54.3% 到 60.8%，并注明「Those figures are the reporter's; this repository has not remeasured them」（A15）。**这是一条二手/未复测读数，不能当作收益证明。**
- 更关键的是**已决事项**：旧结题 §5.2 明确否决「laya 决定给什么 skill/工具/插件（裁剪工具表）」，理由是该用的工具不在桌面＝任务静默失败 + 与 stage 白名单/斜杠命令等确定性契约冲突 + 输入面（只见任务文本）撑不起决策的信息需求；**同时判定「仅重排 ✅」的变体成立**（C15）。
- ⇒ **用户本次的新用途，被 2026-09-21 的旧结题在「裁剪」这一支上已经否决过。** 用户没有改变论据，改变的是期待强度。**这不构成重新评估的理由。**

**（3）旧结题的三条否决理由，正面回应（这是简报要求）**

| 理由 | 2026-10-03 复核结果 | 是否翻转 |
|---|---|---|
| ① 语言栈错位（纯 TS + Python sidecar + ~1GB 权重） | **部分松动**：官方现有 `laya-ts/` npm 包（A20）与 ONNX 导出/量化（A21），协议层还有官方 MCP/HTTP server（A22）。但 Python 3.10+/torch 2.14/transformers 5.x 依赖与 ~1GB 权重仍在（A11、C15） | ✗ 未翻转，扣分减少 |
| ② 架构摩擦（决策须落事件流） | **加重**：不仅「新增事件类型走门禁」，工具面本身就长在可缓存前缀里（C1），每轮变动即前缀重写；PC4 还要求同配置下逐字确定（C3） | ✗ 未翻转，**加重** |
| ③ 能力重叠（`routing/` 已解决 Router 同款问题） | **仍成立**：本轮未在 `routing/` 发现任何工具面能力；`routing/policy.ts` 的 pin > 档位表 > 降级链仍是纯函数 | ✗ 未翻转 |

**（4）旧结题「复评触发条件」的现状（C15 §5.4）**

| 触发条件 | 现状 | 是否触发 |
|---|---|---|
| 1. distill/审查的 LLM 成本被证实为可感知负担 | 未复核（本轮未读计量读数） | 未触发/未知 |
| 2. 官方 ONNX/量化导出或 TS 推理路径，权重 <200MB，免除 Python sidecar | **ONNX 与 TS 路径已出现（A21/A20）**；权重 <200MB **未核**（README 未给量化后体积） | **半数触发** |
| 3. 出现高频分诊场景（每轮多次） | **本轮新增一条**：若真按「每轮选工具」，那就是每轮多次 ⇒ 理论上命中 | 但该场景本身是本报告建议**不要做**的 |

⇒ **触发条件 2 的「免除 Python sidecar」半条已被官方动作部分满足。因此「laya 因分发/维护负担出局」这一条不能原样复用了；但它出局的真正理由已经换成能力形态与已决裁剪契约——这两条与分发负担无关，不受 A20/A21 影响。** 简报要求「正面回应而不是回避」，这就是回应：**旧结题的结论仍然成立，但成立的理由权重需要重排——从①③为主，改为「能力形态不匹配 + 已决契约」为主。**

**（5）laya 在工具面上的净判断**

- **裁剪工具表 ❌**（形态不匹配 A12/A13/A16 + 静默失败 + 已决契约 C15 §5.2）
- **只重排不裁剪 ⚠️ 有条件成立**，但**必须满足**：全表保留（不作可见性闸门）、呈现顺序变化须点名（C2）、同配置下顺序逐字确定（C3），且**先离线量化**才能接线。
- **最诚实的评估顺序**：先用**真实会话日志**离线跑「laya 工具重排 vs 现状顺序」，量**工具选择准确率一致率**——这是旧结题 §5.3 就已点名的共同前置（中文/混合文本判分质量未验证，D9），**本轮仍未执行**。

## 二、方案比较（一致维度）

维度含义：**适用条件**＝什么情况下才该考虑；**收益**＝有证据支持的部分；**成本**＝一次性的 + 每轮的；**风险**＝失败模式；**可逆性**＝回退难度。

| 方案 | 适用条件 | 收益（证据） | 成本 | 风险 / 失败模式 | 可逆性 | 推荐 |
|---|---|---|---|---|---|---|
| **A. 全量注入现状** | 固定面 ≤ 帽且工具都高频 | 确定性最高；零新增机制 | 0 | 装 3 个 MCP server 即 +427%（C7）；**无总闸会静默膨胀** | — | **保留为基线**，但**已完成的一半**见 F |
| **B. 静态分组 / 按角色分工具面** | 角色边界清晰且稳定（如只读子代理） | 本仓 `sessionToolFace` 已支持合法分组变更并点名（C11）；子代理可有不同工具面 | 低（配置） | 分组策略随插件增长腐化；「该用不可见」的静默失败 | 高（改配置） | **可接受**，作为 F 的补充 |
| **C. 渐进式披露（检索工具 + 按需拉取）** | 工具定义 >10k token 或 ≥10 把（A2） | 官方实测 49%→74% / 79.5%→88.1%，省 85% 上下文（A3）；**不破坏缓存的前提是单调追加**（A4） | 高（provider 层无 `defer_loading` 语义；需自建检索器） | 检索漏召回 ⇒ 该用工具不可见；每轮重选 ⇒ 前缀整段归零（C1/C8） | 中 | **方向推荐，但本仓当前规模未到** |
| **D. LLM 自主前置规划选工具** | 需跨轮多步规划时 | 无独立证据；与「模型自己发起检索」等价但多一次 LLM 轮 | 每任务 +1 轮 LLM | 子集化 ⇒ 静默失败；规划错误放大 | 中 | **不推荐**（同 E） |
| **E. 本地小模型 / laya 前置筛选** | 候选集**极大**且**可微调**且**有标注** | **无**（A15 是未复测的二手读数；A16 零样本低于多数类） | Python 运行时 + ~1GB 权重；每轮一次前向 + 前缀重写 | 裁剪＝静默失败 + 违反已决契约（C15 §5.2）；负迁移 | 低（引入即难退） | **不推荐（裁剪）**；**重排待离线验证** |
| **F. 复用 `routing/` 档位表 + bandit 思路扩展到工具集** | 需要「同一判据一处实现」时 | 与既有 `routing/` 同构，不新增运行时；判据纯函数可离线测 | 低（纯 TS） | bandit 的探索期会**主动抖动工具面** ⇒ 与 PC4（逐字确定，C3）冲突 | 高 | **推荐（作为唯一方向）**，但需**先解决探索与确定性的冲突** |

**推荐组合：A（基线不动）→ F（把「工具面总账 + 尾丢 + 点名」这条已存在的机制用于收缩，而不是引入新判断主体）→ 仅当工具面真的越过 10k token 时再评估 C。**

**为什么 F 优于 E：** F 复用本仓已有机制（`model-surface.ts` 降配梯 + `prefix-churn.ts` 判据，C2/C3/C4），同源同刻、纯函数、可离线判、可逆；E 需要引入新运行时、新的失败面、新的私有状态。用户想要的「让 agent 工作得更好」，F 给出的是**可测量的省与防劣化**，E 给出的是**未验证的收益 + 已验证的失败模式**。

## 三、反证与争议（明确列出）

1. **反证 1（对 Q2）**：内在自我纠错不能提升推理、有时反而下降（A7）。
2. **反证 2（对 Q2）**：LLM 评估者识别并偏爱自己的输出，且自我识别能力与偏好强度线性相关（A8）。
3. **反证 3（对 Q2 的措辞支线）**：BFCL V4 在 39 个模型 × 26 种提示配置上发现换措辞**无一致趋势**（A9/A10）。
4. **反证 4（对 Q1 的「越大越差」简化）**：A1 原文报告工具池增长时**选择准确率与任务成功率呈非单调趋势**，并非单调下降。⇒ 不能把「工具多了就差」当作线性规律。
5. **对 Q4 的最强反方论据（诚实登记）**：A21/A20 确实推翻了旧结题复评触发条件 2 的一半——官方 ONNX/量化与 TS 路径已经出现。**若后续核实 `laya-ts` 真正免 Python 且量化后权重 <200MB，则「语言栈错位」这一条将实质失效。** 本报告仍不推荐 E，理由**不依赖**语言栈，而依赖 A12/A13/A16（形态）与已决契约；但**读者必须知道：E 的反对理由里，最弱的一条正是语言栈。**
6. **未解决分歧**：A15 的短名单收益（54.3%→60.8%）是一手仓库**转述第三方**读数且自认未复测。本报告**不作结论**。任何「laya 重排能提升工具选择」的说法，在此数字被本仓独立复现前都不成立。

## 四、风险与未知项
