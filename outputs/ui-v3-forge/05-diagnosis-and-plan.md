# Forge 桌面端 Agent 应用 · 现状诊断与优化方案

> 交付物 ② / 共三件：① 可交互 HTML 原型 ② 本报告 ③ 设计系统规范（`02-design-system.md`）
> 所有现状陈述均为**实测**（读源码 + 构建产物 + git 状态 + 门禁脚本），证据行号可复核。

## 0. 结论先行

1. **你要的不是重做，是"补三处结构性缺口"。** 现有 Forge 界面的对话底子相当扎实（令牌体系完整、无障碍资产齐全、12 处动效降级、消息内审批卡），真正的问题只有三个：**任务执行没有独立视图**、**运行状态处在视线边缘**、**历史只有"会话"一个维度**。
2. **一个必须先纠正的认知偏差**：你的仓库里不是"两套 UI"，而是**一次正在进行、尚未提交的渲染层迁移**（React → vanilla）。这直接导致 `pnpm panels-check` 在当前工作树上**不可能全绿**——这是独立于设计任务的工程债，见 §5。
3. **设计方向确定为"演进而非推翻"**：沿用 oklch 灰阶 + 现有字体栈 + 单一强调色，新增令牌仅 1 组（任务运行四态语义色，双主题实测 AA），新增容器仅 2 个（底栏状态栏 h-6、⌘K 命令面板）。

## 2. 不足诊断（按你点名的三大诉求 + 横向规范）

### 2.1 对话交互：底子好，缺"长对话的可控感"

| 已有 | 缺口 |
|---|---|
| 气泡、think 折叠块（含耗时）、plan 卡（`2/4 已完成`）、diff 卡（token 着色）、复制/撤回、上下文弹层 | ① 流式期间**无排队发送 / 中断恢复**的可见反馈；② 长对话**无消息级导航**（回到底部、跳转某轮、按卡片类型过滤）；③ 卡片状态**靠文字**（`2/4 已完成`），无进度可视化；④ 卡片无统一骨架（`.card` 各类变体结构不一） |

### 2.2 任务执行与状态展示：**最大的结构性缺口**

| 已有 | 缺口 |
|---|---|
| `agents` 面板（worker 卡 + 依赖链 + 合并控制塔）、`schedule` 面板、消息内审批卡 `.card.ask[data-ask]` | ① **无独立「任务执行」视图**——编排被压在 340px 右抽屉的一格标签里，与其余视图争宽；② **运行状态（沙箱/事件数/tokens）被放在侧栏底部**（`docs/m0c-ui-light.png` 可见），处于视线边缘，运行中无全局阶段/进度指示；③ 审批到达**全局提示弱**（仅消息内卡片）；④ 无 run 批次产出汇总；⑤ 内核已有卡死/崩溃恢复能力，**UI 无「卡死/恢复中」呈现** |

> 补充说明：`agents` / `schedule` 等面板在**已入库的 React 版**中存在（`panels/registry.tsx` 有 `AgentsPanel`/`SchedulePanel`），但在**当前工作树的 vanilla 层尚未实现**。因此本模块在 vanilla 层属**新建**，不是"增强现有"。

### 2.3 历史记录管理：只有"会话维度"

## 3. 优化方案

### 3.1 方案总纲：演进而非推翻

| 维度 | 决策 |
|---|---|
| 视觉 | 沿用 oklch 灰阶骨架 + 现有字体栈（实测为 `-apple-system/PingFang SC/system-ui`，**非 Geist**）+ 单一强调色 `--accent: oklch(55% 0.18 255)` |
| 新增令牌 | **仅 1 组**：任务运行四态语义色 `--st-run/--st-wait/--st-stuck/--st-fail`（+ `-fg` 变体），light/dark 双主题实测对比度达标 |
| 新增容器 | **仅 2 个**：底栏状态栏 `.statusbar`（h-6 = 24px）、⌘K 命令面板 `.cmdk` |
| 新增视图 | 任务执行视图、run 批次历史（vanilla 层新建） |
| 落地对象 | `src/renderer/index.html` 内联 CSS + `app.js` 模板（vanilla 层），**非**未接线的 React 版 |
| 不做 | 不换字体/色板/组件库；不引毛玻璃/渐变/新色相（四态除外）；不引路由/多窗口；不回退无障碍资产 |

### 3.2 三大模块的优化要点

**对话窗口**
- 流式可控化：排队发送条 `.queue-bar`（`role=status`）+ 运行中发送钮→停止钮（`[data-state=stop]`）+ 中断后「已中断 · 可继续」态。
- think 两态化：`.think.running`（脉冲 + 「思考中」）/ `.think.done`（静态 + 「已深度思考 Ns」）。
- 卡片统一骨架：`.card > .card-head + .card-body + .card-foot`，6 类变体 `plan/diff/tool/approval/verify/report`；plan 卡补进度可视化。
- 长对话导航：回到底部浮钮（带未读计数）+ 卡片类型过滤器（`[role=toolbar]` + `aria-pressed`）。
- composer：1–8 行自适应（max-height 168px）+ `+` 附件入口 + 引用回填（`.quote-bar`）。

**任务执行面板（重点）**
- 独立「任务执行」一级视图：`.task-row` 列表（四态点 + 阶段 + 进度 + 耗时）+ 主从详情。
- **全局运行状态条**：新增底栏 `.statusbar`（`role=contentinfo`，`--surface-2` 底），收纳沙箱 / 事件数 / tokens / worker 数 / **当前阶段 + 进度**；**独立底栏而非浮层**，故在 1024/1280/1600 三档均可见且不遮主内容区。
- worker 节点卡 `.worker-node[data-state]` 四态 + 依赖链 `.dep-chain`（SVG `aria-hidden` + `aria-describedby` 文字兜底），点击节点右侧滑出事件流。
- 审批入口：顶栏 `.approval-dot` 黄脉冲 + 计数徽标（reduced-motion 降级静态），1 次点击到达。
- run 产出汇总 `.run-output`（`.ro-diff/.ro-verify/.ro-report`）。
- 卡死/恢复：`.worker-node.stuck` + `.recover-btn`。

**历史记录管理**
- 会话维度**零回退**（保留置顶/归档/重命名/文件夹/分组）。
- 新增 run 批次行 `.run-history-row`（可展开 → worker 产出 / verify / diff 汇总）。
- 检索扩展范围（标题/正文/工具/文件）+ 状态筛选 chips（含计数）+ 回收态（删除可撤销）+ 时间轴（可切粒度）。

### 3.3 响应式（补齐四档）

| 断点 | 侧栏 | 右板 | 主区最小宽 | 输入区 | 消息列 |
|---|---|---|---|---|---|
| ≥1600px | 列 264px | 列 340px | ≥480px | 不折叠 | 1040px 封顶居中 |
| 1280–1599px | 列 264px | 列 340px | ≥480px | 不折叠 | clamp 居中 |
| 1024–1279px | **icon 态 64px** | 列 240–340px | ≥480px | 不折叠 | clamp 居中 |
| 960–1023px | icon 态 64px | **覆盖式 Sheet**（复用 `index.html:1177` 的 `.drawer.open-m` 机制） | ≥480px | 不折叠 | 用满宽 |

配套：窗口最小 960×600；栏宽持久化「手动 > 自动」；4K 支持 100/125/150% 缩放。

### 3.4 四态语义色（唯一授权新增色相，双主题实测 AA）

| 态 | Light | Dark | 对比度（非文字 / 彩色文字） |
|---|---|---|---|
| 运行 `--st-run` | `oklch(52% 0.15 150)` | `oklch(74% 0.15 150)` | light 5.11:1 / dark 8.86:1；文字 >7:1 |
| 等待 `--st-wait` | `oklch(45% 0.008 250)` | `oklch(76% 0.012 250)` | light 7.43:1 / dark 8.98:1 |
| 卡死 `--st-stuck` | `oklch(50% 0.14 70)` | `oklch(80% 0.13 80)` | light 6.15:1 / dark 10.19:1 |
| 失败 `--st-fail` | `oklch(53% 0.2 25)` | `oklch(76% 0.16 25)` | light 5.86:1 / dark 8.11:1 |

**状态集为 7 态，三重编码纪律**（硬约束）：颜色 + 图形 + 文字。判定方式：**全部转灰后，仅凭图形 + 文字仍能区分 7 态**即通过。

| 状态 | 颜色 | 图形 | 文字 |
|---|---|---|---|
| 成功 | `--ok` | ✓ | 成功 |
| 运行 | `--st-run` | 实心点 + 脉冲环 | 运行中 |
| 等待 | `--st-wait` | 空心点 | 等待 |
| 卡死 | `--st-stuck` | 点 + 「!」 | 卡死 |
| 失败 | `--st-fail` | 点 + 「×」 | 失败 |
| **被拒** | `--st-fail` | 点 + 「**⊘**」 | 被拒 |
| **已中断** | `--st-wait` | 空心点 + 「**⏸**」 | 已中断 |

两处刻意取舍（**不新增色相**优先于色相区分度，故靠**形状**补偿）：
- **被拒 vs 失败**：同红族 `--st-fail`，形 `⊘` vs `×` 可辨。
- **已中断 vs 等待**：同灰 `--st-wait`，形「空心点 + ⏸」vs「纯空心点」可辨。

> 这两条是审查轮发现并修正的真实缺陷：初版把「被拒」误映射为 `--st-stuck`（amber「!」，语义冲突），且「已中断」与「等待」渲染完全相同。修正后 7 态满足 G-6「删色可辨」。
> 字形安全性已实测：`⊘`/`⏸`/`×`/`!`/`✓` 在本机字体栈（`-apple-system, PingFang SC, system-ui`）下**全部单色渲染并继承 `currentColor`**，无彩色 emoji 回退、无缺字方框。

## 5. 阻断项与风险（必须先决策）

### 5.1 🔴 `pnpm panels-check` 在当前工作树上不可能全绿

**事实**：`scripts/panels-check.ts` 的 7 个 CDP 探针指向 React 版 DOM——`data-m1e-item`（`:257-271`）、`data-m1e-event-count`（`:251`）、`data-virtuoso-scroller`（`:264-269`）、`data-approval-badge`（`:278`）、`data-panel-toggle=git`（`:286`）、`data-panel-id=git`（`:327`）、`data-m1e-settings-open`（`:299`）。

**静态确证**：全仓检索（排除 `node_modules`/`oh-src`/`out`/`dist`）显示这些属性在当前工作树**没有任何渲染方**——仅存在于探针自身、已断链的 `conversation.tsx`，以及 `.tmp/`、`.mimosa/` 的历史快照。

**影响**：`pnpm gates` 在当前工作树**不会全绿**。这不是设计问题，是 §1.3 迁移未收口的遗留债。

**两个可选处置（需你裁决，均不属本次设计范围）**：
- **A（推荐，成本低）**：把 7 个探针改指 vanilla 层真实钩子（`.msg` / `.stream` / `#settingsOpen` / `[data-view]` / `.card.ask[data-ask]`），并同步更新 `docs/m1e-*.png` 截图基线。
- **B**：把 React 层接线回来（恢复 `main.tsx` + `styles.css`），并把 vanilla 迁移作为独立变更单列成本——但那样等于放弃已完成的迁移工作。

**本设计已遵守的纪律**：原型**只保留 vanilla 层真实存在的 35 个钩子**，**严禁伪造** `data-m1e-*`。为迎合探针而造钩子会制造**假绿**，比红门更糟。

### 5.2 🟡 其余风险

| 风险 | 说明 | 处置 |
|---|---|---|
| run 聚合数据源 | 任务视图与 run 历史依赖"一次运行"的聚合字段（worker 产出 / verify / diff 汇总）。若内核 IPC 未暴露 run 聚合，前端只能结构占位 | 原型已按结构占位实现；**需内核补接口后接线**（建议单列任务） |
| 依赖链连线 | 端点按列中心估算，flex 布局高度可变时为近似 | 已用 `aria-describedby` 文字兜底，不单独依赖图形 |
| 「被拒 / 被中断」筛选色 | 仅授权 4 个语义色 | 已落地：**不新增色相**，改为拆分独立状态——被拒 → `--st-fail`（红族）+「⊘」；已中断 → `--st-wait`（灰）+「⏸」。靠形状而非色相区分（详见 §3.4 的 7 态表） |
| 迁移期间的文档漂移 | `docs/` 截图与 `outputs/ui-design-*.md` 两份历史提案均按 React 版描述 | 建议在迁移收口时统一修订，否则后续会持续误导 |

| 双主题 | light / dark 逐屏目检 + 四态对比度复算（正文 >7:1、次级 >4.5:1） |
| 无障碍 | 12 处 `prefers-reduced-motion` 降级不回退；新增动效各自补降级；`role`/`aria-*` 抽查；最小点击区 28×28 |
| 删色可辨 | 四态在三重编码下删除颜色仍可区分 |

## 7. 质量审查与验证结果

### 7.1 审查链路（5 维评审 + Anti-Slop 门控，两轮）

| 轮次 | 结论 | 逐维分数（哲学/层次/执行/特异性/克制） | 关键发现 |
|---|---|---|---|
| 第 1 轮 | **REVISE** | 4 / 4 / **3** / 5 / 4 = 20/25 | P0=0、P1=4：①「被拒」误用 `--st-stuck`（amber「!」，语义冲突）；②`#ctxUpload` 死按钮；③`#archiveToggle` 死按钮；④⌘K `aria-activedescendant` 恒为空（ARIA 断线） |
| 第 2 轮 | **PASS** | 4 / 4 / **4** / 5 / 4 = 21/25 | P0=0、P1=0；7 态编码浏览器实测「色+形」组合唯一性 7/7 |
| 第 3 轮（导出后修复） | **PASS** | 4 / 4 / 4 / 5 / 4 = 21/25 | P0=0、P1=0；覆盖断点开关双向可逆、跨断点无残留、非覆盖分支无回归；回归红线（12 禁用模式 / 35 钩子 / 四态令牌 / 6 个 reduced-motion 块 / 单文件自包含）全绿 |

审查的独立验证手段（**非采信构建师自评**）：全文件 grep、Python 独立复算 oklch→WCAG 对比度、**headless Chrome 真跑 24 项交互 + 5 档断点**、6 张截图目检。审查官如实声明了 3 项**未验证**：Electron 真机窗口最小尺寸、屏幕阅读器真机播报、4K/150% 系统缩放。

### 7.2 审查轮修正的两个真实缺陷（值得记录）

1. **「被拒」色相语义错误** → 拆为独立状态 `rejected`（红族 `--st-fail` + 字形「⊘」）。
   主理人未采纳审查官"直接改成 `fail`"的建议：那样「被拒」与「失败」会同色同形（红 +「×」），只剩文字差异，**违反「删色可辨」**。改为共享色相、靠形状区分。
2. **「已中断」与「等待」渲染完全相同**（都是灰色空心点，仅文字不同）→ 同样拆为独立状态 `interrupted`（`--st-wait` + 字形「⏸」）。
   → 最终 **7 态**全部满足"全部转灰后仅凭图形 + 文字仍可区分"（验收项 G-6）。

### 7.3 导出阶段发现并修复的缺陷

交付达在导出时**未自行改动原型**（正确做法），而是报回主理人：

- **缺陷**：960–1023px 覆盖断点下，右板开关 `#drawerToggle` **逻辑整体取反**——关闭时点击算不出"要打开"，打开时也算不出"要关闭"，即**既开不了也关不了**（`forge-ui-v3.html:2493` 覆盖分支漏了取反）。
- **修复**：单行修正为 `isOverlay() ? drawer.classList.contains('open-m') : ...`。
- **主理人独立复验**（headless，1000px）：`click1{openM:true,scrim:true}` → `click2{openM:false,scrim:false}` → `click3{openM:true}`，开→关→开双向正确；1280px 非覆盖分支无回归。
- **顺带修正同类问题**：覆盖断点**初始化**时面板隐藏但 `aria-pressed` 恒为 `"true"`（视觉与无障碍状态相反，且首次点击不产生状态变化播报）；**跨断点**（宽窗→窄窗）时右板状态不跟随。两处均已修。

> 这条链路的经验：**门禁通过 ≠ 交付无缺陷**。审查轮 PASS 之后，导出阶段的真实操作（而非静态检查）仍能挖出交互缺陷——因为第 1 轮的 24 项交互清单里没有覆盖"覆盖断点下的右板开关"这一条。

### 7.4 流程反思（审查官留档，值得沉淀为检查项）

上述缺陷属于 **「断点切换 × 组件交互」的组合态**：
- 第 1 轮的 **24 项交互清单**只在**固定断点内**测交互；
- 第 1 轮的 **断点测试**只在**默认态**测布局；
- 二者交叉处（**覆盖态下点开关**）成为盲区。

→ 后续原型自检应补一条组合用例：**同一交互在每个断点档 + 跨断点切换后各测一次**。

另一条方法论留档（审查官踩过的坑）：`--dump-dom` 不产生合成帧，**`requestAnimationFrame` 不触发**，因此依赖 rAF 的回调在纯 headless 下不执行——这是**环境限制而非代码缺陷**，需用注入 rAF shim 或 `--screenshot` 交叉证实，**不可据此误判为 bug**。
