## 一、为什么这不是"把帽调大就完事"

那 7 格差额**全部落在将被删的桌面层测试里**（未暂存删除 209 个文件；暂存区 2 条且都是别人的重命名，**删除 0 条**；`src/renderer` 盘上已无而 HEAD 里还有 10 个跟踪文件）。
把两棵树挤进一个数只有两种写法，两种都是谎：

- 按 10 登记 ⇒ 主树（真正在发货的那棵）的进度从此推不动，棘轮变装饰；
- 按 3 红 ⇒ 把别人没提交的删除记成我的尺坏了，而且这个红**我永远修不掉**（修它＝提交别人的活）。

所以帽子中登记成表，读数自己声明它读的是哪棵树：

```ts
export const SCOPE_CEILINGS = {
  "core-only": { multiCopy: 3, bareName: 0 },
  "含桌面层": { multiCopy: 10, bareName: 3 },
} as const;
```

两行各只准降。**「含桌面层」那一行会在删除入库后失去对象 ⇒ 那时删这一行，不许把 core-only 调大**（写进常量注释，同规则 101 的"清单要带反向一侧"）。

## 二、谓词抽成纯函数，但它不是全部

判据面＝`src/renderer` 在不在盘上（AGENTS.md 把"本 checkout 没有 renderer"写成了 core-only 的定义）。
抽成 `treeScopeOf(hasRendererFace: boolean)` 才能两侧钉用例：恒真＝永远拿宽帽，恒假＝HEAD 验跑红在别人的账上。

但**纯函数用例钉不住接线**：`scanRepo` 里把路径写成 `src/renderers`，谓词依旧正确，只是在这棵树上恒假。
⇒ 真仓扫里补一条对账，用另一把原语读同一个事实（`readdirSync(src).includes("renderer")` 对 `existsSync`），和 `copyCount`/`copySites` 那两把尺互检是同一个手法。

## 四、顺带改掉的三条"以在飞半边作活证"的针脚

`r.inFlightFiles.length > 0` 这类断言把**盘上今天有没有人在飞**当成了尺的标准，而那是树的状态：干净树上必然为 0，于是同 HEAD 验跑必假红。
改成两侧配对的互斥条件——在飞集合为空 ⇒ 所有 `flying*` 必须同时归 0（否则"排除在飞"是在凭空抹格子）；非空 ⇒ 在飞清单要真点名到 `tests/`、`src/` 里的文件。
裸名字那族同理：活证从"在飞半边 >0"改成**两半之和 >0** 并加一条 `bareName ＋ inFlightBareName ＝ 按谓词挑出的全部`（这条与树的脏净无关，两棵树都红得住）。
