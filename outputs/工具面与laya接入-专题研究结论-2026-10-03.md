## 一、结论先行（六条）

1. **用户前提需要更正：DSH 已经不是「全量注入工具」。** 每轮装配都过 `planSurfaceBudget`：24 000 字符池 + 描述紧帽 600 字符 + 按数组尾部整条丢弃，`core` 层永不自动砍，走完仍超帽报 `unresolvable` 交人裁决，并**如实点名省了谁**（`src/agent/model-surface.ts:21`、`glm-session.ts:816–839`）。所以问题不是「要不要不全量」，而是**这条已在跑的降配梯是按「位置」而不是按「效用/相关性」选人**。

2. **laya 不能承担「决定用哪些工具」——三条否决全部来自官方一手文档，不是推测。** ① `choice` 是**单选**语义（README 原文 "pick one label"），无多标签/集合输出，`decide` 对 array/对象直接 `SchemaError`；② 一个问句的所有选项**共享** `head_max_len`（英文 192 / 另两支 256 token），官方自陈「约 20 个带短描述的选项」即触发全体裁剪，而本会话可见工具已达 **77–79 把**；③ base 检查点零样本在 typed-decisions 上 **0.362 / 0.352，低于多数类基线 0.461**（随机 0.318），官方原话「**Laya is a fast base to specialise, not a zero-shot decision engine**」。

3. **「不全量给工具是否对 agent 更好」——方向上业界答案是肯定的，但对 DSH 当前规模不成立。** Anthropic 自 2025-11-24 起把 `defer_loading` + tool search 做成常规工程面（Opus 4 49%→74%、Opus 4.5 79.5%→88.1%）；但其**触发条件是「工具定义 >10K token」或「10+ 把」**，而 DSH 首方固定面实测只有 **2 501 tok/轮**（`node --import tsx scripts/prompt-cost.ts`，本日实跑），**低约 4 倍**。DSH 真正越线的是**数量**那一维（含插件 77 把，越过官方「30–50 把」经验线），而官方那条「30–50 把」在文档里**无出处、无实验披露**。

4. **「先无干扰思考、事后用提示词/skill 约束与反向验证」——机制层面不成立。** 两条同行评审反证：无外部反馈的自我纠错**不能**提升推理、有时反而下降（arXiv 2310.01798，ICLR 2024）；LLM 评估者能识别自己的输出并系统性给高分，且自我识别能力与偏好强度**线性相关**（arXiv 2404.13076，NeurIPS 2024）。skill 是**按需加载的说明文本**（`src/agent/plugins/skills.ts:11`），不是规则引擎，换文件名不改变约束力。成立的形式只有一种：**判据来自模型之外**（测试 / lint / 类型 / gate / `verify` 退出码级真值）。

5. **知识沉淀的闭环已经存在，缺的不是流程而是「可判定的沉淀信号」。** 已有：事件流（可回放）→ `memory/distill.ts`（沉淀轮）→ `memory/inject.ts`（逐轮回注）→ `remember` 工具 / skill 文件。缺口有二：① 沉淀闸门缺一个可判定的信号（旧试点实测 noul 0.2985 偏保守 ⇒ 漏沉淀高价值项）；② **「哪套工具面在哪些任务上更好」在整个工程里没有任何一处记账**——装配账每轮都算、算完就丢。

6. **若用户仍想接 laya，唯一可能成立的接入点不是热路径决策器。** 旧结题 §5.2 **已经否决过**「laya 决定给什么 skill/工具/插件（裁剪工具表）」，理由是该用工具不可见＝任务静默失败（错误模式最贵）+ 与确定性契约（stage 白名单、promote 命令）冲突。仅「仅重排、不打折」变体被判定成立，但其收益**只有逻辑论证**（全表保留 + few-shot 位置效应 ⇒ 严格不劣于现状），**从未实测**。

## 三、逐题回答

### Q1｜agent 是否应当「不全量注入工具」？

**接受方向，拒绝把裁剪权交给概率模型；且当前不是「掉分区」，是「临界区」。**

- 三份证据方向一致但强度被下调：Anthropic 官方（49%→74% / 79.5%→88.1%）与 RAG-MCP（arXiv 2505.03275：13.62%→43.13%）都取自**数百把工具、描述数百 token** 的极端候选集；DSH 在官方触发线（>10K token 或 10+ 把）**之下**（token 维度）。
- **反证登记**：RAG-MCP 原文报告工具池增长时，选择准确率与任务成功率是**非单调**趋势，不可简化为「越多必越差」。
- **两个方向的外推都不成立**：把「几千把才有必要检索」的结论搬到 77 把，是超范围外推；把 DSH 的「只有 2.5k token」当成「所以没问题」，漏掉了数量那一维。
- 用户「更能展现大模型能力」的预期，在 DSH 当前规模下**无证据支持**；这是「防劣化 + 省固定面」问题，不是「释放能力」问题。
- **决策权归属**：业界答案是**模型自己发起检索**（`defer_loading` + tool search），**不是另装一个本地分类器**。

### Q2｜「先无干扰思考、事后约束 + 反向验证」是否成立？

**作为机制不成立；作为「外部可验证反馈」成立。**

- 事前面已存在：L0–L4 自主性分级 + 审批门、`gateToolSpecs` 按 mode 摘写向工具、worker 三重硬闸（规格面 + 实例面 + loop 白名单）。
- 事后面已存在：`tools/post-execute` 可替换返回值、verify 系统门、`skillDenial` 可在 run 中途摘工具并出 `removed` + note。`tools/pre-execute` **故意不能改参数**（本项目既有实读，成员 3 grep 未命中字面量，**未独立复核**）。
- 把约束推到思考之后再施加，等于**放弃 pre-execute 那道闸的语义**——它本来就不改参数，只拦/放行。
- skill 不能当约束主体：它能走 disallowed-tools 摘工具，那是**白名单**行为，不是「反向验证」。

### Q3｜知识沉淀落在哪？

**三段已有，第四段（工具面/策略面记账）缺。**

事件流（可回放）→ distill（已有，沉淀轮白名单只允许 `remember`）→ 记忆 / skill 文件（已有，按需加载）→ **工具面/策略面记账（缺）**。laya 不解决沉淀问题；沉淀载体应当是既有三处设施，不需要新模型。
**纪律约束**：若新增「工具选择」而不落事件流，等于新增私有状态，直接违反本仓「**事件流外私有状态 = 设计错误**」。

### Q4｜laya 能否加入、接入点是否是「决定工具集」？

**不建议让 laya 决定工具集。** 三条否决（官方一手）：

| # | 否决 | 官方依据 | 后果 |
|---|---|---|---|
| ① | **形态不匹配** | `choice` = "pick one label"；`decide` 对 array/嵌套对象直接 `SchemaError` | 工具选择是「子集 + 排序」。只能退化成 N 个 `noul` 布尔问句，或 `predict_shortlist`——后者是**词面嵌入相似度检索，不是学会的工具选择** |
| ② | **容量不匹配** | 一个问句全部选项共享 `head_max_len`（192 / 256 或 1024）；「around 20 options with a short description each」即全体裁剪；越界系数 `k ≈ head_max_len/4`；HTTP 侧硬闸 `MAX_CHOICE_OPTIONS = 100` | 本会话可见工具 **77–79 把**，单个 choice 问句装不下 ⇒ 必然 N 问。批量实测 10 问 72ms / 50 问 337ms（T4），MPS 上 16 tickets batch 983–1082ms |
| ③ | **校准不匹配** | base 零样本 typed-decisions **0.362 / 0.352** vs 多数类 **0.461**、随机 0.318；招牌 0.766 那支是**在该 benchmark 自己的训练切分上微调**（2×T4）得来 | 「直接拿来用」被官方数据否掉；要用必须先攒标注数据再训 head——而 DSH **连选对率的尺都没有** |

**对旧三条否决理由的逐条复核（不复用旧结论）**：

| 旧理由 | 状态 | 依据 |
|---|---|---|
| ① 语言栈错位 | **部分松动，未解除** | 0.3.24 已有 `laya-ts/`（纯 TS ONNX：encoder.onnx + head.onnx，`onnxruntime-node` 为可选 peer dep，**推理期不需要 Python**）+ `laya-serve` HTTP + `laya[onnx]` 量化。但 —— **主理人本日实测 `registry.npmjs.org/laya-ts` 与 `laya-client` 均返回 404**：TS 路径目前是**仓库内源码 + 需一次性 Python 导出产物**，不是已发货的 npm 包。且官方浏览器 demo 自陈首次加载 **~1.3GB**，INT8 体积未给数，官方另自陈曾出现 per-channel 量化把决策模型打到与 eager **32% 一致**。⇒「不用 Python」成立，「分发负担消失」不成立 |
| ② 架构摩擦 | **仍成立，且新用途比旧用途更重** | 工具面**就是可缓存前缀本体**（`cacheableFace`）。让 laya 逐轮决定工具集 = 逐轮重写前缀（写价 1.25× / 读价 0.1×）。33ms 的收益与这个代价不在一个数量级。较轻的接法是走 `laya[mcp]` + 既有 `pluginTools` 通道（**不新增事件类型**），但那把「<10ms 免一轮」变成「多一次 LLM 工具轮」，**收益逻辑反转** |
| ③ 能力重叠 | **方向不同，不能照搬** | `routing/policy.ts` + `bandit.ts` 选的是 **3 个档位**、有 verify 真终态做 reward；工具选择是**数十候选、reward 极稀疏**。bandit 的经验是**提高**「不要接概率模型裁工具」的置信度 |

**新增一条时效风险（旧结题没有的）**：laya 公开于 **2026-09-18**，16 天发了 **32 个版本**（0.1.0 → 0.3.24），其中 2026-09-24 一天发 9 个，0.3.19 与 0.3.20 相隔 **5 分钟**。DSH 那份结题报告（2026-09-21，v0.3.4）是在该软件**公开第 3 天**的形态上做的判断。现在把它接进热路径，等于把一个**日更的 pre-1.0 依赖**放进 unsigned DMG。
**另需更正一条既有裁决的形式**：`docs/judgment-layer-calibration-proposal.md` §7 三条接入前提的第 ③ 条（分发口径：**远端 HTTP 可接受**）因 `laya-serve` 出现而**部分被满足**——这影响的是理由清单，不是「不接」的结论。

## 六、反证与争议（不隐藏）

1. **支持用户直觉的证据是强的**：Anthropic 官方触发线「≥10 把或 ≥10k token 定义就该按需装载」、MCPMark 实测「选错工具」是已证错误模式（**二手，待核实**）。本团**不反对方向**，只反对「用概率模型做裁剪」这一实现。
2. **本仓 09-23 综述 §1 说 P1 不够**：它明确写「按位置降配是次优的，真正的解是**按效用选子集**」。P1（按角色/优先级丢）只是缓解；若 P0 读出真实丢工具，**P1 可能不足以闭环，得直接上 C**。这是本报告内**最大的未决分歧**。
3. **「位置尾丢」不是疏忽，是缓存驱动**：成员 2 指出尾丢的动机正是**保住缓存前缀**。因此成员 3 的 P1（改按效用丢）与缓存纪律存在张力：只有当丢弃集**逐字确定**（PC4）时才不破缓存。这条张力**三方未收敛**，需在 P1 设计时正面处理。
4. **未核实的方向冲突**：`github.com/memoverflow/rag-mcp` 声称「Full MCP 工具选择准确率反而高 5.6%」，与 RAG-MCP 原文结论**方向相反**；是否同一实验设置**未确认**，本团不采信任何一侧。
5. **未定位一手出处**：BFCL「引入语义干扰函数致准确率下降」只有二手聚合页，官方页 404 ⇒ **未据此下任何结论**。
6. **替代解释未排除（最大未分离变量）**：候选集变大的同时抬高了上下文长度，「more tools 变差」可能只是 lost-in-the-middle / 长上下文退化。业界与学界都**没有做工具数 × 长度的析因实验**（未检索到）。
7. **第二条替代解释会直接推翻整体判断**：官方把失败归到「工具名相似」。DSH 里 `read_file`/`edit_file`/`write_file`/`apply_patch`、`mnemon_remember` vs `mnemon_runtime_memory`、`univer_inspect` vs `univer_status` vs `univer_screenshot` 都是同型。**若真因是命名歧义，改命名/描述可能比动注入机制性价比更高。**
8. **口径未统一**：本仓固定面读数在 6.4k–8.8k 字符 / 2.5k token 区间浮动，分属不同日期与不同单位（字节 vs 字符）。**不应合并成一个数。**
9. **时效**：laya 一切判断的窗口极短（16 天 32 版）；本次所有 laya 读数带版本号 0.3.24 与日期 2026-10-03。

#### 顺带修了一处指标设计错误

`mergeToolChoice` 的 `violationRate` 原先是**调用次数比**。实测发现它**量错了东西**：
只禁一件工具、每轮必调时，比值 = 1 ÷ 总调用数，于是「每次都违规」会随轮数读成
0.083 / 0.125 / 0.167 —— **晃的是分母，不是信号**。
已改为 **case 级**（这次跑违没违规 = 1），调用级另留 `callLevelViolationRate` 一格，两者必须分开读。
正是这次事故暴露了它：旧读数 0.111 看着像「轻微违规」，我就没警觉去查禁令合不合理。

**样本量为什么上不去**：两个端点都是**免费档、有速率限制**——`agnes-3.0-flash` 四条 case 连着跑即
