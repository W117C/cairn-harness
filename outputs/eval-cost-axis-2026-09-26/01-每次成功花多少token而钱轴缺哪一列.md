## 一、加了什么

`scripts/replay/run-scorecard.ts`（同一台面、同一分母，不另起一面）：

- `usageOfStream(events)`：逐条 usage 事件合计。**两条口径直接从 `UsageEvent` 的注释搬过来**，不是我定的：
  `inputTokens` 是**含缓存的总输入** ⇒ 汇总不再把 `cacheRead/Write` 加第二遍；
  缓存分块**缺字段 = 那个 provider 没上报，不等于命中 0** ⇒ 缺报单独计数报出（规则 95 的又一格）。
- `costOf(totals)`：钱轴走**唯一那把真钱尺** `bucketsSpendUsd`（每桶按自己那一档的表价折），
  价键经 `priceForModel` 反查（价表的键是档位 id，拿模型名当键会 100% 查不到——那是本仓实测过的坑）。
  **算不出 ⇒ `usd=null` + 说出缺哪一面，绝不折成 $0**（"不可知记成免费"是点名的假绿形状）。
- `aggregateScorecard` 多出 `tokensPerJudged` / `tokensPerGreen` / `usageEvents` / `cacheUnreported` / `cost`。
  ⇒ 代价轴与成功率**共用同一套分母**（只算"写过盘且能定终态"的流），否则"每次成功更省"可以靠悄悄扩大分母做到。
- 用例 25 条（原 18 + 新 7），含三条负控：零归因必须 null 而不是 0；未注册档位必须 null；`green=0` 时
  `tokensPerGreen` 是 null 而不是 0。

## 二、真跑读数（21 个语料文件 / 33 条流，一条命令）

```
成功率 89%（分母=能定终态的 18 条）· 证据缺席 4 · 返工中位 0
token 轴：每条能定终态 32318 · 每**一次成功** 30570 · usage 事件 166（其中缓存分块缺报 166 条——缺报≠命中 0）
钱轴：不可测 —— 166 条 usage 事件里没有一条带 model 归因 ⇒ 查不到价表键……写侧补齐归因之前，
      $/成功任务只能报不可测；token 轴仍可读。
```

三件事一次说清：

1. **省 token 从此有基线**：一次成功 ≈ 3.06 万 token（16 次成功、18 条能定终态）。这条数是可比的——
   同一语料、同一分母，之后任何改提示词/压缩/路由的改动都要能把它往下压，才算"更省"。
2. **缓存这一维今天是瞎的**：166/166 条 usage 事件**都没上报 cache 分块** ⇒ 命中率无从计算。
   这不是"命中 0"，是**没有这一列**（事件注释原本就写着缺字段=没上报）。
3. **钱轴缺的不是价表，是归因**：价表、反查、尺子都在（`bucketsSpendUsd` 在产品里就是真钱闸用的那把），
   缺的是 usage 事件上的 `model` 字段——166 条里 0 条带。⇒ 补一列写侧字段，钱轴立刻能算；
   现在硬要算就只能拿"会话那一档"去套全部 token，而那正是本仓实测过的 **40 倍分叉**形状。
