# 01 设计与判据：前缀抖动门（装配前缀单调性）· 2026-09-23

> 实测依据在 `00-实测发现.md`。**这一步的选题来自用户裁决**（四个候选里点了「前缀抖动读数进门（低风险，接着做）」，
> 帽值那格确认取 24,000 字符——见 `../model-surface-budget-2026-09-23/02 §0` C-1）。

## 0. 判什么、不判什么（这条是本格的全部要点）

| | |
|---|---|
| **不判** | 「缓存命中率必须高」。实测 41.5% 的暖轮 `cacheRead` **整段归零**、命中时平均 86.6%、且归零与我们的动作无关（上游分片 / TTL / 驱逐）⇒ 拿它当判据会做出一扇**随机红**的门，正是本仓最忌的假红族 |
| **判** | **我们这一侧确定可判的那一条**：没有声明的变异源时，装配必须**逐字纯追加**；易变块变了**不得牵连**可缓存前缀；工具面自己变了**必须出声**；降配必须**确定** |

四条判据都是确定性、离线、可在 CI 判的——不需要凭据，不进「未证」那一格。

## 1. 依赖序（长在哪个层、谁持有、为何不是别层）

| 层 | 内容 | 持有者 | 为什么不是别层 |
|---|---|---|---|
| L0 纯判据 | `src/agent/prefix-churn.ts`：`serializeLayer` / `lcpChars` / `prefixChurn` / 分层切片 / 四条判据 / 两只反向对照用料 | 新叶子模块（零运行时依赖，只 `import type`） | 判据必须是纯函数才进得了单测与自检；放进 `glm-session` 就得连 provider 才能测，放进 `gym/probe` 就只在靶场里能用（而这条纪律要守的是**每一次真实装配**） |
| L1 观测 | `scripts/prefix-churn-check.ts` 驱动**真 provider** 走 4 轮，收 `transport(messages, _o, tools)` 那一三元组 | 门 | 观测必须来自「真正发出去的那一对」。源码形状断言（"看代码里 system 在前"）正是本仓已判定不够的那种判据——`plan_approved` 那一族只有跑起来才分得清 |
| L2 分层词汇 | 可缓存面 = 首条 system + 工具面；易变面 = 其余 system 块 | 沿用 `gym/probe.classifyAssembly` 的切法 | 同一层不能有两个名字。探针按可缓存性切三层是它的本职，本模块只是把「相邻两轮的等式」补上 |
| L3 反脆弱 | 5 条 `pc-*` 针脚 | mutate-verify | 「判据恒真」「无分辨力也报通过」这两族是自检最容易骗人的地方，必须能被杀死 |

## 2. 四条判据

| id | 判据 | 无分辨力时 |
|---|---|---|
| PC1 | 相邻轮的历史层 `pureAppend` 全真（上一轮整串是本轮前缀） | 只有一轮 ⇒ 红（没有相邻对就没判到） |
| PC2 | 易变块**确实每轮在变**（`volatileChanged`）**且**可缓存面 `distinct === 1` | 易变块没变 ⇒ **红**（不许把「什么都没动」报成通过） |
| PC3 | 工具面变化的每一次都有说明（`faceNote` 非空） | 一次都没变 ⇒ 红 |
| PC4 | 同一份超限面装配 N 次 ⇒ 序列化只有 1 种（确定性；抖动=把省下的字节再花回去） | — |
| PC5 | 压缩改写历史 ⇒ **必须有认账证据**（事件流里真的落了 `compaction`）；要求它抖却没抖 = 样本无分辨力 | 首轮就压 = 没有上一轮可比 ⇒ 红 |
| PC6 | 裁剪改写历史中段 ⇒ 同上，证据 = `prune-attachments/` 多了文件 | 每轮裁同一批旧结果 ⇒ 历史仍纯追加 ⇒ 红 |

「认账」用的是 harness **自己留下的痕迹**（事件流 / 附件目录），不是「看到抖了就当它声明过」——
否则这条判据退化成同义反复。

`serializeLayer` 去掉数组尾那个 `]` 是**判据成立的前提**：纯追加时上一轮的串以 `]` 结尾、
本轮同位置是 `,`，留着括号就等于永远判不出纯追加。这条被针脚
`pc-serialize-layer-keeps-closing-bracket` 钉住（实测：去掉针脚里的 `-1` 即红）。

## 4. 留尾（不假装收口）

1. **跨 run 首轮命中未归因**：10 个 run 里 5 个首轮就有 `cacheRead`（前缀被上一个 run 喂过）。
   这对**靶场/门禁的读数解读**有直接影响——同一个 case 连跑两次的成本不独立。本轮未量化，
   要量化需要**时间戳**（`usage` 事件不带）。
2. **写侧成本量不出来**：`usage` 事件只有 `inputTokens` / `outputTokens` / `cacheReadInputTokens`，
   **没有 cacheWrite 字段** ⇒ 1.25×/2× 写价那份成本在本地不可见。要量得先给 usage 加字段（另一格）。
3. **prune 对前缀的影响仍未证伪**：那 10 个 run 里 prune/compaction 事件 0 条 ⇒ 上日 §2.3 的假设
   还是假设。要判它需要**多轮且能触发压缩**的样本：要么动冻结判卷区（须走 BLOCKED 请求改判据），
   要么在门里造一个「历史长到触发压缩」的合成场景——**后者是这条判据的下一步**，
   且能顺手把 PC1 的「声明的变异源」白名单真正用起来（今天四条判据里没有一条走的是压缩路径）。
4. ~~PC1 的白名单尚未接入~~ → **同日已接**：PC5/PC6 用真 provider 触发压缩与裁剪，
   按「事件流落了 compaction」「prune-attachments 多了文件」两只**harness 自己留下的痕迹**归因。
   实测读数与判读见 `00-实测发现.md` §5（一次裁剪重写 ≈4 万字符；一次压缩后仅 2.9% 前缀仍可缓存）。
   仍留的洞：归因白名单是门内构造的场景，**没有**在真实长会话录制上跑过（那需要联网重放）；
   且 PC1 的「合法抖动」目前只覆盖 compaction/prune 两种，skill 中途激活与记忆重读走的仍是 PC2/PC3 的路径。
