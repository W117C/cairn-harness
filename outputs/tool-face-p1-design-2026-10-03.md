## 1. 硬约束：MS3 只准丢后缀

`scripts/model-surface-check.ts:72–73`：

```ts
export const ms3Holds = (before, plan) =>
  plan.specs.length < before.length && plan.dropped.length > 0 && isPositionalPrefix(before, plan.specs);

/** 降配后的保留表是否为原表的**位置前缀**（尾丢与否的判据；中间摘必红）。 */
export const isPositionalPrefix = (before, after) =>
  after.every((s, i) => s.function.name === before[i]?.function.name);
```

**保留表必须是原表的位置前缀 ⇒ 只准删后缀。** 它的 `why` 写明理由：「缓存按前缀命中（tools → system → messages，上游变化会把它之后全部重写）；中间摘一把就把它之后所有条目的缓存打掉」。

### 1.1 实证：丢一把中间工具，比丢 23 把尾部工具破坏大得多

本日实测（`sessionToolSpecs({mode:"default", pluginTools: 40×1200 字符})`，真 `planSurfaceBudget`）：

| 做法 | 保留 | 丢弃 | 可缓存前缀还能命中 | MS3 |
|---|---|---|---|---|
| **① 现行为（只丢尾部）** | 39 把 | 23 把 | **11,476 / 64,871 字符** | ✅ |
| **② 挑着丢一把中间工具**（`glob`） | 61 把 | 1 把 | **1,002 / 64,871 字符** | ❌ |

**丢一把中间工具，把 10,474 字符的可缓存前缀打没了——比丢 23 把尾部工具还狠。**
（缓存写价 1.25× / 读价 0.1×，见 `model-surface.ts` 的降配梯注释。）

⇒ **任何「按效用挑着丢」的方案都会撞 MS3。** 这不是保守，是被缓存经济性逼出来的。

## 2. 因此：P1 = 让**顺序**承载优先级

既然只准丢后缀，那么「按效用丢」的唯一合法实现是：

> **把数组排成「效用从高到低」**，于是尾丢**自动**变成「丢效用最低的那些」。

这个变形很重要，因为它**一条现有判据都不用放宽**：

| 判据 | 在 P1 下 | 为什么仍然成立 |
|---|---|---|
| MS1 固定面在帽内 | 不变 | 不涉及 |
| **MS2 core 段在前** | **不变，且变成必需** | core 优先级最高 ⇒ 仍整体在前；尾丢仍然只碰非 core |
| **MS3 只做尾丢（前缀不变量）** | **不变** | 实现仍是后缀删除 |
| MS4 未超预算逐字不变 | 不变 | 未超帽时不排序（或排序是恒等） |
| MS5 省了谁必须说出去 | 不变 | `dropped` 仍如实点名 |
| MS6 core 不得被自动砍 | 不变 | core 优先级最高 ⇒ 永远不在尾部 |

**新增的唯一硬要求**：顺序必须是**工具集的确定函数**。
否则「同一套工具、两次装配顺序不同」本身就是新的前缀抖动源——那是把 MS3 想解决的问题从丢弃规则挪回装配层，等于没解。

## 3. 改哪个文件

现在的顺序由**装配层**决定，不由 `planSurfaceBudget` 决定（`planSurfaceBudget` 只是从尾部删）。
所以落点在 `sessionToolSpecs()` / `sessionToolFace()`（`src/agent/glm-session.ts` / `src/main/agent-runner.ts:701`），
`model-surface.ts` **一行不改**。

**这是本设计最大的好处**：改动面小、可逆（排序函数关掉即回到现状）、且 P0 刚落的 `surface_account` 会**自动**记录新顺序下的丢弃结果——P1 的收益可以直接用 P0 的尺子量。

## 4. 优先级从哪来（三个选项）

| 选项 | 机制 | 证据 | 机制成本 | 可逆 | 需要新机制？ |
|---|---|---|---|---|---|
| **A 声明的静态优先级** | 注入口（插件/MCP）多带一个 `priority` 字段 | 无（需要各插件配合） | 中 | 高 | 否（改契约） |
| **B 能力类（capability class）** | 由 harness 按**类**排序：core → 编排 → 通用 → **情境能力**（浏览器 `ego_*`、Office `univer_*`） | **强**：实测 `ego_*` 33 把 + `univer_*` 14 把 = 47 把常驻，占历史可见宇宙 124 把的 **38%**；而这些族在 6,463 次真实调用里份额极小 | 低 | 高 | 否 |
| **C 真实使用频率** | 用 24h/7d 的调用统计排序 | **强**：前 5 把覆盖 90.8% 调用，主会话中位只碰 7 把 | **高**：要一条统计管道 + 冷启动策略 + 「用量变了顺序就变」⇒ 新前缀抖动源 | 中 | **是** |

**推荐：B 为主，A 为接口；C 只做离线校准，不进热路径。**

理由：
- B 的证据就在手上（38% 的常驻是情境能力），零新机制，且顺序是**静态函数**（满足 §2 的确定函数要求）。
- A 给插件一个表达自己「该排多后」的出口，但不强制——没有就用 B 的类兜底。
- **C 有个致命的形态问题**：它让顺序随用量漂移，而顺序就是可缓存前缀 ⇒ **C 直接把 MS3 要防的抖动从「丢弃」搬到了「排序」**。要用 C，必须先解决「顺序多久变一次、变了怎么点名」——那是一条独立机制，不该塞进 P1。
  C 的正确用法是**离线**：定期看哪些类排错了，回头改 B 的类划分。

## 5. 与上游 B / C 的关系

- 上游 **B（静态分面）** 是本设计的**极端形态**：某一类（如 `ego_*`）直接**永不进面**，而不是「排在最后等被丢」。
  B 更省字符，但**丢掉的能力不可降级恢复**；P1 是「按序丢弃」，降配梯走完仍能留下最重要的。**先做 P1，再评估 B 要不要切哪一类。**
- 上游 **C（渐进式披露）** 与 P1 **正交**：C 改的是「哪些进面」，P1 改的是「面装不下时先丢谁」。两者都要，但 P1 便宜得多，且不新增机制。

## 6. 待核（影响设计余地）

**历史工具表 135/135 是按字母严格升序**，而 `MS2` 要求 core 整体在前。二者不可能同时成立。

两种解释，影响不同：
- **(i) 那是「记录面」而非「发送面」**：app 为了日志/UI 排序后再写 `request/header`，实际发出去的是 core-first。⇒ MS2 无恙，历史读数对 P1 仍有预测力。
- **(ii) 那个构建真的不满足 MS2**：尾丢在那套面上等于在砍基础工具（`write`→`write_file` 是 core）。⇒ 那是**比 P1 更严重的既有缺陷**，且历史读数不能当上线后的预测。

**未核**：仓库里 `gateToolSpecs()`/`sessionToolSpecs()` 产出的表**实测是 core 在前**（本日复核，22 把时 core 全在前、插件追加在后），所以 (ii) 若成立，问题出在 app 侧或更早版本。
**这一条必须在 P1 实现前核掉**——否则我们可能在修一个不存在的问题，或在放过一个真问题。

## 7. 验收判据

**必须全绿（复用现有六只，不改）**：`MS1–MS6`，尤其 `MS3`（前缀不变量）、`MS4`（未超预算逐字不变）、`MS6`（core 不得被自动砍）。

**新增判据（P1 专属）**：

| # | 判据 | 可判红的方式 |
|---|---|---|
| P1-1 | **顺序是确定函数**：同一 `(mode, 工具集)` 两次装配，序列化逐字符相同 | 打乱注入口顺序 ⇒ 装配结果仍相同 |
| P1-2 | **顺序只由工具集变化引起**：工具集相同时，任意两次装配的可缓存前缀逐字相同 | 复用 PC2 的口径（`scripts/prefix-churn.ts`） |
| P1-3 | **core 仍整体在前**（MS2 的加强版：排序后仍满足 `coreRunsFirst`） | 给一个 priority 高于 core 的插件 ⇒ 必须红（说明契约被破坏） |
| P1-4 | **未超预算时排序不产生任何字节差异**（MS4 的加强版） | 在缺省装配上开/关排序 ⇒ 逐字一致 |
| P1-5 | **真实面回归**：用 [读数](tool-face-p0-readings-2026-10-03/00-读数.md) 的历史 face 跑 before/after，报「丢弃把数」与「丢掉的工具里有多少真实被用过」的对比 | 数字要往好的方向走；不走就是没改对 |

P1-5 是唯一一条**能证明收益**的判据——前四条只证「没变坏」。它之所以可做，正是因为 P0 已经把读数面建起来了。

**回滚**：排序是一处纯函数调用。关掉它 ⇒ 逐字节回到今天，`MS1–MS6` 不变，P0 的 `surface_account` 不受影响。

## 8. 不做什么

- **不放宽 MS3**。任何「中间摘」方案（包括按效用挑着丢）都不做——§1.1 已量化其代价。

- **不顺手做 B 或 C（渐进式披露）**。它们各有自己的机制与评审。
