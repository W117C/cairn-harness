## 0. 三条前提（先说清楚，否则计划会跑偏）

**① 这个仓库的"完成"有明确定义，不是"代码写完"。**
它的验收文化是：**先量基线 → 再改 → 再用真模型/真命令实测对比 → 全量判卷 + 门禁全绿**，
且**关键机制必须配"反向验证"**（把机制拆掉，对应判卷必须变红）。本仓库自己点过账：
86 笔提交跑在红灯上——所以每笔必须贴**实际命令输出**，光说"做完了"不算。

**② 这个仓库正在被多个会话同时改。**
本计划成文时：**94 棵工作树、11 个分支、296 条 `outputs/` 取料**。
我这一轮亲身踩到：21 小时不动，合并冲突从 5 处涨到 13 处；期间另一个会话独立修了同一个
hook 超时问题，导致我的修法变成"同一问题两套机制"（已撤）。⇒ **第 5 节的协作协议不是形式主义。**

**③ 有三件事不要做**（仓库硬规矩，违反算失败）：
- 不重新引入 Electron / `src/renderer/` / `src/preload/`（本树 core-only 是明确决定）
- 不改冻结判卷与冻结夹具（`scripts/frozen-sha256.json` 覆盖的那些）
- **不放宽断言**来换绿（跳过 / 恒真 / 删用例 / `|| true` 都算）；测试总数只能增

## 2. 模块划分原则（为什么这样切）

三条原则，按重要性排：

1. **按目录切写范围，不按能力切。** 冲突的根源是"两个 agent 改同一个文件"，不是"两个 agent 做两件事"。
   所以每个模块的写范围是**目录前缀**，且两两不交。
2. **把"共享热文件"抽出来单独管。** `src/cli.ts`、`src/main/agent-runner.ts`、`src/main/settings.ts`、
   `scripts/gate-manifest.ts`、`PROGRESS.md`、`package.json` 几乎每个模块都要碰。
   规则：**模块只贡献"纯函数模块 + 一行接线"，接线由该波的集成 owner 统一做**（见 §5.2）。
3. **度量先于改动。** 没有读数，"我优化了"无法证伪——这一轮我自己就因为缺读数，
   把单次成功率当结论过一次。所以 **M0 先落地**，它不产出能力，产出**判断能力有没有变好的尺**。

## 4. 模块任务书（整段贴给执行者）

> 每份任务书都能独立执行。格式统一：**目标 / 现状 / 差距 / 交付物 / 写范围 / 验收 / 反向验证 / 禁区**。

### M0 · 度量与基准底座

**目标**：让"这个 agent 到底行不行"变成**可复现的数字**，而不是感觉。
这是唯一一个**不产出能力、却决定其他模块能否证明自己**的模块。

**现状（实测）**
- 有靶场与 SWE-bench 形态解析器（`src/agent/eval/task-set.ts`）；有 `scripts/loop-eval.ts`。
- 有 `pnpm bench`（3 条自包含任务）与 `pnpm prompt-cost`（每轮固定开销）。
- **没有一次真模型外部基准读数**——仓库自己如实登记「凭据不在，保持没有尺」。

**差距**
1. 只有 3 条任务，且**只够冒烟**（分支自己声明过）→ 不足以判断改动效果。
2. 没有"改动前后同一批任务的成功率/耗时/token 分布"这种**可比对**的读数。
3. 资源占用（CPU/内存）已能落盘，但没有**跨会话汇总**。

**交付物**
- `fixtures/bench/tasks.json` 扩到 **≥12 条**，覆盖四类：跨文件 bug 修复 / 加功能 / 重构改调用点 / 长任务（≥20 轮）。
- `scripts/eval/report.ts`（新）：读 `outputs/*/readings.json`，出**对照表**（两次运行的成功率/token/耗时/内存差）。
- `fixtures/bench/README.md`：写清每条任务考什么、种子为何是红的。

**写范围**：`scripts/eval/`、`fixtures/bench/`、`scripts/bench/`、`outputs/eval-*`。
**不要改** `scripts/loop-eval.ts` 的核心跑法（它是既有尺，改了就没法横比）——需要扩展就走新文件。

**验收（硬指标）**
1. `pnpm bench -- --reps 3` 能跑完 12 条 ×3 轮，输出成功率 + token + 耗时 + 内存峰。
2. `scripts/eval/report.ts` 对两份 readings 能算出差值与**是否超出噪声带**（同一配置跑两次的差 = 噪声带）。
3. 每条新任务的**种子必须开跑即红**（贴出 `node --test` 的 pass/fail 计数）。

**反向验证**：把 report 的"噪声带"判定强行改成永真 → 必须有一条判卷变红。

**禁区**：不联网跑基准（用 `--provider demo` 或明确标注"需凭据"）；不改既有 3 条任务的语义。

### M2 · 精确编辑

**目标**：补上"**补丁级输入**"这条主流通路，让改动更小、更少返工。

**现状**：`edit_file` 按 `old_string` 精确替换（非重写整文件），0 匹配时给"最像的位置"；
有改动行数读数（`line-delta.ts`）；有写前快照；有写后 LSP 诊断。

**差距（核实后的准确说法）**：**没有 `apply_patch` 式统一 diff 输入工具**。
证据：`apply_patch` 这个名字在 `src/` 里**只出现两次**——
`src/agent/no-progress.ts:22` 的 `WRITE_TOOLS` 集合里（与 `delete_file` / `move_file` 并列），
以及 `src/agent/write-face.ts:7` 转述它。也就是说：**写向判据已经把这三个名字"预支"了，
但工具本身一个都不存在**（`ls src/tools/` 无 patch 相关文件）。

**交付物**
- `src/tools/apply_patch.ts`（新）：接受统一 diff 文本，逐 hunk 应用；
  失败给**逐 hunk 归因**（上下文不匹配在第几行、期望 vs 实际），不是一句"失败"。
- 注册进 `src/tools/index.ts` 的 `TOOLS`，并在 `src/agent/tool-surface.ts` 登记写向。
- `tests/apply-patch.test.ts`：正常应用 / 上下文漂移 / 部分 hunk 失败 / 空补丁 / 二进制拒。

**写范围**：`src/tools/apply_patch.ts`、`src/tools/edit_file.ts`、`src/tools/line-delta.ts`、
`src/tools/write-face.ts`、`tests/apply-patch.test.ts`。
**接线**（`src/tools/index.ts`、`tool-surface.ts`）交给集成 owner。

**验收**：新工具能应用 ≥3 段 hunk 的补丁且**行数读数与 `git diff --stat` 一致**；
上下文漂移时返回可操作的错误（含行号与期望/实际片段）；全量判卷绿。

**反向验证**：把 hunk 上下文校验摘掉 → "上下文漂移"那条判卷必须红。

**禁区**：不许把 `edit_file` 的既有语义改掉（它是既证判卷的被测对象）。

### M4 · 长程规划与长任务

**目标**：让"**跑很久的任务**"真的能跑完、不遗忘、不卡死。

**现状**：目标模式真能续跑（`--goal` + `--max-turns` + `--max-usd`，停止理由落事件流且终端可见）；

**差距（审计实测，最醒目的一条）**：**定时任务调度器没人启动**——
`initScheduler` 定义在 `agent-runner.ts:1024`，**全树零调用者**；
CLI 上那五把 `automation_*` 工具规格面与执行面一起摘掉了。
也就是说「长任务按点自动跑」**只有实现、没有在产入口**。

**交付物**

**写范围**：`src/agent/goal*.ts`、`src/main/scheduler.ts`、`src/agent/orchestrator*.ts`、`src/agent/recovery.ts`。

**验收**：调度器有生产调用者且**有判卷钉住**（摘掉调用 → 判卷红）；

所以本模块的默认动作是"不动"，只在有实测证据的地方加固。**

**现状（审计：已实现，且是全项目最强）**
- `autoVerify` 默认开：写过盘没自测 → 收束前 harness **自动补一拍**。
- 同轮修复：verify 失败把原文注回**同一轮**继续修，连败 3 拍收束。
- **归因分类**：timeout / not-run / 127 工具链缺失 / pnpm 自身错误 / 代码红**五类分开**，
  **环境红不占模型的修复额度**——直接防"模型照着假红改本来正确的代码"。
- 本轮已修：verify 假红（harness 无条件把靶子的 `pnpm test` 换成自己的 vitest）。

**差距**
1. 只有"跑测试"这一种验证面；**没有静态分析/lint/类型检查的统一收口**（靠 `.agent/config.json` 手配）。
2. 验证**只在收束前补一拍**；长任务中途没有周期性自检。
3. `verify` 的失败分类没有**回归跟踪**（同一个错误反复出现时没有升级处置）。

**交付物**
- `src/agent/verify.ts` 扩：验证面**自动探测**（存在 `tsconfig` 就能跑 typecheck、有 lint 配置就跑 lint），
  **一条命令产出多面结果**，仍保持五类归因。
- 「同一错误重复 N 次」→ 升级处置（换策略/换路径提示），配判卷。
- 新增 `tests/verify-multiface.test.ts`。

**写范围**：`src/agent/verify.ts`、`src/agent/loop.ts`（**仅验证相关块**，改前先与集成 owner 对齐）。

**验收**：多面验证在真实靶子上跑通（贴命令与输出）；五类归因**一条不丢**（反向验证逐类拆）；
全量绿。

**反向验证**：这是本模块的**核心要求**——对每一类归因，构造一个"环境红"和一个"代码红"，
断言分类正确且环境红**不消耗**修复额度。

**禁区**：**不许削弱既有验证**（不许把 autoVerify 改默认关、不许减少归因类别）。

### M6 · 记忆与跨会话学习

**目标**：让"**上次踩过的坑不再踩**"。

**现状**：两层记忆（项目层 `.agent/*.md` + 全局 `memory/`），按 6K token 预算每轮回注；
会话末自动沉淀；代码库约定与历史决策能记住。

**差距**：**跨会话"从失败轨迹学习"没有成型机制**——
失败留在事件流里，没有被提炼成"下次别这么做"的规则。

**交付物**
- `src/agent/memory/lessons.ts`（新）：从**失败轨迹**（verify 红 / 工具连败 / 重复同一动作）提炼
  可复用条目，写进项目记忆；**必须带"证据指针"**（哪条会话、哪个 callId），不许凭空总结。
- 回注时**限量且可解释**（为什么这条被注入；命中率可观测）。
- `tests/memory-lessons.test.ts`：从一段人造失败轨迹提炼出条目；**无证据时不产出**。

**写范围**：`src/agent/memory/`。

**验收**：提炼出的条目**能追到原始事件**；注入预算不超既有上限；
跑一条真任务，第二次同类失败率**有读数**（贴对比）。

**反向验证**：把"必须有证据指针"的校验摘掉 → 对应判卷红。

### M7 · 安全与权限（**小而高价值，优先做**）

**目标**：把一处**方向反了的默认值**翻回来，并补上"新工具漏登记"的兜底。

**现状（我自己复现过，不是照抄审计）**

```
read-only + write_file      => deny
read-only + ghost_tool      => allow   ← 不存在的工具名反而放行
read-only + automation_create => allow
```

同一个函数里：「未知**档位** → 取问」（保守，`index.ts:108-110`）
与「未知**工具** → 放行」（激进，`index.ts:106`）**方向相反**。

**缺口与风险（说清楚，不夸大）**
- **当前没有可利用的洞**：CLI 会话实际可达的 **18 个工具名**
  （9 静态 + 14 注入 − 5 定时工具，定时那五把在 CLI 上规格面与执行面一起摘掉了）逐个核对过，
  该摘的都摘了；`web_fetch` 是有意保留的。
- **但默认方向是开的**：以后新增工具族若忘了登记 `SIDE_EFFECT_TOOLS`，就会**静默绕过写禁**。
- 已有三道防线（`tests/tool-surface-parity.test.ts`：写向漂移、只读档摘除面、源文本注入名必须登记），
  **抓得住"已声明的注入工具"漂移，抓不住一个全新工具族**。

**交付物**
- 立一份**权威的只读工具白名单**（可从 `TOOLS` + `INJECTED_TOOLS` 派生，不要手抄第二份）。
- 把 `checkPermission` 的第一行翻成**白名单外一律问**（非交互时由 `gate()` 降成 deny）。
- **必须先决定**：动态注入的 MCP / 插件工具怎么归类（用 server 注解？默认问？）——
  这个决定要写进文档，并配判卷。

**写范围**：`src/permissions/`、`tests/permission-*.test.ts`。

**验收**：
1. `ghost_tool` 在只读档**不再 allow**；
2. **18 个既有工具的行为一条不变**（逐个列表对比，贴输出）；
3. MCP 工具按新规则有明确去向；
4. 全量绿（这是重点：改错会让正常读操作在非交互下被拒，**比现在更糟**）。

**反向验证**：白名单故意漏掉一个只读工具 → 必须有判卷红（否则白名单本身就是新的 fail-open）。

**禁区**：**不许顺手扩大改动面**（这块是全仓最敏感的地方，小步 + 判卷）。

### M8 · 人机协作

**目标**：在没有 UI 的前提下，把"**人能审查、能接管**"做到最好。

**现状**：能澄清歧义、能提交方案等批准、能给 worker diff（整块文本）、能在轮界取消。

**差距（审计）**：core-only 无 UI ⇒ 审批是 `[y/n]`、diff 是整块文本、**没有行内批注/接受部分改动**；
`forkSession`（从事件流分叉重跑）在 `src/` 里**唯一调用者是 gym**，**CLI 没有 fork/replay 命令**。

**交付物**
- `m0 --fork <会话> --from <轮次>`：从任意一轮分叉重跑（事件溯源本来就支持，缺的是**入口**）。
- `m0 --replay <会话>`：重放看决策链（调试"它当时为什么这么干"）。
- diff 审查增强：把 worker diff 输出成**可逐文件接受/拒绝**的交互流程（终端多选，不依赖 UI）。
- `tests/cli-fork-replay.test.ts`。

**写范围**：`src/agent/fork*.ts`、`src/main/ask-gate.ts`、`tests/cli-fork-replay.test.ts`。
**`src/cli.ts` 的接线交给集成 owner。**

**验收**：fork 出的会话**事件流可独立重放**且原会话不受影响（贴两份日志对比）；
中断（Ctrl-C）后事件流**完整可续**；全量绿。

**反向验证**：把 fork 的"新会话 id"改成复用原 id → 判卷必须红（否则分叉会污染原历史）。

### M9 · 工程化与集成

**目标**：把"31 道门全靠人记得跑"这件事，变成**有自动兜底**。

**现状（审计实测）**：`.github/` **不存在**；`.git/hooks/post-checkout` 与 `post-commit` 都是
**只有一行 `#!/bin/sh` 的空壳**；没有 husky / lint-staged；`core.hooksPath` 未设置。
而门禁里 `head-cert-check` 实测 **123.7s**、`mutate-verify` **18–25 分钟**。
仓库自己的注释承认：**86 笔提交跑在红灯上**。

**差距**：质量**没有任何自动保险丝**。

**交付物（分档，按代价选）**
- **L1（必做，零打扰）**：`.github/workflows/verify.yml` —— `typecheck` + 全量判卷 + 轻门。

- **L2（可选，需要你先拍板）**：`pre-commit` 只跑 `typecheck`（约 5 秒）。

**写范围**：`.github/`（新）、`scripts/ci/`（新）、`scripts/ci/*.ts`。

**验收**：CI 配置**语法可校验**（本地用同一组命令跑一遍，贴输出）；
**不新增本地阻塞**（L2 若做，必须可一键关闭）。

**反向验证**：故意提交一处类型错误 → CI 配置能抓到（本地用同样命令证）。

**禁区**：**不要在本地加会拖慢每次提交的钩子**，除非业主明确同意（会伤到并行会话）。

**写范围**：`src/agent/no-progress.ts`、`src/agent/cost-per-progress.ts`、
`src/agent/model-surface.ts`、新抽出的纯函数模块。

**验收**：`no-progress` 有生产调用者且有判卷钉住；拆分后**行数与扇入读数**改善且全量绿；

## 5. 并行协作协议（**这一节决定会不会互相踩**）

### 5.1 写范围隔离（硬规矩）

1. **一个模块只在自己的目录前缀里写。** 越界修改算失败（本仓已有此惯例）。
2. **共享热文件**（`src/cli.ts`、`src/main/agent-runner.ts`、`src/main/settings.ts`、
   `scripts/gate-manifest.ts`、`PROGRESS.md`、`package.json`、`README.md`）
   **每波只允许一个 owner 写**，其他人**只提交"一行接线请求"**（写进自己的 output 目录，由 owner 落地）。
3. **`PROGRESS.md` 是最大的串行点**（9,736 行，被 **393 笔**提交改过）。
   建议：非 owner 把台账条目写在自己的 `outputs/<模块>-*/LEDGER.md`，由 owner 合并。
   （若想改成 `PROGRESS.d/<波次>.md` 分片，那是**门禁改动**，需单独排期。）

### 5.2 集成 owner 轮值

每一波指定**一个**集成 owner，负责：共享热文件的接线、`settings` 登记、`gate-manifest` 加门、
`PROGRESS.md` 合并、把当波产物并进主分支。**当波其他人不碰这些文件。**

> 这是我这轮血的教训：我并 port2 时，另一个会话同时在改同一个测试文件，
> 结果我的修法作废、还要额外撤一次重复机制。**没有 owner 就会反复发生。**

### 5.3 分支与合并节奏

- 每个模块**一条分支**，命名 `feat/<模块>-<短描述>`。
- **合并由集成 owner（或业主）做，不由模块作者自己并**——避免"我并我自己"跳过审查。
- **至少每天合并一次**：本轮的实测数据是，21 小时不合并，冲突从 5 处涨到 13 处。
- 合并前**必须**：`typecheck` + 全量判卷 + 当波相关门禁全绿，且**贴实际输出**。

### 5.4 每笔提交的固定动作（本仓惯例，照做）

1. 先量基线（改之前先跑一次，把读数记下来）
2. 改
3. 真命令实测对比（改前 vs 改后）
4. `node --import tsx scripts/typecheck.ts`
5. `node node_modules/vitest/vitest.mjs run --config tests/vitest.config.ts`
6. 相关门禁（`node --import tsx scripts/gates.ts --only=<本模块的门>`）
7. **反向验证**（关键机制必须能被"拆掉后判卷变红"证明）
8. 证据落 `outputs/<模块>-<日期>/`，台账写一行
9. 提交（一笔一事，提交信息里带实测读数与局限）
