## 二、外部读数（为什么主判据是 F2P，不是数 TODO）

**FeatBench**（arXiv 2509.22237，真实仓库的"加功能"评测）：

- **Patch Apply Rate 100% ⇄ Feature Validation Pass Rate 平均 41.72%**（§3.3）：
  补丁"能打上"与"功能成立"之间差 58 个百分点——**这正是 G1/G2 那个洞的规模**。
  最好的一组模型配置解题率上限也只有 **29.94%**。
- 机制：跑 **Fail-to-Pass（F2P）** 确认新功能真的把测试从红推到绿，
  跑 **Pass-to-Pass（P2P）** 抓被改坏的旧逻辑（§2.1、§2.3）；
  平均每题配 **1657.53** 条用例（§2.2），作者主张靠密集自动执行而非人工 review。
- ⚠️ **作者明说：这套评测里没有 stub 计数、也没有人工判"实现是否真做了"**。
  ⇒ 这条读数直接决定本页取向：**结构信号（TODO/空体）只配当提示，判定面交给 F2P/P2P 的集合比对**。
- 另参：`What Breaks When LLMs Code?`（arXiv 2605.30777，运维安全刻画）与
  `Why Do Multi-Agent LLM Systems Fail?`（2503.13657）把"看似完成"列为反复出现的失效类——
  两者都不给检测算法，故不作为判据依据。
- 本仓自己的读数补一刀：`01` §四——**"空函数体"宽正则在本仓 `src` 命中 48 处**（空 catch / 空回调 / 接口声明），
  而 `TODO/FIXME` 在 `src` 命中 **0** 处。⇒ 宽结构判据**在本仓自己身上就是假红制造机**，
  只能作用域收窄到"本次新增行"，且只作提示。

## 三、设计：四层，按依赖排（各答「长在哪 · 谁持有 · 为何不是别层」）

### L0 摘要解析（**前置，且顺带修缺陷 D1**）

`src/agent/verify.ts` 侧新增纯函数 `parseTestSummary(output) → { pass, fail, skipped, cases: string[] }`：
按 runner 族取表（`node --test` 的 `# pass/# fail/# skipped`、vitest 的 `Tests N passed`、
jest、pytest 的 `N passed`），**取数不取值**——`# fail 0` 必须是"零失败"，不是"有 fail 字样"。

- **长在哪**：验证面（`verify.ts` / `events` 契约），**不是** `evidence.ts`。
  `hasFailureSignal` 那套关键词属于**证据摘要**（决定"给模型看哪几行"），
  语义是"有没有可疑文本"，与"跑了几条测试通过"是两回事——**今天它被同时当两件事用**，
  这就是 D1 能发生的根因（`01` §二：status=failure 而 exit 0）。
- D1 的修法按本仓既有口径写成**合取判据**：`# fail 0` 不得判失败 **且** `# fail 2` 必须判失败 **且**
  中英两表都要有（`FAIL_RE` 本来就中英并收）。三侧各测各的会漏中间。

### L1 基线快照 + F2P/P2P 比对（本页主论）

一次任务内在**首次写盘前**取一次基线通过集，收束时再取一次，比对出
`{ newlyPassing, newlyFailing, stillFailing, newlySkipped }`（按用例 id 集合，非计数）。

- **长在哪**：run 生命周期，与能力 16 的 `SeenLedger`、17 的 `effect` 同一层（`agent-runner` 构造 → loop 透传）。
- **成本要算清**：多一拍测试。**不是**多一拍模型请求——
  `outputs/auto-verify-readout-2026-09-20.md` 已实测自动验证拍"几百毫秒、零额外模型请求"，
  本页加的是同数量级的第二拍。⚠️ 但**套件很大时基线拍是主要新成本**，
  必须允许"无测试面就整段跳过"（沿用 `verify.surface?()` 那条既有探测），
  并**绝不为省这一拍去猜**（本仓忌的"拿没量的东西判人"）。
- **为何不是别的层**：不做成 `edit_file` 的即时回执（单次写入看不见"哪些用例因此变绿"），
  也不做成门禁脚本（脚本在收口才跑，绿早吞了）。与 18 同一个理由。

### L2 与 18 共用聚合器，收束闸加第三条判据

`verify_result` 上并排两个读数：`gradingDelta`（18：考卷变薄）与 `evidenceDelta`（21：绿有没有增量）。
能力 5 收束闸从「写过盘且没 verify」扩成
**「写过盘且（没 verify ∨ 绿是变薄来的 ∨ 绿没有任何 newlyPassing）」** ⇒ 后两种标 `thinned` / `unbacked`，**不并入干净绿**。

- **`unbacked` 只出声、不拦**：修 bug 类任务常常只让原本红的用例变绿、也可能只是不再报错；
  掏空场景才是"什么都没变绿却说完成了"。分清真绿与假绿需要靶场数（§`01` 五），
  与 16/17/18 同口径：**先 detection，enforcement 等数**。

### L3 结构弱提示 + 死字段处置

- 弱提示：只在**本次新增/替换行**上判 `TODO 新增行` / `返回值从有值改成 null/undefined` / `抛 NotImplemented` / `函数体语句数为 0`，
  **仅追加一行文案**，不进判定、不进门（理由见 §二末的 48 处实证）。
- **D2 需要用户裁决（不偷做）**：`uncertain` 要么**删掉**（本仓规矩：不留没有生产者的字段），
  要么**接上真生产者**——但接给谁？它语义是"**证据**不确定"，
  **不该**拿来装"实现不确定"（那是 L1 的 `unbacked`）。二者混一格 = 造一个说不清读数的字段。
  建议：**删**，把"不确定"表达在 `evidenceDelta` 上。此项单独一笔，不夹在别的能力里。

## 五、明确不采纳（理由 / 证据 / 反转条件）

| 不采纳 | 理由 | 反转条件 |
|---|---|---|
| 用 stub/TODO 计数当**判定面** | 本仓实测：宽正则 `src` 命中 48 处误报；FeatBench 作者明确不采用 stub 计数；`TODO` 是合法自我声明 | 反转：真语料里"掏空且无 F2P 信号"的样本 ≥ 每格 100（届时它才配得上判定） |
| 证明"实现语义完整" | 不可判定；能判的是"有没有用例因此变绿"与"函数体有没有语句" | 永不 |
| 让 LLM 判"这次是不是真做了" | 自报置信度是已点名的反模式（`gap-fix` P2-5）；且加一次模型请求违背"消耗 token 最少" | 反转：判别器与被审模型不同源 + 有靶场数 |
| 每次写盘后跑全量测试 | 成本失控；本页只在**首次写前**与**收束时**各一拍 | 无 |
| 把 `uncertain` 复用成"实现不确定" | 语义是"证据不确定"，混用会造出一个没人读得懂的字段 | 反转：先重写 schema 语义并走裁决 |
| 另建一套 21 专属聚合器 | 与 18 是同一层同一形状，两份迟早漂移（本仓为这名字立过规矩） | 无 |
| 现在就把 `unbacked` 设成硬拦 | 真绿与假绿的本地分母还没有（`01` §五） | 长出计数后再议 |
