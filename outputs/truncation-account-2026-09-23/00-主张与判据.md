# 能力 31：截断账（丢了多少得是个字段，而且那个数得是真的）

一句话：**本仓把"截断要如实标注"做得比多数实现好，但那个"如实"只活在正文里，而且它在中文下是假的。**
`createOutputRing` 用 UTF-16 字符数执行一个名叫 `BYTES` 的帽 ⇒ 同一份代码，
ASCII 守住上限、**中文把 8KB 帽撑到 23,952B（破 2.9×）**，而提示行仍报"省略中间 8064 字节"（真实 24,048B，**少报 3.0×**）。

## 一、空位核对（这已是本程序第八次"以为空白"）

| 看着像空白的地方 | 实测已有 | 还缺什么 |
| --- | --- | --- |
| 截断要不要告诉模型？ | **告诉，而且分型**：`truncationNotice`（只留头）、`middleTruncationNotice`（留头尾＋如实报省略量）、`read_file` 四路提示（大文件前缀 / 50KB / 行截断 `…[行截断]` / `[offset: …]`），产出提示的文件 12 个 | 提示是**散文** |
| 提示行自己占的预算 | `NOTICE_RESERVE_BYTES = 256`，注释原话：不给它留位就会把「输出 ≤ 上限」这句承诺撑破，且**已经为 UTF-8 字节实测红过一次** | 那次修的是"预留位"，**没修"长度用什么单位量"** |
| 结构化信号该不该进 `ToolResult` | 有先例且理由写得很清：`exitCode?` 的注释——「结构化信号在 settle 时被丢掉 ⇒ 任何想区分…的读者只能去匹配文案」；同批还有 `snapshotId?`、`timedOut?` | **截断没有这一格**：实测 `ToolResult` 字段只有 `ok, output, snapshotId?, exitCode?, timedOut?`；仓里的 `omittedBytes` 只是 `middleTruncationNotice` 的**形参名**（数到形参不等于有字段——同 21 页把类型声明数成生产者的那次） |
| 头+尾环的保留策略 | 对的，且注释解释了为什么（结论在尾部，只留头等于把结论丢在源头） | 本页**不碰策略**，只碰计量单位与字段 |

⇒ 结论的形状与合册 §四 的 A 类（事实缺字段）＋一句新的：**已有正确做法的字段化先例就在同一个接口里**，
施工不需要新发明，只需要照 `exitCode` 那一次再做一遍。

## 二、机制：一只 ring，三个消费者，一个单位错

`src/tools/output-ring.ts` 的三处长度判据全部是字符数：`out.length > limitBytes`、`seen += s.length`、
`tail.length > tailBytes`；而 `SHELL_OUTPUT_LIMIT = 32 * 1024`、`NOTICE_RESERVE_BYTES`、
`middleTruncationNotice(omittedBytes)` 与文案「省略中间 N 字节」都叫字节。
ASCII 下两者恒等 ⇒ 这个错**永远不会在英文测试里露馅**；中文（每字 3 字节）下同时坏两件事：

1. **帽被撑破**：`keepBytes` 按"字符"留，输出字节数 ≈ 3× ⇒ 实测 8,192 的上限产出 23,952 字节；
2. **省略量少报 3×**：`seen - headBytes - tail.length` 混合了字符数与字节预算，报 8064 而真实是 24048。

消费者实测四个文件（`tools/run_shell.ts`、`agent/verify.ts`、`main/sandbox.ts`、ring 自身），
且 `run_shell` 与 `verify` 共用是**刻意的**（文件头注释：两处各写一份时修好一处另一处仍是旧的）。
所以这一只 ring 的错误同时进**执行路径**与**验证路径**——后者正是判卷面。

## 三、判据总则

硬事实（可跑谓词）与规模读数分开；规模读数样本不足时**不得**当判据主面（④ 就是这种）。

## 五、已证 / 未证（分列）

**已证**（真函数、真语料，`TERM=dumb node --import tsx measure-truncation.mts`，两次 `diff -q` 逐字一致）：
C1 的两个倍数（2.9× / 3.0×）、ASCII 对照组守住；C2 的字段清单；C3 的消费者清单；
④ 的 4/284 与 1 回补 / 3 未回补。
另记一条**自我纠正**：① 第一版把"全仓 grep 到 `omittedBytes`"当成了"有字段"，
实际命中的是 `middleTruncationNotice(omittedBytes: number)` 的形参位 ⇒ 判据改成"只看 `ToolResult` 块内"才成立。

**未证 / unmeasurable**：
- ~~`read_file` 的字节前缀路径（`LARGE_FILE_PREFIX_BYTES`）是否也有同类单位混用~~ **本轮已测，读数为否定**：
  该常量是 16 MB，走 `Buffer.byteLength`，中英两语种都守住帽（详见 `01` 追加节）。
  ⇒ ② 的单位错是 `output-ring` 独有，不是全仓通病。留一条尾巴：本测的返回被更靠前的行帽截断，
  所以只否定了"撑破帽"，未否定"前缀分支内省略量算得准不准"。
- 真实分布里中文输出的占比 ⇒ "破 2.9×" 是**构造最坏情形**（纯中文块），不是均值；
  混合文本的实际倍数介于 1× 与 3× 之间，未测。
- C4 的"未回补 = 有害"未证：不回补可能确实不需要（截掉的正是无关中段）。这条只能当线索。
- 帽撑破对**总上下文预算**的净影响未测（要看 provider 侧是按字符还是按 token 记）。

## 六、最小施工

1. `output-ring.ts` 内所有长度判据统一改 `Buffer.byteLength(...)`（一次改，三处消费者同时受益）；
   截断点必须落在 UTF-8 安全边界（`read_file` 已有做法可借）。
2. `ToolResult` 加 `truncated?` 对象（缺省缺席 = 零行为，照 `exitCode?`/`timedOut?` 的加法），
   数字一律字节；正文里那句 `middleTruncationNotice` **继续留着**——它给模型看，字段给判定层看，
   两面都要（同 D7 快照那句"同一个事实有两个读者"）。
3. 一只断言钉住单位：`createOutputRing(limit)` 的输出**字节数** ≤ limit（今天是红的，改完即绿），
   再加一条中文样本，防英文测试恒绿。

## 七、需要裁决才动的点

- **W-31a**：`truncated` 的粒度——只报"省略多少"，还是也报"头尾各留多少 + 上限"（后者才能让人判断被砍的是不是结论段）。
- **W-31b**：32KB 帽在中文语境要不要下调（守字节就意味着守不住原来的"字符观感"，二者会互相牵动上下文预算那条线）。
- **W-31c**：`verify` 的判卷摘要是否改用结构化截断（它是最需要尾部的一段，口径错会连累判卷读数）。
