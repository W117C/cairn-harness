## 二、注入位置：轮次边界合法，调用与结果之间是禁形状（真 `projectContext`）

同一条插话「等一下，只改 shipping.js，别碰 cart」，放两个位置：

```
[轮次边界（结果已全部落流之后）]
   投影序列：user → assistant[calls] → assistant → tool → user
   id 配对：孤儿 0 / 悬空 0 ⇒ 过；插话是否落在「调用与其结果之间」：否

[调用与它的结果之间]
   投影序列：user → assistant[calls] → user → tool
   id 配对：孤儿 0 / 悬空 0 ⇒ 过；插话是否落在「调用与其结果之间」：是（这就是要禁的形状）
```

三条读数：

1. **两种位置都通过 id 配对**（无孤儿、无悬空）⇒ **只按 id 配对判是漏的**。
   这条**反喂给能力 20**：那个出口收束器必须加"邻接"这一维，
   否则转向一上线，它就看不见 `assistant[calls] → user → tool` 这种破口。
2. 真正可判的形状是「一条非 tool 消息被塞在 `assistant[calls]` 与它的结果之间」。
   ⇒ **"只能在轮次边界注入"不是洁癖，是 provider 的合法性要求**，
   与本仓 `context.ts` 注释自己写的「带 tool_calls 的 assistant 之后必须紧跟覆盖这些 id 的 tool 消息」同口径。
3. ⚠️ 顺手量到一条**与插话无关的既有形状**：本仓正常投影在 `assistant[calls]` 与它的 `tool` 结果之间
   **本来就会夹一条 assistant 文本行**（第一例序列里的 `assistant[calls] → assistant → tool`）。
   各 provider 是否接受这种非紧邻排列，**本页未证**——留给能力 20 复核（我第一版的邻接判据太严，
   把这条既有形状也算成"破"，因此上面的判据已收窄到只认"插话落进中间"）。

## 三、硬前置：无进展检测器看不见"用户改过口"（真函数实测，预测成立）

用**真** `verifyBeatsFromEvents` + `detectVerifyStagnation`（能力 14 的 R1）跑三组：

```
[无插话（用户没说任何话）]   beats=2  wroteSinceLast=false,false ⇒ stagnant=true（repeats=2）
[中间用户改了口]             beats=2  wroteSinceLast=false,false ⇒ stagnant=true（repeats=2）
[对照·中间有成功写]          beats=2  wroteSinceLast=false,true  ⇒ stagnant=false
```

⇒ **用户改口对判定毫无影响**：唯一的抑制信号是"中间有没有成功的写"。
所以转向一旦上线，"按新指示重试同一条红"会被 R1 判成停滞，`noProgressLadder` 随即出声/升级。

这不是"以后要注意"，是**上线顺序上的硬前置**——因为该模块自己在文件头写着：
把**前进**误判成**停滞**是"这条判据最贵的错法"（门里 NP5 钉着同类），
而它的 `VerifyBeat.wroteSinceLast` 注释把自己的语义说得很清楚：
"上一次 verify 到现在有没有成功的写动作。R1 的头号抑制条件"。
**用户说了一句新话，在它眼里等于什么都没发生。**

顺带引出一条语义问题（需裁决，见 `00` §三 L3）：转向之后，能力 5 收束闸的
`wroteThisRun` 该不该复位——新指示构成新任务段，拿上一段的"写过盘没验"来判这一段并不对。
