## 二、`collectChangeSet` 的真实形状（跑出来，不是读注释）

输入：同一路径 `x.ts` 依次「写 → 改 → 写」。

```
条目: path=x.ts op=write lines=[L1 | L2 | FINAL-ONLY]
条目: path=x.ts op=edit  lines=[E1]
```

两条读数，都是缺陷候选：

1. **分组键是 `op + path`** ⇒ 同一个文件上"先 write 再 edit"被切成**两条**，
   一次真实意图在数据里根本不是一条。
2. **`lines` 是拼接，不是最终态**：最后一次 `write` 已经把整份内容换成 `FINAL-ONLY`，
   但 `L1/L2` 仍在条目里。而函数注释写的是「同 (op,path) 重复写入按序拼接，**最终态可见**」——
   拼接的结果里"最终态"确实看得见，但**也混着已被覆盖掉的行**。
   ⇒ 后果要看清：`scanChangeSet` 的 finding 行号是**条目内相对**（该文件注释自己写的），
   所以一条指向"已不存在的行"的发现是可能出现的。
   **这条我没有证据说它已经造成误报**（本轮只证形状，不证后果），故按 D-24a 交裁，见 `00` §六。

## 三、实弹：半套重构 + **真的各回滚一次**

临时项目两个文件，`def.mjs` 导出 `total`，`call.mjs` 导入它。把定义改名成 `sumTotal`、
调用点还没改（= 一次重构做到一半被打断），此时：

```
跑起来：ok=false :: [exit code: 3]
```

（坏是**测得到**的——这不是本页要问的。）真正的问题是"怎么退回去"。
两次写各留一份 D7 快照（快照默认开）：

```
snapshotId #1： .agent/snapshots/1790164282879--k1/src/def.mjs
snapshotId #2： .agent/snapshots/1790164282880--k2/src/call.mjs
.agent/snapshots/ 下 2 个条目，键是 <毫秒>--<callId>
```

两个目录**互不相干**，没有任何字段说「这两次写是同一件事的一半」。
于是我**真的各回滚了一次**：

```
回滚第一个快照（def.mjs 的原版）→ 跑得通（ok=true）
回滚第二个快照（call.mjs 的原版）→ 仍坏：[exit code: 3]
```

⇒ **只有回滚 A 修得好**；而"该回滚哪个"这条信息不在任何读数里——
它就在"这两次写属于同一次未完成的意图"这句话里，**而那个单元今天在本仓不存在**。
D7 给的是**每个文件自己的退路**，半套重构需要的是**这一组的退路**。

顺带在真实读数里再确认一次：`snapshotId` 里带着毫秒（`1790164282879`）——
这正是 `BLOCKED.md` #56 未裁的那件事（毫秒进 id ⇒ 破坏确定性），本页不重复裁，只记它出现在哪。

## 四、已证 / 未证

**已证**
- 多文件会话占 43%（§一，真语料计数）。
- `collectChangeSet` 按 `op+path` 切条、`lines` 为拼接含被覆盖行（§二，真函数）。
- 半套重构下逐文件回滚**会挑错**，且没有任何读数支持挑对（§三，真的各滚一次）。
- 快照键是 `<毫秒>--<callId>`，与"组"无关（§三）。

**未证 / 待核**
- §二-2 的后果：拼接是否**已经**造成过误报 finding——本轮只证形状，未证后果（交 D-24a）。
- "单元"该由谁切：模型自报（一个 `intent_id` 参数）还是 harness 按边界推。
  自报 = 让被审者自己说；harness 推 = 边界规则可能不合意图。**这是本能力最大的设计风险点**，
  `00` §三 L0 选了"harness 推 + 模型可覆盖"，但**未实弹**，落地前必须证。
- 真实仓库里"一次重构"到底多少文件（语料是 fixture 短跑）。
- 取消发生在**两次写之间**还是**一次写中间**的相对频率（决定这个单元多常被判"开着"）。
- 回滚整组的**代价**：一组 10 个文件时，"全部退回"可能比"继续补完"更糟——两个出口的比例没人量过。
