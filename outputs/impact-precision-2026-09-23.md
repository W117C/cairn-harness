# 影响面的精度实测：19 万条边里只有 20% 由 import 支撑（2026-09-23）

起因不是「慢」，是「慢」把它引到了这台机器上：`outputs/analysis-perf-2026-09-15.md` 的
P1-6 手法②③ / P1-7 说 `buildImpact` 每次编辑全量建图，要加进程内缓存。要裁这句话就得先量一次
真实建图。**量出来的第一条不是耗时，是这张图在说谎。**

对象：本仓 HEAD `5a9e542`，图 = 400 个受支持后缀源码（帽 400），宿主 ZEdeMacBook-Pro，
`node 22.23.2`（直接 `node --import tsx`，非 pnpm 那条 Electron-as-node 支路）。

## 二、根因：抽取判据把「同名」当成了「相连」

`src/agent/map/parse.ts` 的 `PATTERNS`（23 条，def 侧 0–12 / ref 侧 13–21）逐条跑一遍归因
（每条 pattern 单独编译、在同一棵已解析树上跑，捕获数按编号归因；复刻的 v0 边数 194,292
与线上逐字相等 ⇒ 归因表可信）：

| 侧 | pattern | 捕获数 | 其中非模块作用域 |
| --- | --- | --- | --- |
| def | `variable_declarator name:` | **11,701** | **10,184** |
| def | `function_declaration name:` | 1,666 | 161 |
| def | `method_definition name:` | 392 | 382（类体里，本就应该） |
| def | 其余（class/interface/type/enum/py） | 553 | 12 |
| ref | `call_expression function: (identifier)` | 25,270 | — |
| ref | **`call_expression function: (member_expression property:)`** | **20,519** | — |
| ref | `new_expression constructor: (identifier)` | 1,225 | — |
| ref | 其余（value/assign/属性式 new/py） | 289 | — |

⇒ 全部 14,312 个「定义」里 **71% 是函数体内的局部变量**；全部 47,303 个「引用」里
**43% 是属性名**（`console.log`、`arr.push`、`Object.keys`、`s.slice`）。
名字表不带作用域、引用不看对象，于是任何文件的 `log` 引用会与任何文件的 `log` 定义连一条边。

还有一条更基本的：**这张图从不看 import**。4,803 个 import 绑定名（362 个文件有）里
没有一个被抽进 tags——跨文件连接完全靠撞名字。

## 三、消融：把两种噪声各自去掉，边数与真依赖各怎么变

真依赖（ground truth）取可机械判定的一条：**调用方文件 import 了这个名字，且该名字定义在别的文件**。

| 变体 | 站点级边 | 文件对 | 其中由 import 支撑 | import 链接召回 |
| --- | --- | --- | --- | --- |
| v0 现网 | 194,292 | 5,285 | 38,442（**20%**） | 2,180 / 3,256（67%） |
| v1 = 丢三条属性式 ref | 97,011（−50%） | 3,010 | 38,400（40%） | 2,180 / 3,256（67%） |
| v2 = v1 + 局部变量不计定义 | **49,049（−75%）** | 2,496 | 28,111（**57%**） | 1,936 / 3,005（64%） |

读法与两处必须说清的细节：

1. **v1 一分钱召回不付**：链接召回 2,180/3,256 一字未动。站点级边里少掉 42 条 import 支撑的边
   （38,442→38,400），但那是同一 (文件,符号) 对的第二条站点，对「谁受影响」这个答案没有影响。
   ⇒ 属性式 ref 在这份真依赖判据下**纯噪声**。
2. **v2 撤掉的 244 条覆盖不是真损失**：逐笔查，这 244 对「别处的定义」全部是局部变量。
   样本全是同一个形状——`tests/*.test.ts ← it`：测试文件从 vitest import `it`，
   而图里那条「定义在别处」是某个文件函数体里的 `const it = …`（vitest 自己在 node_modules，被帽与忽略规则挡在图外）。
   分母从 3,256 变 3,005 也是同一件事：这些链接的「定义」本就假。
   ⇒ v2 的召回是 **1,936/3,005 = 64%（对更干净的分母）**，而不是「从 67% 掉到 64%」。

## 四、代价与不做的部分（写下来，别让下一轮重推）

- **命名缺口 ①**：v1 之后 `obj.method()` 形式的方法调用不进图。不是「不重要」，而是
  名字图无法判断 `logger.log()` 的 `log` 属于哪个定义文件；保留它的实测代价是 45,160 条假边。
  要拿回这类边必须先解析 `object` 标识符的绑定（`@obj` 是不是本文件的模块级绑定/import），
  那是另一笔工程，别和这条混着做。
- **命名缺口 ②**：召回 67%（v0/v1）说明还有一类引用压根没抽——只抽了「调用位置」的裸标识符
  （`foo()`），把符号当参数传、作为返回值、放进条件里、`export { x }` 重导出都不算引用。
  这条不在本次修法内，先量在纸上。
- **`up` 的截断仍按字母序取前 200**：`upward()` 排序键是 (symbol, file, line)，
  所以「哪 200 条活下来」与被改符号的相关性是零。#43 落地后噪声少 75%，这条的伤害跟着变小，
  但仍然应该改成「import 支撑的先留」。留作 #43 之后的独立一笔，不夹带。
- **进程内图缓存（P1-6 手法③）先不批**：见下节耗时读数——**边构建与排序才是那 170ms 的主体**，
  而它正是 #43 要砍 4 倍的那一块。先修精度再复测，否则是给一个即将缩小的成本加常驻 19 MiB 的缓存。

## 五、顺带量到的耗时（同一轮，`buildImpact` 拆段）

| 段 | 实测 |
| --- | --- |
| `scanSourceFiles`（帽 400） | 13.7ms（无帽全量 13.3ms，441 个候选） |
| `buildImpact` 冷启动（空缓存目录，全量解析） | 首次 1,462ms，之后 168–174ms（grammar 已热） |
| `buildImpact` 温（缓存全命中） | **170.6ms** |
| 每次编辑后那一次（先让 1 个文件指纹失效，连测三轮） | 166.2 / 162.1 / 170.2ms |
| `fileImpact` 每次编辑后那一次（写后钩子完整一跳） | 163.1 / 162.9 / 171.6ms |
| 连改 5 个文件（5 次全量建图） | 829.6 / 826.3 / 843.9ms |
| └ 读 400 个 tags 缓存 + JSON.parse | 30.6ms |
| └ addSites 建 defs/refs 表 | 6ms |
| └ **边构建（笛卡尔积 + seen）** | **90.1ms**（内层迭代 208,247 次，产出 194,292 条） |
| └ **`edges.sort` 用 `localeCompare`** | **39.4ms**；同一比较器只把字典序换成码位序 = **4.4ms** |
| └ defs/refs 站点清单排序 | 7.1ms |
| 一张图常驻堆 | ≈19 MiB（ΔheapUsed，含 GC 噪声） |
| `graphCandidatePosition`（「不在图内」那次候选集重扫，#41 加的） | 13.5ms |
| `affectedFilesOf`（spawn 语义租约准入） | 184.7ms |
| `graph.files.includes` ×1000 | 0.1ms |
| `[...defs.keys()].filter(...)`（取该文件符号）×1000 | 111ms ⇒ **0.11ms/次** |
| `downward(graph, file)` ×1000 | 154ms ⇒ 0.15ms/次 |

三条结论：
1. **P1-7 的「线性扫描改 Set/倒排索引」这半实测不值得做**——三项都在 0.1ms 量级，
   对面是 170ms 的建图。原文那句「可改 Set/倒排索引」的收益是零头，别照着做。
2. 170ms 的主体是**边构建 + 排序**（129ms），两者都随边数超线性/线性放大。#43 把边砍 75%
   之后这笔会自己缩小 ⇒ 复测在 #43 之后（已立任务）。
3. `localeCompare` 那 35ms 是真的，但**换比较器会改输出次序**，而次序正是「哪 200 条活下来」的判据
   （见 §四 缺口 ③）。所以这条不做成性能优化，要做就做成排序策略的一部分，一起裁。
4. 一次模型往返是秒级，`fileImpact` 是 163ms；修完精度如果降到 ~50ms，「每次编辑全量建图」
   在墙钟上就不构成 P1。**这就是手法③至今没批的原因**：先证明它省的还是笔值得省的账。

## 六、复现

探针是 .gitignore 里的一次性读物（`.tmp/p3.ts`，未跟踪、不入库）：
`TERM=dumb node --import tsx .tmp/p3.ts`（在仓根跑）。它做四件事：
① 逐条 pattern 单独编译并在同一棵树上跑，按编号归因捕获数；
② 「模块作用域」判据 = 从捕获节点向上到 `program` 的路径上没有函数体/语句块/类体节点
   （注意：不能只看「能否走到 program」——那样所有节点都是模块作用域，第一次跑就错过一次）；
③ 真依赖 = 调用方 import 了该名字 ∧ 该名字定义在别的文件；
④ 三个变体各自重算边数/文件对/召回。
v0 的站点级边数与线上 `buildImpact` 返回值逐字相等（194,292），这是这条复刻可信的依据。
