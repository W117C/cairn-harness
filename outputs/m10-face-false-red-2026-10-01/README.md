# M10 · 多面验证「一起跑」时各面的假红率（2026-10-01）

**一句话结论**：**当场 9 条面-跑零假红；历史 84 趟全量判卷里红过 11 趟，其中 2 趟有名字、有同树对照的假红，两趟都在"撞窗"态。**
也就是说——**"一起跑会假红"不是假说，真发生过；但当前这棵树（在 `testTimeout: 30_000` 与 `HOOK_BUDGET_MS` 之后）已经量不到它了。**

---

## 一、这一格以前为什么没量过（用仓里自己的话，不是我的判断）

`scripts/lib/head-cert-deps.ts` 里那两段注释把话说尽了：

> **`collisionHint`**：「判卷有红，且两端采到 N 套判卷并行 ⇒ 先排撞窗再查代码（判卷面有写共享 `/tmp` 的用例，
> 两套并行会互踩出假红；本次读数不是独占跑的）」

> **`timingNearCapCell`**：「**安静态这一格读数是 0 条**，这是事实不是缺陷：这一格量的是
> "隔壁会话在同一台机器上跑起来的那一刻"，**而那一时刻恰好就是红发生的那一刻**」

⇒ **机制建好了（能报"你在撞窗"），撞窗那一刻的假红率没有读数。** 本笔补的就是这一格。

## 二、口径（写死在这儿，免得读的人自己猜）

| 项 | 定义 |
|---|---|
| **假红** | **树没动**（每趟前后 `git rev-parse HEAD` + `git status --porcelain` + `git diff --stat` 逐字相同）而某面报红 ⇒ 那一次红是假的；再用**单独复跑**确认（单跑绿 = 假红；单跑也红 = 真红，不算进分子） |
| **面** | 判卷（`test`）／类型面（`typecheck`）／门面（`gates` 快门面 20 道 = `.github/workflows/verify.yml` 逐字点名的那 20 道）。**本仓没有 lint script**（`src/agent/verify.ts:73` 的 `lint?: string[]` 在本仓是空的）⇒ 门面就是 lint 那一格的位置 |
| **臂 Q（对照）** | 三面**依次**跑（不存在撞窗），作为真红基线 |
| **臂 C（一起跑）** | typecheck + 判卷 + 快门面**同时起**（依次跑不存在撞窗） |
| **「一起跑」的总判卷套数** | 环境里已有的 + 我自己起的；由仓里现成的 `countConcurrentSuites`（按 pgid 去重）每 2s 采一次 |

## 五、两次有名字的假红——**最硬的那对是同一棵树一红一绿**

### ① `bd5ec44`：同一棵树 `bd5ec4496c0f32ad79b194d9e7237faab1067c38` 跑了两次

| 跑 | 判卷结果 | 并发判卷 |
|---|---|---|
| `head-cert-bd5ec44-run1.log` | **2 failed** \| 3369 passed (3371)，**exit=1** | 起前 1 套／跑完 **2 套**（撞窗） |
| `head-cert-bd5ec44-run2.log` | **257 passed (257)**，**exit=0** | 起前 1 套／跑完 **0 套** |

同一棵树、同一条命令、同一份判据 ⇒ **撞窗那趟红、独占那趟绿**。
红的两条也不是断言失败，而是 `Error: Test timed out in 5000ms`（`outputs/judge-timeout-2026-10-01/analyse.mts` 头注释记着：
"隔离复跑 205/205 全绿"）。**这是本格最干净的一对证据**：它同时给出了假红的存在、方向（并发）、与机制（超时而非断言）。

### ② `e42b4af`：撞窗态钩子超时

`outputs/hook-budget-291-2026-10-01/wait-and-verify.log` 原话：

> 「把真仓那支 `beforeAll` 的显式时限摘掉…钩子改吃 vitest 缺省 10s，而 `scanRepo(真仓)` 冷缓存实测 **8.9～9.5s**：
> **空闲刚好过、隔壁起一套判卷就炸**（`e42b4af` 那趟认证就是这条：`Error: Hook timed out in 10000ms.`）」

该趟的并发读数正是撞窗（起前 0 套／**跑完 1 套**）。**第二趟想复现独占却拿不到窗口**——
日志里只有一行 `STILL_BUSY_AFTER_180s  # 没起尺，这一趟不构成认证`（等了 180s 机器仍然忙）。
⇒ **这既是假红的第二例，也是本机"拿不到独占窗口"的直接证据。**

**容量红签名全史只出现 3 处**（`Test timed out` / `Hook timed out`）：上述 `Hook timed out in 10000ms` 一处、
`outputs/orchestrator-hold-column-2026-09-30/self-check-1.log` 的 `Test timed out in 5000ms` 两处。
**三处都在"缺省预算"下发生**——这与后来的修法（`testTimeout: 30_000` + 两处重钩子显式 `HOOK_BUDGET_MS = 30_000`
+ `mutate-shards` 等拿到 15000ms 显式预算）正好对上。

## 六、结论与建议

1. **当前"多面一起跑"是安全的**：当场 9 条面-跑零假红，3632 条逐条用例零贴帽（最紧的一条占帽 61%）。
2. **但这不是天然如此，是修出来的**。两处历史假红的根因分别是"缺省 5s 超时"与"缺省 10s 钩子帽"，
   两者都已被后来的显式预算堵住。⇒ **要守住的不是"再加一层保险"，而是那句已有的贴帽读数**
   （`timingNearCapCell` 每次认证自动印一行）。
3. **不建议加重试/降级**：撞窗这件事仓里已经会印方向（`collisionHint`），而重试会把**真红**一起吞掉——
   本仓最忌讳的就是"把红变成绿"。**"一起跑会红"也不是我这笔代码错**，`collisionHint` 刻意不改退出码，理由原文：
   "接进退出码等于把这道门变成共享树上的随机红"。
4. **余量最薄的那一格是 `tests/m3c.test.ts`**（撞窗态 15242/25000ms = **61%**，本身就是全表最慢的）。
   要盯就盯它——它是"下一个 m3c 在哪里"的答案。
5. **给业主的一条资源读数**：8 核 / 8GB 的机器上，**"拿到独占窗口"并不总能做到**——
   84 趟里有 9 趟是在别的判卷并行时跑的；有一次认证为了争独占**等了 180s 仍然失败**。
   撞窗态峰值 **19 个 node 进程 / 1288MB**。⇒ 多 agent 并行时，判卷读数**默认应读作"非独占"**，
   而不是默认"我的读数是干净的"。

## 七、诚实标注（没量到的，不许读成 0）

- **样本小**：当场只有 3 条臂 / 9 条面-跑。零红**不等于**"假红率是 0"，只能说"这一轮没量到"。
  要更硬的率，得把臂 C 的趟数提上去（每次一趟 ~180s）。
- **不是真安静**：臂 Q 自己那一趟环境 0 套判卷，但 `load1` 仍有 **3.86–6.20**——
  这台机器上 `WindowServer`、DSH 渲染进程、`FlClash`、Qoder 渲染进程常驻吃 CPU。所谓"独占"只是**没有别的判卷**，不是没有负载。
- **臂 C 的 2 套是"环境 1 + 我 1"**：环境的第二套是另一个 Claude 会话的全量判卷（采样里 1–2 套波动是因为它中途结束了）。
  两套跑在**同一棵树**上是刻意加重（共享 `/tmp` 名 + 共享 vitest 缓存），属**最坏情形**，不是常态。
- **一趟被我自己的判据作废**：上一轮抢在"环境真有别的会话在跑"时跑的臂 C，第 1 趟横跨了另一个会话的两笔提交
  （`2ec61c8` 20:25:59、`be944f4` 20:26:06）⇒ 指纹变了，探针**主动标成不可用于判假红**。
  那趟的裸证据留在 `raw/ambient-contention-2025/`（两趟判卷日志都写着 271 文件 / 3632 条全过，
  外加那趟的 `results.json` 快照、采样与跑前树指纹）。**该目录里没有再放一份 1.6MB 的判卷 json 副本**：
  同一份证据日志里已经完整（默认 reporter 逐条印了用时），本仓不宜重复存同一份证据（那个副本是本次清理时删掉的）。
- **`suite-b.json` 不存在**：本轮臂 C 只起 1 套判卷（`--suites=1`），没有第二份 json ⇒ 那一格是"没量到"，
  不是"0 条贴帽"。
- **历史红 ≠ 假红**：说过了，仍要再说一次——表格里 11 趟红只有 2 趟能证成假红。

## 八、怎么复现

```sh
# 1) 当场读数（臂 Q 依次跑、臂 C 同时跑；--suites=N 控制臂 C 自起几套判卷）
node --import tsx outputs/m10-face-false-red-2026-10-01/probe.mts --arms=Q,C --reps=2 --suites=2

# 2) 出表（从 results.json 重算，不手抄）
node --import tsx outputs/m10-face-false-red-2026-10-01/analyze.mts

# 3) 挖历史（扫 outputs/ 下所有日志里的全量判卷汇总行）
node --import tsx outputs/m10-face-false-red-2026-10-01/mine-history.mts
```

**零源码改动、零模型花费**：三个脚本都在 `outputs/` 下，不进 `scripts/`（避开门禁的恒真式体检扫描面与孤儿验收脚本护栏），
不动 `package.json`。

## 九、写这份读数时自己踩的两个坑（留个记号）

1. **`persist()` 读自己刚写的纸面**：原先每次落盘都现读一次 `results.json` 判"是不是新阶段"，
   而同一进程里 `persist()` 会被调两次（每趟收工一次、收工后一次）⇒ 第二次读到的正是自己刚写的，阶段相同 ⇒
   判成"同阶段"⇒ 拿内存里那几条**覆盖掉刚合并好的结果**，臂 C 的读数就这么丢过一次（裸日志还在，机器可读的表没了）。
   ⇒ 已改成**每进程只读一次**纸面，之后一律"带过来的 + 自己的"。**教训与本仓那句"两份字段清单就是两次会漂的账"同族**：
   判"要不要合并"时，别把判据押在自己刚写出去的东西上。
2. **横幅照着另一条臂印**：跑 `--arms=Q` 时横幅仍照臂 C 的清单印"自起 2 套判卷"，而实际只起 1 套 ⇒ 会误导读数的人。
   已改成按当前这条臂真会起的面印。**读数的前提条件印错了，比读数错更糟**——它让复核的人按错误的形状去核对。
