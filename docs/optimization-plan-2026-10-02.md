## 1. 工作波次

### W1 · `outputs/` 提交占比封顶门（新增 `repo-hygiene-check` 第 ① 面）

**取证**：`git ls-files | grep -c 'outputs/'` = **1446**，总已跟踪 **2440** ⇒ 占比 **59.2%**。
`outputs/` 是取料（实验日志），不是源码；`.git` 已 73MB。

**为什么这条要进门**：本仓的规模失控不是"文件多"，而是**取料与源码同仓**——
每一次实验取料都进git，于是 `git ls-files` 的信噪比降到 41%，而 `docs-check` 等门
正以 `git ls-files` 为取料面。

**做法**：
- 新增 `scripts/repo-hygiene-check.ts`，纯读 git 清单，**零写入**。
- 判据：`outputs/` 已跟踪占比 > 帽 ⇒红。帽取**当前实测值上取整**（不是拍一个理想值），
  否则第一天就红、门被当成噪声关掉。
- **口径纪律**：占比必须与分子分母**一起打印**（规则82：范围得是字段，不是数出来的差值）。
  只印一个 `59.2%` 会被读成「其中有多少是源码」——那件真事它答不了。
- 门自带**反向验证**（把 `outputs/` 清空后必须转绿），沿用本仓「每条核心断言配一条反向验证」。

### W2 · 单文件体量封顶门（第 ② 面）

**取证**：`src/main/agent-runner.ts` = **2,761 行**（8 个不相关关注点）；
`src/agent/orchestrator.ts` = **2,564 行**（单个 `Orchestrator` 类 **45 个方法**）。

**做法**：同一支门加第② 面——`src/**/*.ts` 单文件行数超帽即红，**并点名是哪一支、当前多少行**。
点名是硬要求：本仓吃过「一 道门红了但不知道红在哪」的亏（路线图记「合并冲突从 5 处涨到 13 处」）。

**帽的取法与 W1 同纪律**：取当前实测值上取整，先让门绿着站住，再逐波降帽。
**降帽必须一次只降一档、且在提交信息里写清降到多少**——否则多会话并发下没人知道是谁在哪一档上撞的红。

### W3 · `goal-drift.ts` 接进运行路径（消掉真孤儿）

**取证**（全树 import 扫描，非文件名 grep）：
`src/agent/goal-drift.ts` —— **`src/` 内零消费者**，只有 `tests/goal-drift.test.ts` 引用。

**对照**（同样src 零引用但**不算缺陷**，已核实）：
- `src/agent/reproducibility.ts` → 被 `scripts/gym-check.ts` / `replay-determinism-check.ts` 消费；
- `src/agent/eval/task-set.ts` → 被 `scripts/loop-eval.ts` 消费。

⇒ `goal-drift` 是三者中唯一**既无生产消费者、也无判卷消费者**的一支。

**做法**：在会话收束处（`runAgent` pipeline，事件流盖章点所在）算一次目标漂移，
读数落进事件流；判据函数一律取 `goal-drift.ts` 现有导出，**不抄第二份**。
接线前先确认它当前导出面与调用点签名——**这一波需要读代码后再定实现形态**，不预判。

### W4 · `agent-runner.ts` 按「拆分面」先例切出调度器块

### 7.2 查出来**确实**成立的一条：安全合入门缺判卷

这是本轮唯一有实测支撑的新缺口，链路已逐段核实：

```
worker 写盘 → 静态扫描 scanChangeSet（security/scan.ts，有 43 条门 + 变异锚点）

           → w.lastFindings = merged
           → mergeWorker：safeMode==="gate" 且有 high|critical ⇒ 未 force 则拒绝合并
```

**缺口在中间那一段**，三处证据：

| 证据 | 读数 |
|---|---|
| 专用判卷 | `tests/` 里**零**条断言调 `llmReviewDiff`；只有 `hardening3.test.ts` 引了同文件的 `buildMessages`（只测消息拼装，不测 findings 产出） |
| 变异锚点 | `scripts/mutate-verify.mjs` 的 1234 条锚点里，`src/agent/security/llm-review.ts` **一条都没有** |
| 常跑门 | `scripts/security-check.ts` 里 `llm` 出现 **0** 次、`gate`/`merge`/`blocking` 出现 **0** 次 ⇒ 43 条安全门**不覆盖**合入门 |
| 现有间接覆盖 | 只有 `tests/terminal-sync-window.test.ts:142` 设了 `safeMode:"gate"`，但它断的是**合并时序**（安全流水未跑完不许合并），**没有断「有 high/critical 时必须拒」这一格** |

**为什么这一格值得补**：它是「静态扫描漏了、但 LLM 审查补上了」这条**唯一**的兜底路径。
`llm-review` 出错时按设计 `findings: [] + error`，静态 findings 照常生效（降级方向正确），
但**「LLM 补出来的高危能不能真的挡住合并」这一格没有证人**——
把 `severity` 判错、把 findings 丢掉、或把 `high` 从 blocking 里去掉，现有判卷**一条都不会红**。

**建议的最小修法**（不写实现，只给判据形状）：
给 `security-check` 加一段真跑断言——构造一个「静态扫描干净、LLM 报high」的 worker 收尾，
断言 `mergeWorker` 在 `safeMode:"gate"` 下 `ok:false`，且 `force:true` 时才放行；
再加一条反向验证：把 `severity==="high"` 从 blocking 过滤器里去掉，该断言必须转红。

实测取证（三步）：

1. 完好态：`{"approved":["/etc/hosts"],"declined":[]}`
2. 把文件截断成半截 JSON（模拟写坏/掉电）
3. `loadExternalRefState()` 返回 **`{"approved":[],"declined":[]}`**，**不吭一声**

⇒ **用户批准过的 @path 全部回到未批准**（每次回注重新问一遍），
**拒绝过的也一并回到未决**（等于拒绝记录也没了）。而这是**安全决议**在蒸发。

**为什么说它与本仓既有纪律冲突**：`src/routing/bandit.ts` 的 `loadBanditState`

记忆这边还留着同一种写法。

### 7.11 `tools/apply_patch.ts`（优先级 2 的第四条）——已有 28 条判卷，补的是两种形状

#### 查出来的两处（都是**安全地拒绝**，不是静默改坏）

**① CRLF 文件（同族：BOM）**
`contentLines`（`src/tools/line-delta.ts`）只按 `\n` 切 ⇒ 每行留着 `\r`；
而 `locate` 要求**逐字**相同（源码注释：「静默改到别处比改不动危险得多」）。
实测：CRLF 文件 + LF 补丁 ⇒ 抛错，报错正文把差异点出来
（`期望 "line one"，实际是 "line one\r"`），**盘上 32 字节逐字节不变**。
BOM 同族同结果（`实际是 "﻿line one"`）。

**② hunk 不按升序排列**
`buildFile` 按补丁里的**出现顺序**推进 `cursor`，于是「先声明第 4 行那段、再声明第 1 行那段」
会被判成「与上一处重叠」。实测抛错、盘上不变；把同样两段**升序**排列则正常落地
（对照组证明拒的是顺序不是内容）。

#### 为什么值得钉（即便两条都是安全侧）

**CRLF 这条尤其值得**：将来有人觉得「CRLF 匹配不上很难用」而去 `strip \r`，
那会把**整个文件的行尾**静默改写成 LF —— 比拒绝坏得多，而**那时没有一条断言会红**。
反向验证第 1 条就是钉这个的。

**②顺带记一处文案不准**：两段并没有重叠，只是顺序反了，报错却说「重叠」。
本轮**不改文案**（会动到既有判卷的文案面），只把现状与「为何不改」写进用例注释。

**生产代码一行未动**（`apply_patch.ts` 与 `line-delta.ts` 的 `git diff` 均为空）。

### 7.12 `routing/bandit.ts`（优先级 2 的第五条）——查出**一个真的挂死**，并修了

**普查读数**：162 行、**零**变异锚点；`nextRandom` / `defaultPosterior` / `armKeyOf` **零判卷**，
而 `docs/m5-proposal.md` §5.12 把「同 seed 两次跑逐字段一致」写成了**验收要求**。
要求在文档里，却没有人钉它。

#### 先排除的：RNG 本体是对的

实测（seed 1/42/99/1234/7）：同 seed 逐值一致 · 值恒在 `[0,1)` · 2000/2000 全不重复 ·
十桶分布最大偏离 34（噪声带内）· 不同 seed 不同序列。**没有缺口，补判卷钉住即可。**

#### 查出来的真缺口：畸形 posterior ⇒ `selectArm` **挂死**

链条（每一步都实测过，不是推断）：

1. `loadBanditState` 的守卫只查到「`posteriors` 是个非 null 对象」就放行，
   **`{"alpha":"oops"}` / `{"beta":2}` 这类条目内部畸形原样通过**，`onCorrupt` 不触发；
2. 该值流进 `selectArm` → `sampleBeta` → `sampleGamma(p.alpha,…)`；
3. `shape` 是字符串 ⇒ `shape - 1/3` 得 `NaN` ⇒ 拒绝采样的判据
   `Math.log(u3) < …NaN…` **恒为 false** ⇒ `for(;;)` **永不退出**。

实测对照（子进程自带时限，强杀判定）：

| posterior | 结果 |
|---|---|
| `{alpha:1,beta:2}` 合法 | OK |
| `{alpha:"oops",beta:2}` | **HANG（>3s 强杀）** |
| `{beta:2}` 缺 alpha | **HANG（>3s 强杀）** |
| `{alpha:-5,beta:2}` / `{alpha:null,…}` / `{alpha:2,beta:"x"}` | 返回，不挂（但仍是畸形） |

> 取证方法记一笔：我第一版用 `timeout 4 node …` 批量测，**macOS 没有 `timeout`**，
> 于是**每一种形状都被印成 HANG**，差点报出一个不存在的 bug。
> 改用「Node 子进程 + 父进程自带时限 + `SIGKILL`」才拿到上面这张可信的表。

**为什么它违反本仓自己的纪律**：`loadBanditState` 的文档原话是
「文件存在但损坏/畸形 = 学习历史无痕丢失，**必须经 onCorrupt 显式告警**」——
**承诺在，兑现没到位**（只查了顶层，没查条目）。

#### 本轮唯一一次改生产代码（4 行 + 注释）

`src/routing/bandit.ts` 加 `isValidPosterior()`，在既有守卫之后**逐条**校验
`alpha`/`beta` 是正的有限数，坏条目**点名**报错 ⇒ 走既有的 `onCorrupt` + 重播种路径。

为什么这次可以动生产（与前四轮「只钉不改」不同）：
① 它的**文档承诺已经存在**，这是补齐实现，不是新决策；
② 后果是**挂死**（可用性），不是可两解的取舍；
③ 对**任何合法状态零行为变化**（实测：合法态 `onCorrupt=no`、不重播种、`selectArm` 正常）；
④ 改动量 4 行，走的是文件里**已有**的 `throw → onCorrupt` 通路，不新增机制。

修后实测：6 种畸形全部 `onCorrupt=YES` + 重播种 + `selectArm` 正常返回（不挂）。

## 8. 横向排查：「只查顶层、不查条目」这一族缺陷全仓分布（2026-10-02）

§7.12 在 bandit 上撞到的那族缺陷值得横向查一遍：**读一份状态/清单文件时，
守卫只到顶层（是不是对象/版本对不对），不逐条校验条目内部**。
这类缺陷的危险在于条目里的值会流进后续计算——在 bandit 那儿流进了 Gamma 采样器（挂死）。

### 8.1 取料面：全仓 18 处「读文件并 JSON.parse」

按后果排序（时间触发的执行 › 授权 › 凭据 › 路由学习 › 记忆 > 靶场/插件配置）。

### 8.3 剩下那一处的严重性：比 bandit 轻得多（实测后才敢这么说）

`loadExternalRefState`（外部 @引用的批准/拒绝状态）损坏后返回空态。逐格验过后果：

| 维度 | 结论 | 依据 |
|---|---|---|
| **安全性** | **fail-closed，不漏** | `inject.ts:76` 只在 `state.approved.includes(ref)` 时放行；空态 ⇒ 无一批准 ⇒ 全部走「未批准」分支被替换成 `[外部引用已停用: @…]` |
| 授权的**内容** | 不泄漏 | 同上 |
| 体验 | 用户批准/拒绝过的 @path **要重新问一遍**（决策记忆丢失） | 完好态 `approved:["/etc/hosts"]` → 损坏态 `approved:[]` |

⇒ 与 bandit 的差别是**本质**的：bandit 是**挂死**（可用性全失），
这一处是**静默但安全**（决策遗忘 + 重复询问）。
所以本会话**不动它**——改成抛错会让重复询问变成硬失败，比现状更差；
真要改，正确形态是 bandit 那套「告警 + 继续」，而那需要把回调从 `inject.ts` 一路铺进来，
是一次独立的改动，不该顺手塞进补判卷这一轮。

### 8.4 这一族给本仓留下的可复用结论

**好的一面**：18 处里 16 处是对的，且 `scheduler` / `provider-keys` / `license` / `gym`
四家的报错都**带定位信息**（第几条 / 哪个 id / 哪个 provider），
不是一句「格式错误」。这与「让门说的话等于门测的事」是同一条纪律的另一种体现。

**该盯的是新写的读点**：bandit 与 memory 都是**后加的**功能
（`routing/bandit.ts` 是 M5b 的，`memory/store.ts` 的 external-refs 是 §8.1.8 的），
不是早期骨架。也就是说：**纪律在老代码上执行得好，在新功能上漏了**。
建议把这条写进新代码的检查清单：**凡新增「读一份 JSON 状态」的函数，
必须逐条校验条目，且每条错误要带定位信息**——这三样在 16 处正确实现里都是齐的，
照抄成本极低，而漏掉的代价是 bandit 那次实测出来的挂死。
