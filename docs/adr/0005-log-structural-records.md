# ADR 0005：日志结构控制记录（log-structural records）

- 状态：**已接受**——2026-10-22 业主定案「回退 / 元数据更新走既有字段还是新事件型」，本 ADR 把裁决落成可执行的协议与投影约定
- 日期：2026-10-22
- 决策者：仓库所有者
- 取代：无（**澄清** `docs/CODE-WIKI.md` §①.3 第 3 条「新增能力优先走既有字段的 origin 通道，而不是新增事件类型」的适用范围，不推翻该条）
- 关联：`src/events/types.ts`（协议面）、`src/events/projection.ts`（投影面）、`src/events/log.ts`（存储面）、`src/agent/session-cursor.ts`（游标）、`src/agent/submission-ledger.ts`（提交幂等）

## 背景

`docs/CODE-WIKI.md` §①.3 第 3 条写着：「新增能力优先走既有字段的 origin 通道，而不是新增事件类型」。
理由是实的：新增一种事件会让每条旧日志的重放都多一个分支，而重放面是本仓最贵的那条面。

但这一轮要落的两样东西——**回退**（把会话退回某个事件点）与**会话元数据更新**——
与那条规则的前提对不上：

- 它们描述的不是「agent 做了什么」，而是「**日志本身**被怎么了」。
- 它们没有 origin 通道可挂：`user_message.origin` 挂的是「这条消息的来源」，
  而回退指针挂的是「**整段历史**的位置」，两者不是同一维度的信息。
- 先例已在仓内：`compaction`（关于日志的记录：摘了哪些事件、摘要插在哪）与
  `session_meta`（关于会话身份的记录）**都是既有事件型**，不是既有字段。

于是本 ADR 要同时保住两件事：§①.3 那条纪律不被悄悄废掉，以及回退/元数据这两样能力有地方落。

## 裁决

### 1. 适用范围：§①.3 管「agent 做了什么」，不管「日志怎么了」

> **§①.3 治理的是描述 agent 行为的那些能力。它不治理日志结构控制记录——关于日志本身的记录。**

分界线一句话：**这条事件说的是「agent 干了什么」还是「日志被怎么了」？**
前者走既有字段的 origin 通道（新增能力 = 加一个可选字段 + 一个投影分支）；
后者才允许新事件型。

「允许新事件型」不等于「可以随意加事件型」。下面两条是硬约束。

### 2. `replay()` 保持哑且逐字：解释控制记录是**投影**的活

`replay()` / `replayIncremental()` **原样返回**落盘的事件，控制记录包含在内——一条不少、一字不改。
读侧要「有效历史」（回退之后的样子）时，走**投影层**：

- `src/events/projection.ts` 的 `effectiveEvents(events)` —— 应用全部回退后的消息历史；
- `src/events/projection.ts` 的 `sessionMetaPatch(events)` —— 累积的会话元数据补丁。

这是本 ADR 的核心架构动作，也是「JSONL 逐字重放」与「事件 id = 1-based 行号」能**同时**为真的原因：

- **逐字重放**成立，是因为 `replay()` 不解释任何东西；
- **id = 1-based 行号**成立，是因为控制记录**照旧占着自己的行**——它不回填、不改写、不删除任何已落盘的行。

一条控制记录进了日志，它就永远在那儿、永远占一行号；「回退之后的历史」是**读侧算出来的**，不是**盘上被改过的**。

### 3. 哪些能力进新事件型、哪些走既有字段

| 能力 | 落点 | 理由 |
| --- | --- | --- |
| 回退（会话退回某事件点） | **新事件型** `session_rewind` | 描述的是日志的位置，不是 agent 的行为；origin 通道无处可挂 |
| 会话元数据更新（改名/别名/标签…） | **新事件型** `session_meta_update` | 同上；且它是**会话属性**的增量，与消息历史正交 |
| 压缩 | 既有事件型 `compaction`（先例） | 早已是「关于日志的记录」 |
| 分叉血缘 | 既有事件型 `session_meta.fork`（**新增可选字段**） | 血缘挂在会话身份记录上，不另起事件型 |
| 权限判定留痕 | 既有字段 `tool_result.gate`（先例） | §①.3 的正面教材 |
| sidechat 提升 / goal 续跑 | 既有字段 `user_message.origin`（先例） | §①.3 的正面教材 |

判别口诀：**「这件事发生在日志里」还是「这件事发生在 agent 身上」？**

### 4. 新字段的缺席语义（每一格都写死，不许读成「零」）

沿用 §①.3 第 2 条「缺席 ≠ 零」的纪律：

| 字段 | 缺席 = |
| --- | --- |
| `session_rewind.to_event_id` | **必填**（缺席 = 坏事件，不是「回退到 0」） |
| `session_rewind.reason` | **没记理由**（不是「没有理由存在」） |
| `session_meta_update.patch` 的某个键 | **该键不变**（不是「清空该键」） |
| `session_meta_update.patch` 整体为空 | **什么都没改**（记录存在，但这一笔不改变任何东西） |
| `session_meta.fork` | **这是个独立/根会话**（不是「边界 0」） |
| `session_meta.fork.boundary_event_id` | **含**该条（1-based 行号口径，与 `to_event_id` 同族） |

「独立会话」与「边界 0」必须分得开：前者是「压根没有父会话」，后者是「父会话存在但一条都不继承」。
把缺席读成边界 0，独立会话就会被当成「分叉自某个空前缀」，血缘树整个歪掉。

### 5. 回退的语义与「响亮地失败」

`session_rewind.to_event_id = N`（1-based 行号口径，含 N）：

- 有效历史 = 日志里 id ≤ N 的事件（**含** N）；
- 回退标记**本身不在**有效历史里（它是对日志的记录，不是历史的一环）；
- 标记**之后**的事件全部丢弃（那正是「回退」的意思）；
- 多次回退：后一条作用在**那一刻**（已被截短）的历史上，只会截得更早。

坏控制记录**一律抛**（`ProjectionError`），不静默忽略：

- `to_event_id` 非整数 / < 1 → `rewind-invalid-target`；
- `to_event_id` 越过当前边界（指到还没发生的行，或指到已被前一次回退丢弃的行）→ `rewind-out-of-range`。

理由：一条坏控制记录会让整份历史变得不可判读；静默忽略它等于交出一份看着没事、其实算错的历史。

### 6. 分叉是**指针**不是拷贝

会话分叉不复制父会话的事件：新会话的 `events.jsonl` 只有**一行** `session_meta`，
带着 `fork?: { from_session_path, boundary_event_id, from_session_id? }`。

- 父会话文件**只读**（字节不变，可被 sha256 钉住）；
- 读侧用解析器（`replaySession(path)`）把「父会话前缀 + 本会话自己的事件」合成有效历史；
- **在飞状态不继承**：父会话里「已发起但未收尾」的那几笔（`tool_call` 无配对 `tool_result`、
  `clarify_requested` 无配对 `tool_result`、`plan_proposed` 无配对 `plan_approved`、
  `approval_requested` 无配对 `approval_resolved`）**不跟着继承**——
  子会话没有那个「等结果」的上下文，接过来就是一笔永远等不到的挂起。

解析器 fail-closed：父会话文件缺失、边界越界、父链成环 ⇒ **抛**。

`forkSession()`（拷贝式）**保持原样**：gym 的反事实实验需要一份**独立文件**去重跑，
拷贝在那儿是工具需要，不是产品语义。

### 7. 游标不透明且 fail-closed

游标（继续一条会话的指针）编码成不透明字符串（base64url 的紧凑 JSON + 版本号 + 短校验和）。
四种坏法各有各的码，**一律抛，绝不换一个位置顶上**：

| 码 | 触发 |
| --- | --- |
| `malformed` | 解不开 / 校验和不符 / 版本不对 / 形状不对 |
| `unsupported-kind` | 解得开、校验也对，但种类不是本实现支持的 |
| `session-mismatch` | 游标属于**另一个**会话 |
| `out-of-range` | 位置越界（超出事件数，或 < 1） |

「绝不换成另一个位置」是重点：旧式的默认回落（「接着上一轮」）会把续跑接到**另一个**状态上，
模型看着一段不是它自己写的历史继续干，而日志里查不出断点。

游标的 `eventId` 是**含**的（指针所在的那一条属于重放范围，与 ACP `session/resume` 的 `replayFrom` 同一口径）。

### 8. 提交幂等：`requestId`

工具/提供方提交带一个 `requestId` 幂等键：

- `submit(requestId, run)` —— **幂等且失败粘滞**：同一个 `requestId` 再提交一次，
  返回已记录的结果（或重抛已记录的错误），**绝不重跑**。失败过的提交**也算提交过**：
  重试不会重新执行（否则「失败 → 重试 → 再失败」会把一次失败放大成两次副作用）。
- `submitOnce(requestId, run)` —— **只在飞去重**：并发调用共享第一个 promise，但**失败不粘滞**，
  之后可以重试。给「同一瞬间只许跑一次、但失败后允许再来」的场景用。

键的推导：`submissionRequestId(scope, toolCallId)`，**按会话分域**。
碰撞边界：provider 的 tool-call id 在一次会话内唯一 ⇒ 同一次调用重放必碰撞、两次真正不同的调用不碰撞；
**但**一个 provider 若在同一会话里给两笔真正不同的调用复用了同一个 id，就会碰撞——这是已知边界，写在这里而不是假装不存在。

## 后果

- `AgentEvent` 联合新增两型（`session_rewind` / `session_meta_update`）⇒ **每条旧日志的重放都多一个分支**：
  这是 §①.3 想避免的成本，本 ADR 明确接受它（代价是**一次性的**：只有这一个分支，
  而不是每种能力各来一个分支），换来「回退」「元数据更新」不再挤进 origin 通道。
- 读侧多一个投影层入口（`effectiveEvents` / `sessionMetaPatch` / `replaySession`），
  但 `replay()` 本身**不变**——旧调用点一行不用改。
- 分叉从拷贝改成指针 ⇒ 父会话文件小、磁盘省；但**读路径必须走解析器**，
  漏一处就会看到「只有元信息、没有历史」的会话（这是本轮改动最需要盯的回归面）。
- 控制记录进脱敏表：带自由文本的（回退理由、元数据补丁的值）要扫，纯计数的（`to_event_id`）不扫。

## 被否决的替代方案

| 替代方案 | 为什么否决 |
| --- | --- |
| **回退塞进 `user_message.origin`** | origin 挂的是「这条消息的来源」，回退是「整段历史的位置」。维度不对：一条 origin 无法表达「退回第 7 条」。且回退不是任何用户消息带来的。 |
| **元数据更新塞进 `session_meta` 的更多字段** | `session_meta` 是会话**头**（首行身份记录），不是可追加的变更流。要记「第 3 轮改了标题」就得给它加时间序列语义——那已经是另一种事件了，只是名字没改。 |
| **回退/元数据走既有事件的**新增可选字段**（例如 `tool_result.rewound`） | 回退发生时**未必有工具结果**（用户手动回退就没有）；挂在工具结果上等于让回退依赖某次工具调用，虚构因果。 |
| **让 `replay()` 解释控制记录** | 会把「逐字重放」变成「重放即投影」：重放结果不再等于盘上内容，`id = 1-based 行号` 也要跟着重排（控制记录被吃掉后，后面所有行的 id 都会移位）——两条契约同时破。 |
| **回退 = 删掉后面的行（改写 JSONL）** | 破坏 append-only：事件 id 会漂移（`origin.source_event_ids`、`compressed_event_ids`、`parent_event_id` 全按行号引用），历史被抹掉后不可审计。 |
| **分叉继续用拷贝** | 磁盘随分叉数线性膨胀；父会话后续的修改不会反映到分叉上（拷贝是快照，语义上「分叉」更接近「指针 + 边界」）。保留 `forkSession()` 拷贝原语给 gym 用，但产品分叉走指针。 |
| **游标明文 JSON** | 明文游标会被手改；手改后若还照单全收，就等于允许调用方指定任意续跑位置。版本号 + 校验和把「手改」变成 `malformed`。 |
| **坏游标回落成「最后一条」** | 那会把续跑接到**另一个**状态上（模型看着不是它自己写的历史继续干），且日志里查不出断点。宁可炸。 |

## 推翻条件

- 出现第三类「日志结构控制记录」需求，且它无法表达为「日志位置」或「会话属性增量」；
- 或投影层被迫开始解释**非**控制记录（那说明控制记录与业务记录的边界画错了）；
- 或 `replay()` 的调用点开始需要「解释后再返回」——那时逐字重放这条契约本身已经破了。
